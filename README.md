# 多总线数据采集终端

**STM32F103C8T6** ｜ 全程寄存器手写（**不使用 HAL**） ｜ I2C + SPI + UART 三总线 ｜ **FreeRTOS** 三任务 ｜ 32 B 双 CRC 断电一致性记录

在 64 KB Flash / 20 KB RAM 的 STM32F103C8T6 上，从寄存器层实现三条总线的驱动，并搭起一条完整的
**采集 → 存储 → 上传 → PC 端校验** 数据链路：

- **I2C**（bit-bang）读 BME280 温湿压，含 33 个出厂校准系数与 Bosch 整数补偿算法
- **SPI**（bit-bang）驱动 W25Q64，实现顺序追加 + 断电续写的定长记录存储
- **UART** 上报实时数据、接收串口命令，并把整片记录区倒出给 PC 端逐字节校验

项目的重点不是"把外设跑通"，而是**可靠性设计**：共享总线的并发保护、断电瞬间的记录一致性，
以及"数据是否真的落盘"的证据链。

## 关键指标（均为实测，非估算）

| 项 | 结果 |
|---|---|
| 主频 | **72 MHz**（HSE 8 MHz × PLL9），开机回读 `RCC->CFGR` 自证，非"写了就算" |
| 资源占用 | Flash **27 948 B（42.6%）** ／ RAM **11 712 B（57.2%）** |
| RTOS | FreeRTOS V10.3.1（原生 API），3 任务 + 2 队列 + 2 互斥锁 + 1 二值信号量 |
| 记录格式 | **32 B 定长**：28 B 数据 + 头 CRC(2) + 尾 CRC(2) |
| 存储容量 | 记录区 4 MiB = **131 072 条**（1 Hz 采样约 36.4 小时） |
| 记录校验 | **1840 / 1840 条**在 PC 端独立重算头尾双 CRC，**100% 通过**，序号全程无跳号 |
| 温湿压校验 | PC 端独立复算 **30 项逐位一致**（含 64 位气压补偿中间量） |
| 稳定性 | 连续运行 **11.65 小时**（41 938 s）无复位；21 个采样点上记录数与运行秒数严格 1:1 |
| 栈空间 | 实测水位后重分配，总栈 1536 → **525 字（压缩约 66%）** |

## 系统架构

```
                     ┌──────────────┐
                     │    BME280    │  温湿压
                     └──────┬───────┘
                            │ I2C @ PB6/PB7（bit-bang）
                            │
   ┌────────────────────────┴────────────────────────┐
   │            STM32F103C8T6  @ 72 MHz              │
   │     寄存器手写 · 无 HAL · FreeRTOS V10.3.1       │
   └───────┬──────────────────────────────┬──────────┘
           │ SPI @ PA4~PA7（bit-bang）     │ UART1 @ PA9/PA10 · 115200
           │                              │
      ┌────┴─────┐                  ┌─────┴──────┐
      │  W25Q64  │  32 B × N 条      │  PC 端     │
      │  8 MB    │  顺序追加 + 断电续写 │  校验工具   │
      └──────────┘                  └────────────┘
```

### 任务模型

```
task_acq   (prio 4) ── vTaskDelayUntil 精确定时 1 Hz ──▶ [ q_raw · 8 ]
   │  取 I2C 锁读 BME280；读失败不阻塞、不重试、不写坏数据

task_proc  (prio 3) ◀── q_raw
   │  阈值判定（湿度 65% 触发 / 62% 解除 回差）→ 二值信号量通知报警
   │  打包 32 B 记录 → 取 SPI 锁落盘 ──▶ [ q_rep · 8 ]

task_comm  (prio 2) ◀── q_rep
      串口上报 + 命令处理（h/s/c/m/r/v/t/i/e/p）
```

**为什么这样切分**：采集任务的周期精度要求最高（1 Hz 不能漂），通信任务最慢也无所谓。
队列把"采集速率"与"存储 / 上报速率"解耦，队列满时丢弃并**计数**——
丢数据不可怕，丢了不知道才可怕。

## 技术要点

### 1. 三总线全部寄存器手写，不依赖 HAL

逐位实现 I2C 与 SPI 主机时序：

- I2C：START / STOP / Repeated Start、ACK/NAK 采样、总线卡死时的 9 时钟恢复
- SPI：CPOL/CPHA 四种模式可配，并提供 `spi_soft_transfer_ex(tx, tx_mode, rx_mode)`
  支持收发**使用不同模式**（用于演示主从模式不匹配）
- USART1：直接写 `BRR = 72000000 / 115200 = 625`，误差 0%

**动机**：时序细节必须可控。以 I2C 为例，早先的延时是 `for (i=0;i<5;i++)` 空循环，
注释写着"8 MHz 下约 3~4 µs"——主频从 8 MHz 提到 72 MHz 后它会直接快 9 倍，
现象是"在 8 MHz 下好好的，一提频就不通"。现在延时统一由 **DWT 周期计数器**产生，
与主频严格绑定，无需标定。

### 2. 共享总线的并发保护 + 带超时降级

三个任务共享 I2C 与 SPI 两条总线，用互斥锁串行化。关键设计是**锁超时降级**：

```c
if (app_lock_spi(LOCK_TMO_MS) != 0U) {      /* 200 ms 拿不到锁 */
    /* 跳过本拍落盘，但继续采集与上报 —— 不死等、不重试、不写坏数据 */
}
```

系统的设计原则是**永不无限阻塞**：`w25q64` 状态轮询、记录写入、串口收发全部带超时，
任何单点异常都不会把整个系统拖死。

### 3. 32 B 记录格式：头尾双 CRC 的分工

```
偏移   长度   字段
0–3     4     序号            uint32 小端
4–7     4     时间戳(秒)       uint32 小端
8–11    4     温度            int32（℃ × 1000）
12–15   4     湿度            uint32（%RH × 1000）
16–19   4     气压            uint32（Pa）
20–23   4     ADC 通道 1      uint32（预留）
24–27   4     ADC 通道 2      uint32（预留）
28–29   2     头 CRC          CRC-16/MODBUS，覆盖 0–27
30–31   2     尾 CRC          CRC-16/CCITT-FALSE，覆盖 0–29
```

字段一律**手工逐字节拆装**，不使用 `memcpy(struct)`——结构体会因内存对齐插入填充字节，
不同编译器 / 优化等级下填充位置可能不同，存储格式就不可控了。

**两级 CRC 的分工**：头 CRC 回答"数据区有没有被改坏"；尾 CRC 回答"这条记录有没有写完"。
配合**两步写入**（先写 0–29 字节，再写 30–31 字节），断电后的状态可以被精确区分：

| 状态 | 头 CRC | 尾 CRC | 含义 |
|---|---|---|---|
| `OK` | ✅ | ✅ | 记录完整 |
| `UNFINISHED` | ✅ | ❌ | **数据完整，只是没写完**（两步写入之间断电） |
| `HALF` | ❌ | — | 数据区被改坏（编程中途断电） |
| `EMPTY` | — | — | 全 `0xFF`，从未写过 |

单 CRC 方案只能区分"整条坏了"，会把 `UNFINISHED` 这类**数据完好**的记录一起丢掉。

> **一个容易踩的数学陷阱**：头尾两个 CRC 不能用同一个多项式。
> CRC 对初值是仿射的（`crc_J(m) = crc_0(m) ⊕ g_len(J)`），
> 因此只要第二条 CRC 的覆盖范围是「数据 + 第一条 CRC 的输出」且多项式相同，
> 结果必然退化为**与数据无关的常数**（实测：初值 `0xFFFF` 恒得 `0x0000`，
> 换初值 `0x0000` 恒得 `0x4FFE`）。本项目尾 CRC 改用 CCITT-FALSE（poly `0x1021`）打破恒等式，
> 两条 CRC 才互为独立证据。推导过程见 [`docs/11`](docs/11_W4缺陷分析与修复.md)。

### 4. 断电一致性：槽位状态机 + 写后回读校验

- **上电扫描定位写指针**：页级粗扫（只看每页第 1 条）+ 回退一页逐条精扫，兼顾速度与正确性
- **绝不重写同一槽位**：NOR Flash 位只能 1→0，重写一次得到的是 `旧值 & 新值`。
  任何写入失败都调用 `slot_abandon()` 把该槽位永久作废，从结构上消灭脏数据
- **擦除与检查的顺序**：跨入新扇区时**必须先擦除、再检查槽位**——
  顺序反了会让"槽位被占用"的判断挡住擦除本身，导致整扇区被逐条跳过
- **写后回读校验**：写完把该条读回来重算头尾 CRC。Flash 的页编程可能"假成功"
  （命令在器件忙时被静默忽略），返回值只能证明"命令发出去了"，证明不了"数据落进去了"

### 5. PC 端独立校验：为固件建立外部基准

固件是考生，PC 端是考官。`tools/` 下的 Python 工具用**独立实现**的算法复算固件输出：

| 工具 | 作用 |
|---|---|
| `golden_vectors.py` | **基准向量**：期望值取自固件（C 实现），是真正的外部基准 |
| `verify_bme280.py` | 用原始 ADC + 33 个校准系数独立复算温湿压，与固件逐位比对 |
| `parse_records.py` | 解析 `r` 命令倒出的记录流，逐条重算双 CRC 并分类统计 |
| `stack_budget.py` | 栈水位 → 重分配建议 → 压缩比计算 |
| `run.py` | 一体化菜单（校验 / 烧录 / 串口监视），无需手写命令 |

> **一条验证红线**：不能用被测代码自己造测试数据。
> 项目早期曾用 `make_sample_log.py`（调用被测的 `multibus.py`）生成"假日志"再回头验证它，
> 得到过"18 项 0 不一致"的**假 PASS**——同一条有 bug 的代码自己对自己必然自洽。
> 接上真板子后立刻暴露：湿度算成 3.04 %RH（固件真值 55.48 %RH）。
> 现在所有校验的期望值都来自固件或公认检查值。

## 实测验证

三个实验轮次，每轮都是完整的上板 → 抓取 → PC 端复算闭环：

| 实验轮次 | 时长 | 记录数 | 结果 |
|---|---|---|---|
| 首次上板（打通基本链路） | ~10 min | 1 246 | 1 243 完整 / 3 半写 ← 由此查出缺陷 ①②③ |
| 长跑（验证稳定性） | **11.65 h** | 41 266 | 采集节拍零漂移；暴露缺陷 ④ |
| 校验闭环专项（验证最终固件） | 30 min | **1 840** | **全部完整、零半写、零未收尾、序号连续** |

### 分项验证

| 项目 | 结果 |
|---|---|
| 时钟树 | 开机横幅 `#CLK,got:` 与 `#CLK,expect:` 四项完全相等（SYSCLK / HCLK / PCLK1 / PCLK2 = 72 / 72 / 36 / 72 MHz） |
| 串口 | `BRR = 625`（0x271）、误差 0%、DWT 可用 |
| BME280 | CHIP_ID = `0x60`；33 个校准系数全部落在手册典型区间。**关键是有符号数处理正确**：`P2=-10691`、`P6=-7`、`P8=-11800`——漏符号扩展会变成 54853 / 65529 / 53736，量级足以让气压补偿算出荒谬结果 |
| 温湿压复算 | PC 端独立复算 30 项与固件逐位一致 |
| SPI 四模式 | 回环自测四种模式全 `MATCH`（这是**预期**结果，见下）；`MISMATCH` 用例 `tx_mode=1 / rx_mode=0` 把 `0xA5` 读成 `0xD2`，移位演示成功 |
| W25Q64 分模式读 ID | Mode0/2/3 = `EF 40 17`（Winbond / SPI NOR / 8 MB）通过，Mode1 = `FF FF FF` 失败 |
| 记录闭环自检 | 256 槽跨越 1 个扇区边界 + 32 个页边界，`mismatch = 0` |
| 断电三情况自检 | `完整 / 未收尾 / 半写` 三种状态全部正确识别，`未收尾` 的尾 CRC 实测为 `0xFFFF` |
| 记录逐字节校验 | **1 840 条 × 32 B = 58 880 B，PC 端逐条重算头尾双 CRC 全部通过** |

> **关于"回环自测全 MATCH"**：单主机回环时收发用的是同一个模式，
> "什么时候把数据摆上线"和"什么时候去读线"是同一个人控制的，两者永远自洽——
> 所以四种模式都会读回原值。它证明的是**位引擎正确**（移位方向、边沿计数、MISO 通路），
> **不能**证明模式配对正确性。真正能证明配对的是**用真实从机分模式读 JEDEC ID**。

## 调试实录：5 个只有上板才会暴露的缺陷

这些缺陷都通过了编译与代码评审，只在真实硬件上跑起来才现形——也是本项目最有价值的部分。

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| ① | `uart_hold_us = 4235319666`（声称持锁 4235 秒） | `DWT->CYCCNT / 72` 的回绕周期是 **59.65 s**，不是 2³² µs。差值跨回绕后得到 ≈ 4.2×10⁹ 的假值，任何超时判定立刻成立 → **假超时** | 新增 `delay_elapsed_us()` 按真实周期处理；反推真实持锁仅 4.7 ms |
| ② | 1 246 条记录里 **1 245 条的尾 CRC 都是 `0x0000`** | 尾 CRC 从头 CRC 续算，触发 CRC 的**追加性质**；换初值后仍恒为 `0x4FFE`——推导确认这是 CRC 仿射性的**数学必然** | 尾 CRC 改用 **CCITT-FALSE** 多项式打破恒等式；新增"反退化"回归断言 |
| ③ | idx 980/981/982 三条半写，解析出的 seq 是 `1024 / 1024 / 1280` | 即 `0x400 & 0x401`、`0x500 & 0x501`——**同一槽位被写了两次**的铁证。① 的假超时 → 页编程判失败 → 写指针不推进 → 下一秒重写同一槽位 → 按位与 | 写前确认槽位为擦除态；任何失败都 `slot_abandon()` 永久跳过 |
| ④ | 11.65 h 长跑倒出 41 266 条，其中 **12 726 条是"半写"** | 擦除逻辑只擦"用到的扇区"（清空那一刻只擦了 3 个），4 MiB 里其余 1021 个扇区残留着**更早格式的数据**；且"先检查后擦除"的顺序让检查挡住了擦除本身 → 整扇区被逐条跳过 | `e` 改为擦除**整个记录区**（1024 扇区，实测约 26 s）；扇区擦除挪到占用检查**之前** |
| ⑤ | 1 h 运行出现 **9 条连续"未收尾"**，尾 CRC 全为 `0xFFFF`，而固件**没报任何错误** | Flash 页编程**静默失败**：第二步编程命令在器件仍忙时发出会被静默忽略，随后的状态轮询又恰好读到"空闲" | 新增**写后回读校验**：写完读回重算双 CRC，失败先重发一次，仍失败则作废该槽位 |

这些缺陷的共同点是**静默产生错误数据**。如果不对代码做"证据化"的设计
（回读校验、独立复算、时钟自证），它们会被当成"Flash 偶尔脏一下"糊过去。

## 已知局限与后续计划

诚实地列出还没做完的部分：

- **SPI Mode2 的异常**：W25Q64 手册标称支持 Mode0 / Mode3，实测 Mode2 也能读出正确的 JEDEC ID。
  怀疑与 bit-bang 实现的边沿顺序有关，**需逻辑分析仪抓波形才能定性**。
- **栈重分配尚未复测**：已测得各任务峰值并给出推荐尺寸（183 / 120 / 222 字），
  但"按推荐值编译后再跑一遍、确认剩余水位仍 > 0"这一步还没做。
- **未启用独立看门狗（IWDG）**：目前依靠各处的超时机制避免死锁，但缺少硬件级的最后一道保险。
- **记录区未跑满圈**：容量边界（131 072 条 = 36.4 小时）尚未测到。
- **无低功耗设计**：目前是常供电采集，未做 STOP / STANDBY 模式。
