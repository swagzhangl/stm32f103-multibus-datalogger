## 一、先说"为什么要配时钟树"（白话）

芯片里有两种时钟源：

- **HSI**：芯片内部自带的 RC 振荡器，8 MHz。**上电默认就用它**。缺点是精度差（±1% 左右），而且只有 8 MHz。
- **HSE**：板子上那颗金属壳的晶振，也是 8 MHz。精度高（±20 ppm 量级），但**上电时它是关着的**，要你去打开、等它起振。

STM32F103 内部还有一个**倍频器（PLL）**，可以把 8 MHz 乘 9 变成 **72 MHz**。

所以"配时钟树"这件事，白话就是：

> 把默认的 8 MHz 内部 RC 换掉，改成"打开外部晶振 → 倍频到 72 MHz → 再分配给各条总线"。

**为什么要费这个劲？** 三个现实理由：

1. **串口波特率算不准**。BRR 寄存器是按主频算出来的，主频不确定，波特率就不准。
2. **延时函数没法定标**。bit-bang I2C / SPI 全靠循环延时控制时序，主频是 8 MHz 还是 72 MHz，
   同样的循环差 9 倍速度 —— I2C 会直接超速到 900 kHz，超出器件上限。
3. **面试会问**。"你板子跑多少 MHz？怎么配的？"——答"用 CubeMX 点的"和
   答"FLASH 配 2 等待周期、HSE×9、APB1 分频 /2"是两个层次。

## 二、三个坑（先记住，能省一整天）

| # | 坑 | 后果 | 现象（为什么难查） |
|---|---|---|---|
| **1** | `FLASH->ACR` 忘了配 2 个等待周期 / 配晚了 | Flash 取指跟不上 72 MHz | **能下载、能跑几秒、然后不知跳到哪了**。看起来像"程序有 bug"，其实是取指出错 |
| **2** | APB1 分频忘了改成 /2 | APB1 被超频到 72 MHz（上限 36 MHz） | **外设时好时坏**。不是彻底不工作，所以很难怀疑到时钟上 |
| **3** | 切完 SYSCLK 没回读确认 | 后续所有按 72 MHz 算的数全错 | 串口乱码、延时失准。而"乱码"会让你先怀疑接线和波特率设置 |

**一句话记忆**：**等待周期要在提频之前配，APB1 必须 /2，切完要回读确认。**

## 三、逐行讲解 `clock_init_72mhz()`

代码在 `Core/Src/clock_init.c`。整个函数就六步，下面按步拆。

### 第 ① 步：Flash 等待周期 + 预取

```c
FLASH->ACR = FLASH_ACR_PRFTBE | FLASH_ACR_LATENCY_2;
while ((FLASH->ACR & FLASH_ACR_LATENCY) != FLASH_ACR_LATENCY_2) { }
```

- `FLASH_ACR_LATENCY_2`：**2 个等待周期**。按参考手册 RM0008 的表，
  `48 < SYSCLK ≤ 72 MHz` 时必须 2 个。
- `FLASH_ACR_PRFTBE`：打开**预取缓冲**。Flash 读到一条指令后，顺手把下一条也取回来放在缓冲区，
  这样 CPU 连续执行时就不用每次等 Flash。
- 后面那个 `while` 是**回读确认**：写寄存器不一定立刻生效，等它真的变过去再往下走。

> **为什么要放在第一位？** 因为"2 个等待周期"是针对 72 MHz 的要求。
> 如果你先提频、后配等待周期，那么在提频到配好之间的**那几十个时钟里，CPU 正在以 72 MHz 从 0 等待周期的 Flash 取指** ——
> 这几十个时钟足以让程序跑飞。所以顺序上必须"**先降低期望（配好等待周期），再提高频率**"。

### 第 ② 步：打开 HSE 并等它稳定

```c
RCC->CR |= RCC_CR_HSEON;
t = CLOCK_TIMEOUT;
while (((RCC->CR & RCC_CR_HSERDY) == 0U) && (t != 0U)) { t--; }
if (t == 0U) { return 1U; }
```

- 晶振起振**需要时间**（典型几毫秒），所以要轮询 `HSERDY` 位等它。
- `t` 是超时计数。**"永不无限阻塞"是嵌入式铁律**：万一晶振坏了/虚焊了，
  死等会让整个系统失联，你连"晶振没起振"这个信息都看不到。
  给个超时后返回错误码，`main()` 会把 `rc=1` 打到串口上 —— **问题可见**。

### 第 ③ 步：配 PLL（源 = HSE，倍频 ×9）

```c
RCC->CFGR &= ~(RCC_CFGR_PLLSRC | RCC_CFGR_PLLXTPRE | RCC_CFGR_PLLMULL);
RCC->CFGR |=  (RCC_CFGR_PLLSRC | RCC_CFGR_PLLMULL9);
RCC->CR   |=  RCC_CR_PLLON;
while (((RCC->CR & RCC_CR_PLLRDY) == 0U) && (t != 0U)) { t--; }
```

三个点：

1. **先清零再置位**。这三个位字段一起清零，避免上次运行/复位留下的值混进来。
2. `RCC_CFGR_PLLMULL9` 是**偏移编码**：寄存器的 4 位值 = "倍数 − 2"。
   所以 ×9 对应 `0111`（7）。`1111` 也是 ×16（和 `1110` 一样）。
   —— 这个"偏移编码"是面试常问的小陷阱。
3. PLL 锁定也要等 `PLLRDY`，同样带超时。

### 第 ④ 步：配总线分频（**必须在切 SYSCLK 之前**）

```c
RCC->CFGR &= ~(RCC_CFGR_HPRE | RCC_CFGR_PPRE1 | RCC_CFGR_PPRE2);
RCC->CFGR |=  RCC_CFGR_PPRE1_DIV2;
```

这是**坑 #2 的正解**。

复位后 `PPRE1` 的默认值是 `/1`。如果你直接切到 72 MHz，APB1 就变成 72 MHz —— **超出 36 MHz 上限一倍**。

| 总线 | 分频 | 频率 | 上限 | 挂什么 |
|---|---|---|---|---|
| AHB (HCLK) | /1 | 72 MHz | 72 MHz | 内核、DMA、SRAM |
| **APB1 (PCLK1)** | **/2** | **36 MHz** | **36 MHz** | TIM2-4、USART2/3、I2C1/2、SPI2 |
| APB2 (PCLK2) | /1 | 72 MHz | 72 MHz | GPIO、USART1、SPI1、ADC |

> **面试点**：为什么 APB1 上限是 36 MHz 而 APB2 是 72 MHz？
> —— 因为 APB1 上的外设（I2C、USART2/3 等）设计时就只保证跑到 36 MHz，
> APB2 上的外设设计余量更大。这是芯片设计上的取舍，不是随便定的。

### 第 ⑤ 步：切 SYSCLK 到 PLL，并**回读确认**

```c
RCC->CFGR &= ~RCC_CFGR_SW;
RCC->CFGR |=  RCC_CFGR_SW_PLL;
while (((RCC->CFGR & RCC_CFGR_SWS) != RCC_CFGR_SWS_PLL) && (t != 0U)) { t--; }
```

- `SW` 是"我要选谁"，`SWS` 是"我现在实际是谁"。**这是两个不同的位域**。
- 切换是**异步**的（时钟源本身在变），必须等 `SWS` 跟着变过去。
- 这是**坑 #3**。不等就往下跑 → 后面一切按 72 MHz 算，但实际可能还在 8 MHz 上。

### 第 ⑥ 步：告诉全世界"现在是 72 MHz 了"

```c
SystemCoreClock = BOARD_SYSCLK_HZ;
```

`SystemCoreClock` 被两处依赖：

1. `FreeRTOSConfig.h` 的 `configCPU_CLOCK_HZ` → 决定一个 tick 是多少毫秒。
   不更新 → **tick 长度错 9 倍**，`vTaskDelay(1000)` 变成 111 ms。
2. `delay_us()` 的 DWT 每微秒周期数标定。不更新 → 延时全错。

> 这个变量"忘了更新"是很典型的 silent bug：程序能跑，只是所有时间都错。
> 所以本工程在开机横幅里**同时打印"我以为的"和"从寄存器反算的"**，见下。

## 四、时钟自证：不要"以为"，要"读出来"

新手常见写法是配完就 `printf("72MHz")`。但那只是打印了一个宏，**证明不了任何事**。

本工程的做法（`clock_init.c` 的 `clock_get_sysclk_hz()` 等）：

```c
uint32_t clock_get_sysclk_hz(void)
{
    uint32_t sws = RCC->CFGR & RCC_CFGR_SWS;
    ...
    // 从 SWS 位 + PLLMULL 位 + PLLSRC 位 + PLLXTPRE 位现算
}
```

它是**从 RCC 寄存器反推频率**，而不是返回一个常量。开机横幅会并排打出两行：

```
#CLK,got:    SYSCLK=72000000 HCLK=72000000 PCLK1=36000000 PCLK2=72000000
#CLK,expect: SYSCLK=72000000 HCLK=72000000 PCLK1=36000000 PCLK2=72000000
#CLK,APB1上限=36000000 —— 上面 PCLK1 超过它就会外设时好时坏
```

两行一致 = 时钟树真的配对了。`PCLK1` 那行专门用来盯**坑 #2**。

## 五、USART1：BRR = 0x271 是怎么算出来的

这是 W1 最值得当场推导的一个数字。

**公式**（过采样 16 倍时）：

```
USARTDIV = f_CK / (16 × Baud)
BRR      = USARTDIV 的定点表示（高 12 位 = 整数部分，低 4 位 = 小数部分×16）
```

**代入** USART1 挂 APB2 = 72 MHz、目标 115200：

```
USARTDIV = 72 000 000 / (16 × 115200)
         = 72 000 000 / 1 843 200
         = 39.0625
```

- 整数部分 = **39** = `0x27`
- 小数部分 = 0.0625 → 0.0625 × 16 = **1** → 低 4 位 = `0x1`
- **BRR = 0x271**（= 39 × 16 + 1 = 625）

**反推验证实际波特率**：

```
实际波特率 = 72 000 000 / (16 × 39.0625) = 115 200     误差 0.00%
```

> **面试可以直接讲的一句**：
> "72e6 ÷ (16 × 115200) = 39.0625，尾数 39、小数正好 1，所以 BRR = 0x271，
> 实际波特率正好 115200，误差 0%。"

代码里这个值不是手写死的，而是 `board.h` 算出来的：

```c
#define BOARD_UART_BRR  ((BOARD_PCLK2_HZ + (BOARD_UART_BAUD / 2UL)) / BOARD_UART_BAUD)
```

**为什么写成算式而不是 `0x271`？** 因为 `BRR` 的数值恰好等于 `f_CK / Baud`（这是过采样 16 倍下的数学性质），
写成算式后，**哪天你改了主频或波特率，BRR 会自动跟着变** ——
就不会出"时钟提到 72 MHz 却忘了改 BRR，串口全是乱码"这种事。

### 引脚配置的两个细节

```c
// PA9 = 复用推挽输出 50MHz（AF push-pull）
GPIOA->CRH &= ~(0xFU << 4);
GPIOA->CRH |=  (0xBU << 4);

// PA10 = 上拉输入
GPIOA->CRH &= ~(0xFU << 8);
GPIOA->CRH |=  (0x8U << 8);
```

- **PA9 必须是"复用推挽"**，不能是"通用推挽"。
  通用推挽是让 CPU 直接控制电平；复用推挽是**把引脚交给外设**（这里是 USART），由外设波形去驱动。
  配错的表现是：**寄存器都对，但 TX 脚一动不动**。
- **PA10 用上拉而不是浮空**。串口线没插的时候，浮空输入会收到一堆噪声，
  软件上表现为"莫名其妙的乱码命令"。上拉把它钉在高电平。

### 控制寄存器一次配齐

```c
USART1->CR1 = USART_CR1_UE | USART_CR1_TE | USART_CR1_RE | USART_CR1_RXNEIE;
```

| 位 | 名字 | 作用 |
|---|---|---|
| 13 | `UE` | 串口总使能（**放最前面**） |
| 3 | `TE` | 发送使能 |
| 2 | `RE` | 接收使能（本版新增，为了 PC→板命令通道） |
| 5 | `RXNEIE` | 收到字节就中断 |

## 六、DWT 微秒延时：为什么不用空循环

老代码里是这么写的：

```c
static void i2c_delay(void) { for (volatile uint32_t i = 0; i < 5U; i++) { } }
// 注释：HSI 8MHz 主频下，一次空循环约 5~6 个周期 → 循环 5 次约 3~4us
```

**问题**：这个延时长度取决于**主频、优化等级、编译器版本**。主频从 8 MHz 提到 72 MHz，
同样的循环**快 9 倍**，I2C 跑到约 900 kHz —— 远超 BME280 的 400 kHz 上限。
而且现象是"**在 8 MHz 下好好的，一提频就不通**"，非常难查。

**本工程改用 DWT**（Data Watchpoint and Trace）的周期计数器 `DWT->CYCCNT`：

```c
void delay_init(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;   // 使能跟踪模块
    DWT->CYCCNT = 0U;
    DWT->CTRL  |= DWT_CTRL_CYCCNTENA_Msk;             // 开周期计数

    // 探测：计数器到底走不走
    probe = DWT->CYCCNT;
    for (i = 0; i < 200; i++) { }
    s_dwt_ok = (DWT->CYCCNT != probe) ? 1U : 0U;

    s_cycles_per_us = SystemCoreClock / 1000000UL;    // 72 MHz → 72
}

void delay_us(uint32_t us)
{
    uint32_t start = DWT->CYCCNT;
    uint32_t ticks = us * s_cycles_per_us;
    while ((DWT->CYCCNT - start) < ticks) { }
}
```

**DWT 的好处**：

| | 空循环 | DWT |
|---|---|---|
| 依赖主频吗 | 是（改主频要重标定） | 否（自动跟着 `SystemCoreClock` 走） |
| 会被优化器干掉吗 | 会（所以要加 `volatile`） | 不会（是硬件寄存器） |
| 精度 | 差（±50%） | 高（±几个周期） |
| 改 `-O` 等级要重调吗 | 要 | 不要 |

**两个容易写错的地方（都已在代码里注释）**：

1. **无符号减法跨回绕**。`DWT->CYCCNT` 是 32 位，72 MHz 下约 **59.6 秒**就溢出回绕一次。
   `(now - start) < ticks` 用无符号语义天然正确跨越回绕；
   写成 `now >= start + ticks` 就会在回绕那一刻卡死或提前退出。
2. **退化路径**。极少数兼容芯片里 `TRCENA` 位写不进去，`CYCCNT` 永远停在 0。
   所以 `delay_init()` 会**先探测再决定**：探测失败就退化到空循环延时，
   并把状态暴露给自检（开机横幅里的 `DWT=ok / FAIL`）。
   —— "问题可见"比"问题消失"重要。

`delay_now_us()` 是同一个计数器的另一个用法：**单调递增的微秒计数**，
给 W25Q64 驱动做**超时判定**用（见 `w25q64.c` 的 `wait_busy`）。

## 七、`system_stm32f1xx.c`：为什么自己写

ST 给的那份 `system_stm32f1xx.c` 里，`SystemInit()` 会去读一堆 HAL 的宏
（`HSE_VALUE`、PLL 参数…）。而本项目**决策 1 是不用 HAL**。
与其为了两个函数把 HAL 的头文件拖进来，不如自己写 —— 总共不到 40 行。

**关键约束**（写在文件注释里）：看启动文件的顺序

```
Reset_Handler:
    bl  SystemInit        ← 复位后第一个 C 函数
    拷贝 .data 段（初值从 Flash 搬到 RAM）
    清零 .bss 段
    bl  __libc_init_array
    bl  main
```

→ **`SystemInit()` 执行时 `.data` 段还没初始化，所以它绝对不能依赖任何"有初值的全局变量"**。
这是一个很容易踩的坑（比如在 `SystemInit` 里判断一个初始化为 1 的 flag）。

`SystemInit()` 只做三件不依赖全局变量的事：
1. 设 `SCB->VTOR = FLASH_BASE`（向量表位置，为将来加 IAP 铺路）
2. 开 Flash 预取（**不改等待周期** —— 此刻还在 8 MHz，等待周期由 `clock_init_72mhz()` 统一设）
3. 写 `RCC->CSR` 的 `RMVF` 位清复位标志（这样后面读 CSR 得到的是本次运行的复位原因）

## 八、验收怎么做

| 验收项 | 怎么测 | 判据 |
|---|---|---|
| 串口能打印 | 串口助手 115200 8N1 | 看到开机横幅 + 每秒一行的采集数据 |
| **真的在 72 MHz** | 看横幅 | `#CLK,got:` 和 `#CLK,expect:` 两行一致 |
| BRR 正确 | 看横幅 | `#UART,BRR=625 (expect 625 = 0x271, baud=115200 err=0%), DWT=ok` |
| **UART 波形** | 逻辑分析仪接 **PA9**，触发方式设"下降沿"（起始位） | 量**一个 bit 的宽度**，应 ≈ **8.68 µs**（= 1/115200） |
| LED 能闪 | 看板子 | 每 **10 秒**翻转一次（不是 1 秒，别以为坏了） |

### 用逻辑分析仪量 UART 的窍门

1. 抓一帧：起始位（低）+ 8 个数据位 + 停止位（高）= **10 bit**（8N1，无校验）。
2. **发 `0x55` 或 `0xAA` 最容易量** —— 位图是 0101…，边沿多，一眼能数出 bit 边界。
   本工程开机横幅里正好有大量 `0`/`1` 字符（ASCII 0x30/0x31），也好数。
3. 判据：**一个 bit 宽 8.68 µs**，一帧 10 bit = 86.8 µs。
   如果量出来是 78 µs（= 1/8MHz×10）左右，说明**时钟没提上去**，BRR 是按 72 MHz 算的 —— 典型的坑 #1/#3。

### 一个必须能答的问题

> **"为什么 1 bit 是 8.68 µs？"**

因为串口异步通信每 bit 占一个固定时间：
`1 / 115200 s = 8.6806 µs`。
所谓"波特率 115200"就是"每秒 115200 个 bit"。
（注意不是"每秒 115200 字节" —— 一个字节要 10 个 bit。）
