## 一、I2C 的物理基础：为什么必须开漏

### 白话版

I2C 总线上挂着**一个主机和若干个从机**，它们共用两根线。问题是：
如果两台设备同时想说话，一台想输出高、一台想输出低，会怎样？

**推挽输出**的答案是：**两个管子直接对打，形成短路** —— 轻则通信失败，重则长期发热烧引脚。

**开漏输出**的答案是：**大家只能"拉低"，不能"输出高"**。
高电平由一根上拉电阻提供（谁都不拉时，被电阻拉上去）。

这就叫**"线与"**（wired-AND）：

```
                 +3.3V
                   │
              R    R        ← 上拉电阻（模块自带，或外接 4.7k）
                   │
   SDA ──┬──────────┴─────── ... 挂到所有设备
         │
       ┌─┴─┐    ┌─┴─┐
       │设备A│    │设备B│       每台设备的引脚内部只有一个 MOS 管到 GND
       └───┘    └───┘        "拉低"或"松开"，没有"输出高"这个动作
```

**结论：任何时候只要有一个人拉低，整条线就是低。所有人都不拉，才是高。**

### 代码上的体现（关键技巧）

常规写法是"发的时候把引脚配成输出、收的时候配成输入"，每次都要改 CRL 寄存器。
本工程用的是更优雅的做法 —— **全程保持开漏输出模式，用 ODR 位控制**：

```c
// 拉低：ODR 写 0
static void sda_low(void)  { GPIOB->BRR  = SDA_BIT; i2c_delay(); }
// 松开：ODR 写 1（引脚进入高阻，交给从机/上拉）
static void sda_high(void) { GPIOB->BSRR = SDA_BIT; i2c_delay(); }

// 读"真实电平"要去 IDR 读：
// 即使 ODR 写了 1，只要从机在拉低，IDR 读回来仍然是 0
static uint8_t sda_read(void) { return ((GPIOB->IDR & SDA_BIT) != 0U) ? 1U : 0U; }
```

**一句话记住**：`ODR` 是"我想干什么"，`IDR` 是"线上实际是什么"。
开漏模式下这两个**必须分开看** —— 这也是为什么"读 ACK"要读 IDR 而不是 ODR。

### 引脚配置

```c
// PB6(SCL) / PB7(SDA) → 开漏输出 2MHz
// CRL 里 PB6 是第 6 个四位组（位 [27:24]），PB7 是第 7 个（位 [31:28]）
// 开漏 → CNF=01、MODE=10 → 0b0110 = 0x6
GPIOB->CRL &= ~(0xFFU << 24);
GPIOB->CRL |=  (0x66U << 24);
```

> **为什么用 2 MHz 而不是 50 MHz？** `MODE` 位在 F1 上控制的是**输出驱动能力/翻转速率**。
> 2 MHz 的边沿更缓、振铃更小，对 I2C 这种低速总线更友好。50 MHz 只会徒增 EMI。
> （注意：上升沿的时间常数由**上拉电阻 × 总线电容**决定，跟这个设置无关。）

## 二、I2C 的四个"暗号"

I2C 只有两根线，却要表达"开始""结束""发数据""收数据""应答"五件事。
它的办法是：**约定"在 SCL 高电平期间翻转 SDA"是非法动作，然后把非法动作用作控制信号。**

```
        ┌─────────────────────────────────────────────┐
        │  正常传数据：SCL 为【低】时才允许翻 SDA      │
        │  特例（控制信号）：SCL 为【高】时翻 SDA      │
        └─────────────────────────────────────────────┘
```

### START（起始条件）

```
SDA ────┐
        └────────          ← SCL 高时，SDA 由【高变低】
SCL ────────┐
            └──────
            ↑
          这里是 START
```

```c
static void i2c_start(void)
{
    sda_high();   // 先确保 SDA 释放为高（否则 START 无法成立）
    scl_high();   // SCL 拉高
    sda_low();    // ★ SCL 高时拉低 SDA = START
    scl_low();    // 拉低 SCL，准备发第一位
}
```

### STOP（停止条件）

```
SDA ┌────────
    ┘                  ← SCL 高时，SDA 由【低变高】
SCL ────────┐
            └──────
            ↑
          这里是 STOP
```

### Repeated Start（重复起始）

**"发出 START 但不发 STOP"** —— 直接用第二个 START 接着谈下一轮。

**为什么需要它？** 看读寄存器的流程：

```
① START + 地址+W  →  ② 发寄存器号  →  ③ START + 地址+R  →  ④ 读数据  →  ⑤ STOP
                                       ↑
                                  这里叫 Repeated Start
```

如果②和③之间插了 STOP，总线会短暂变成"空闲"，**别的主机可能趁机抢走总线**。
那样"写寄存器号"和"读数据"两段就落在两个不同的事务里，从机的状态机被打断，读到的东西不可信。

```c
i2c_start();                                   // 阶段 1
i2c_write_byte((addr7 << 1) | 0);              // 写方向
i2c_write_byte(reg);                           // 阶段 2
i2c_start();                                   // 阶段 3：Repeated START
i2c_write_byte((addr7 << 1) | 1);              // 读方向
for (i = 0; i < len; i++)                      // 阶段 4
    buf[i] = i2c_read_byte((i == len-1) ? 1 : 0);
i2c_stop();                                    // 阶段 5
```

### ACK / NACK（应答）

每发完 **1 个字节（8 位）**，第 9 个时钟周期留给接收方"表态"：

```
主机发出的 8 位     ┌──────────────────────────┐
                    │ D7 D6 D5 D4 D3 D2 D1 D0  │
                    └──────────────────────────┘
                                              第 9 个时钟
                    ┌──────────────────────────┐
接收方拉低 SDA ─────┤ 0 = ACK（我收到了）       │
接收方不拉   ───────┤ 1 = NACK（没人应 / 不要了）│
                    └──────────────────────────┘
```

**关键细节**：主机读 ACK 之前**必须先松开 SDA**（写 1），否则主机会把线拉着，
从机想拉低也拉不动，永远读不到 ACK。代码里这一句就是：

```c
sda_high();     /* 主机松手，让从机拉低表示应答 */
scl_high();     /* 第 9 个时钟上升沿 */
nack = sda_read();
scl_low();
```

**读数据时的 ACK 方向是反的**：主机收完一个字节要**回**一个 ACK 给从机，
表示"我还要下一个"。最后一个字节回 **NACK**，表示"够了，别发了"。

```c
static uint8_t i2c_read_byte(uint8_t ack)
{
    ...
    if (ack != 0U) { sda_high(); }    // 最后一个字节：NACK，告诉从机"够了"
    else           { sda_low();  }    // 还要继续收：ACK，让从机继续发
    ...
}
```

### 总线复位（一个很实用的兜底）

如果主机在从机正在发某一位时被复位/打断，从机会一直拉着 SDA 等下一个时钟 ——
从从机的视角看，它"卡在事务中间"了。此时主机再发 START 也没用
（START 要求 SDA 从高变低，而 SDA 一直是低），表现就是
**"程序看着没错，就是一条都不通"**。

救法：发最多 9 个 SCL 脉冲，把从机剩下的位全"顶"出来，它自然会松手，然后补一个 STOP。

```c
uint8_t i2c_soft_bus_recover(void);   // 见 i2c_soft.c，已带调用次数统计
```

> 这是一个**很加分的细节**：说明你考虑过"异常恢复"，而不只是"正常流程能跑"。

## 三、延时怎么定标（本版最重要的改动）

老代码用空循环，注释写着"HSI 8 MHz 下约 3~4 µs"。
**主频提到 72 MHz 后同样的循环快 9 倍**，I2C 会跑到约 900 kHz，超 BME280 的 400 kHz 上限。

本版改成基于 DWT 的可配置微秒延时（见 `01_W1` 的第六节）：

```c
#define I2C_DELAY_US_DEFAULT   4U        // 100 kHz → 半周期 5 µs，取 4 µs 留余量
static uint8_t s_delay_us = I2C_DELAY_US_DEFAULT;
static void i2c_delay(void) { delay_us(s_delay_us); }

void i2c_soft_set_delay_us(uint8_t us);  // 可在运行时降速，排查用
```

**为什么留了运行时降速接口？** 因为 I2C 不通时的第一件事就是降速：

```
排查顺序（按这个来，别乱试）：
  ① 降速：400k → 100k → 50k → 20k
  ② 万用表测 SDA/SCL 空闲时是否为高
       不是高 → 上拉没接（或引脚模式配错，没配成开漏）
  ③ 逻辑分析仪看 START 条件有没有出来
       没有 → 引脚配置/时钟问题
       有但立刻 NACK → 器件地址错了
  ④ 确认模块上的 SDO 接的是 GND(0x76) 还是 VCC(0x77)
```

## 四、BME280 驱动

### 4.1 为什么必须读 33 个校准系数

BME280 内部是**压阻式/电容式传感器 + ADC**。它输出的是**原始 ADC 值**（20 位），
而这个值随**每一颗芯片的工艺偏差**不同 —— 同一批芯片，同样的气压，ADC 值能差几个百分点。

所以芯片出厂时会做一次标定，把补偿参数（**33 个系数**）**烧在 NVM 里**。
你必须：
1. 把这 33 个系数读出来
2. 代入 Bosch 官方补偿公式
3. 才能算出真实的温湿压

> **不读校准系数的后果**：能得到"原始值"，但换一颗芯片数值就全变了，没有可比性。

### 4.2 33 个系数藏在哪（分段读取）

| 段 | 地址范围 | 字节数 | 内容 |
|---|---|---|---|
| 第 1 段 | `0x88 – 0xA1` | 26 | `dig_T1..T3`（6 B）+ `dig_P1..P9`（18 B）+ `0xA0` 保留（1 B）+ `dig_H1`（1 B） |
| 第 2 段 | `0xE1 – 0xE7` | 7 | `dig_H2`（2 B）+ `dig_H3`（1 B）+ `dig_H4/H5`（3 B）+ `dig_H6`（1 B） |

**注意 `0xA0` 是保留字节，要跳过**；`dig_H1` 是**单字节**，在 `0xA1`：

```c
dig_T1 = (uint16_t)(((uint16_t)b[1] << 8) | b[0]);   // 无符号，小端
dig_T2 = (int16_t)(((uint16_t)b[3] << 8) | b[2]);    // 有符号！
...
dig_H1 = b[25];                                       // b[24] 跳过了
```

> **符号！符号！符号！** `dig_T1 / dig_P1 / dig_H1 / dig_H3` 是**无符号**，
> 其余大多是**有符号**。搞错了会出现"温度对了气压差一半"这种诡异现象。

### 4.3 最容易写错的地方：`dig_H4` / `dig_H5` 跨字节瓜分

这两个是 **12 位**值，被拆成"高 8 位 + 低 4 位"存，而且 **`0xE5` 这一个字节被 H4 和 H5 瓜分了**：

```
   0xE4      0xE5                0xE6      0xE7
┌────────┬────────────┬────────┬────────┬────────┐
│ H4[11:4]│H5[3:0]│H4[3:0]│ H5[11:4]│  H6   │
└────────┴────────────┴────────┴────────┴────────┘
     ↑          ↑    ↑        ↑
   H4 高 8 位  H5 低 4 位  H4 低 4 位  H5 高 8 位
```

```c
/* ★ 照抄 Bosch 官方写法，不要自己"简化" */
dig_H4 = (int16_t)((int16_t)((int16_t)e[3] << 4) | (e[4] & 0x0FU));  // 0xE4 全部 + 0xE5 低 4 位
dig_H5 = (int16_t)((int16_t)((int16_t)e[5] << 4) | (e[4] >> 4));     // 0xE6 全部 + 0xE5 高 4 位
```

> **面试点**：这是 BME280 驱动里最经典的一个坑。能说出"`0xE5` 被两个系数瓜分"
> 说明你**真的读过数据手册**，不是抄的代码。

### 4.4 配置顺序：`0xF2` 必须在 `0xF4` 之前

```c
/* 顺序不能换！数据手册明确规定 */
v = 0x01; i2c_write_reg(BME280_ADDR, 0xF2, &v, 1);   // ① ctrl_hum（湿度过采样）
v = 0xA8; i2c_write_reg(BME280_ADDR, 0xF5, &v, 1);   // ② config（待机 + IIR 滤波）
v = 0x57; i2c_write_reg(BME280_ADDR, 0xF4, &v, 1);   // ③ ctrl_meas（温压过采样 + 模式）
```

**为什么？** 因为 `ctrl_hum` 只有在**写 `ctrl_meas` 时才被"锁存"进生效寄存器**。
如果先写 `0xF4` 再写 `0xF2`，湿度配置根本不会生效 ——
而且它不会报错，只是湿度读数一直是默认值。**又一个"静默失效"**。

本工程的配置值：

| 寄存器 | 值 | 含义 |
|---|---|---|
| `0xF2` ctrl_hum | `0x01` | 湿度过采样 ×1 |
| `0xF5` config | `0xA8` | 待机 1000 ms + IIR 滤波 ×4 |
| `0xF4` ctrl_meas | `0x57` | 温度 ×2 / 气压 ×16 / Normal 连续模式 |

> 气压过采样给到 ×16 是因为**气压对噪声最敏感**，需要更多平均。

### 4.5 为什么必须一次连读 8 字节

数据区 `0xF7 – 0xFE` 依次是：气压 3 B + 温度 3 B + 湿度 2 B。

**必须一次读完**。分三次读可能跨两次转换，导致"气压是上一秒的、温度是这一秒的"——
三个量不是同一批测量。数据手册明确要求"同一批测量必须整段读出"。

```c
if (i2c_read_reg(BME280_ADDR, 0xF7, d, 8U) != 0U) { return 1U; }

/* 20 位数据分 3 字节：MSB(8) + LSB(8) + XLSB 高 4 位 */
*adc_P = (int32_t)(((uint32_t)d[0] << 12) | ((uint32_t)d[1] << 4) | ((uint32_t)d[2] >> 4));
*adc_T = (int32_t)(((uint32_t)d[3] << 12) | ((uint32_t)d[4] << 4) | ((uint32_t)d[5] >> 4));
/* 湿度只有 16 位 */
*adc_H = (int32_t)(((uint32_t)d[6] << 8) | (uint32_t)d[7]);
```

**为什么是 `>> 4` 而不是 `& 0x0F` 之类？** 因为 XLSB 字节的高 4 位才是数据的高 4 位，
低 4 位是无效的，所以整体右移 4 位把无效位丢掉。

### 4.6 气压补偿必须用 64 位

Bosch 提供了两版补偿算法：

| | 中间量类型 | 精度 | 本项目实测 |
|---|---|---|---|
| 32 位版 | `int32_t` | 低 | ❌ 输出 1164 hPa，真值 1011 hPa，**偏 +15%** |
| **64 位版** | **`int64_t`** | 高 | ✅ 正确 |

**根因**在这一行：

```c
p = (((p << 31) - var2) * 3125) / var1;      // ★ 必须 64 位
```

`p << 31` 在 `int32` 下**直接溢出成负数**，结果完全不可信。
64 位版中间量最长到 2^47 量级，必须用 `int64_t`。

> **这条很适合写进论文/面试**：
> "Bosch 官方给了 32 位和 64 位两版气压补偿，我一开始用了 32 位版，
> 发现气压偏高 15%，定位到是 `p << 31` 在 32 位下溢出，换成 64 位版就正确了。"
> —— 这是一个**真实调过的 bug**，比背公式有说服力得多。

### 4.7 温湿压必须"一起算"：`t_fine` 是共享的

```
   温度 ADC ─→ compensate_temperature() ─→ t_fine ─┬─→ compensate_pressure()
                                                   └─→ compensate_humidity()
```

`t_fine` 是温度补偿的中间量，**气压和湿度的公式都要用它**。
所以顺序是固定的，不能反：

```c
T = compensate_temperature(adc_T);        // 先算温度，得到 t_fine
out->temperature = T;
s_raw.comp_press_q24_8 = compensate_pressure(adc_P);   // 再用 t_fine
s_raw.comp_hum_q22_10  = compensate_humidity(adc_H);
```

三种输出的定点格式（很重要，PC 端复算要对齐）：

| 量 | 函数返回 | 换算 | 我们转成 |
|---|---|---|---|
| 温度 | `int32`，单位 0.01 ℃ | 直接用 | 0.01 ℃ |
| 气压 | `uint32`，**Q24.8** | `>> 8` 得 Pa | **Pa** |
| 湿度 | `uint32`，**Q22.10** | `/1024` 得 %RH | 乘 100 再 `>> 10` 得 0.01 %RH |

## 五、那个"确定性数据污染"，和本版的两道防线

### 问题现象（原代码注释里记录的真实事件）

> 连续运行 **8.35 小时 / 30062 条**记录中，有 **2 条**出现温度 +15.6 ℃、气压 +25.2 hPa 的孤立尖峰，
> 下一条立刻恢复。两次偏移量**几乎完全相同**（+15.62/+15.61 ℃，+25.20/+25.20 hPa）。

**为什么能断定不是噪声**：随机噪声**不可能**重复出同一幅度。
用实测校准系数反推，单一 `t_fine` 偏移 Δtf≈79975 **恰好同时**产生
+15.62 ℃ 与 +25.21 hPa，与观测量吻合 → **温度 ADC 被污染，气压因依赖 `t_fine` 被同步带偏**。

### 为什么 CRC 抓不到它（关键认知）

```
   ┌── 传感器 ──┐   ┌── 打包 ──┐   ┌── Flash ──┐   ┌── UART ──┐   ┌── PC ──┐
   │  读 ADC   │──→│ 加 CRC   │──→│  存储      │──→│  传输    │──→│  校验  │
   └───────────┘   └──────────┘   └───────────┘   └──────────┘   └────────┘
        ▲                                                              ▲
        │                                                              │
   CRC 保护范围从这里开始 ──────────────────────────────────────────────┘

   CRC 只能证明"存进去的字节 = 读回来的字节"
   它【不能】证明"从传感器读到的字节是对的"
   —— 这是两个完全不同的断言
```

所以在驱动层必须再加一道**物理量闸门**。

### 防线一（事后拦截）：物理量合理性校验

```c
#define VALID_T_ABS_MIN   (-4000)   /* -40.00 ℃，芯片规格下限 */
#define VALID_T_ABS_MAX   ( 8500)   /* +85.00 ℃，芯片规格上限 */
#define VALID_T_MAX_STEP  (  200)   /* 1 Hz 下相邻两次最大允许变化 2.00 ℃ */

static uint8_t temp_is_plausible(int32_t t)
{
    if ((t < VALID_T_ABS_MIN) || (t > VALID_T_ABS_MAX)) { return 0U; }
    if (s_have_last != 0U) {
        int32_t diff = t - s_last_temp;
        if (diff < 0) { diff = -diff; }
        if (diff > VALID_T_MAX_STEP) { return 0U; }   // ← 那条 +15.6℃ 会被这条拦下
    }
    return 1U;
}
```

**判据的第二条为什么是 2.00 ℃？** 因为 BME280 的**热惯性很大**，
1 秒间隔内真实温度不可能跳 2 ℃。所以"相邻跳 2 ℃ 以上"等价于"读错了"。

不可信就**立刻重读一次**（相隔不到 1 ms，落在同一次转换结果内，不引入新误差）；
两次都不可信 → 返回错误码，**上层直接跳过，绝不写进 Flash**。

### 防线二（事前避免）：读之前先看 `measuring` 位

**根因**：本芯片配的是 Normal 连续模式（待机 1 s），而本机也恰好 1 s 轮询一次。
两颗时钟**各自独立**，8 字节突发读（100 kHz 下约 0.7 ms）有可能
**跨过从机内部的寄存器更新时刻**，读到"半新半旧"的一组数据。
（数据手册明确写有"数据寄存器不是同时更新的"。）

**本版的修法**（比改用 Forced 模式改动小得多，效果等价）：

```c
static uint8_t wait_not_measuring(void)
{
    uint8_t st;
    for (uint8_t tries = 0U; tries < 30U; tries++) {
        if (i2c_read_reg(BME280_ADDR, 0xF3, &st, 1U) != 0U) { return 1U; }
        if ((st & 0x08U) == 0U) { return 0U; }   // measuring = 0 → 数据稳定，可以读
        delay_us(2000U);
    }
    return 2U;
}
```

**为什么这样就够**：转换只占 1000 ms 周期里的约 46 ms。
所以"看到 `measuring = 0`"就说明接下来的 0.7 ms 突发读
**必然落在不会被改写的窗口里**。

**代价**：一次单字节 I2C 读（约 90 µs）。
**收益**：从"事后拦截"变成"事前避免"，那条数据不再丢。

> 原来的物理量闸门**保留**，退化成第二道防线 —— **纵深防御：能预判就预判，预判不到还有兜底**。

## 六、"PC 端复算逐位一致"怎么证明

简历上写"温湿压结果经 PC 端复算逐位一致"。这句话要成立，PC 端必须**独立**算一遍。

**关键是"只用输入"**：PC 端只使用 `#CALIB`（33 个校准系数）+ `#RAW`（3 个 ADC 原始值），
**不复用固件的任何中间结果**，然后和 `#CMP` / `#OUT` 比对。

```bash
# 1) 抓日志：先发 c 拿校准系数，再发若干次 m 触发测量
python tools/serial_capture.py --port COM5 --out log.txt --seq c,m,m,m --gap 2

# 2) PC 独立复算并比对
python tools/verify_bme280.py log.txt
```

**PC 端实现里有一个必须注意的坑**：

```python
# C 的整数除法是"向零截断"，Python 的 // 是"向下取整"
#   C:      -7 / 2  = -3
#   Python: -7 // 2 = -4
# 气压补偿里 (p << 31) - var2 完全可能是负数，所以必须显式实现向零截断除法
def c_div(a, b):
    q = abs(a) // abs(b)
    return q if (a >= 0) == (b >= 0) else -q
```

> 如果不处理这个，PC 端算出来会**差 1**，而且看起来像随机误差 —— 最难查。
> `multibus.py` 里已经按 C 语义实现了。

## 七、验收与排查

### 验收清单

| 项 | 怎么测 | 判据 |
|---|---|---|
| I2C 通了 | 命令 `i` | `#CHIPID,0x60,BME280(有湿度)` |
| 校准系数读到 | 命令 `c` | `#CALIB,...` 里 `count=33`，且 18 个值都**不是 0** |
| 波形完整 | 逻辑分析仪接 PB6/PB7 | 能看到 START → 地址 → ACK → 寄存器 → Repeated START → 读 → NACK → STOP |
| 读数合理 | 看每秒的数据行 | 温度接近室温、湿度 30~70%、气压 99000~103000 Pa |
| **PC 复算一致** | `python tools/verify_bme280.py log.txt` | `结论：PASS` |

### I2C 读不到数据的排查顺序（**按这个来，别乱试**）

```
① 降速：400k → 100k → 50k → 20k        ← 先用 i2c_soft_set_delay_us()
② 万用表测 SDA/SCL 空闲时是否为高       ← 不是高 = 上拉没接，或引脚没配成开漏
③ 逻辑分析仪看 START 有没有出来          ← 没有 = 引脚/时钟问题；有但立刻 NACK = 地址错
④ 确认 SDO 接的是 GND(0x76) 还是 VCC(0x77)
⑤ 换一根杜邦线                        ← 真的，线坏是常见原因
```
