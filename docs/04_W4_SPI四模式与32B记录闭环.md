## 一、SPI 与 I2C 的根本区别（先建立对照）

| | I2C | SPI |
|---|---|---|
| 线数 | **2 根**（SCL/SDA，双向复用） | **4 根**（CS/SCK/MOSI/MISO，各管一件事） |
| 从机寻址 | 有**地址**（7 位） | **没有地址** —— CS 拉低就是"我找你" |
| 应答机制 | **有 ACK/NACK** | **没有** |
| 速度 | 100 k / 400 k / 1 M | 几 MHz ~ 几十 MHz（W25Q64 支持到 80 MHz） |
| 多从机 | 挂同一对线，靠地址区分 | 每个从机一根独立 CS |
| 主机能否知道从机收到了 | **能**（看 ACK） | **不能** —— 这是 SPI 最大的特点 |

### 最后一行是重点

**SPI 没有 ACK，主机发完不知道从机收没收到。**

那怎么验证通不通？唯一办法是：**读一个从机出厂就固定好的值**。
对 W25Q64 来说就是 **JEDEC ID**（命令 `0x9F` → 应返回 `EF 40 17`）。

```
EF = 厂商 Winbond
40 = 存储类型（SPI NOR）
17 = 容量代码，2^23 = 8 MB = 64 Mbit
```

**⇒ 所以每次 bring-up 都先干这件事，而不是急着写数据。**
ID 读对了 = 接线通 + 时钟正常 + 模式（CPOL/CPHA）正确 + 供电正常，四件事一次全验完。

## 二、四种 SPI 模式（简历原话："四种 SPI 模式"）

### 本质只有两个参数

| 参数 | 决定什么 |
|---|---|
| **CPOL** | SCLK **空闲时**是高还是低 |
| **CPHA** | 在**第几个边沿**采样 |

每个时钟周期有**两个边沿**：

```
       ┌──── 前沿 ────┐     ┌──── 后沿 ────┐
       │（离开空闲态） │     │（回到空闲态） │

CPOL=0（空闲低）：
SCLK  ___┌────────┐________┌────────┐___
         ↑        ↓        ↑        ↓
       前沿     后沿      前沿     后沿
      (上升)   (下降)    (上升)   (下降)

CPOL=1（空闲高）：
SCLK  ‾‾‾┐________┌────────┐________┌‾‾‾
         ↑        ↓        ↑        ↓
       前沿     后沿      前沿     后沿
      (下降)   (上升)    (下降)   (上升)
```

### 四种模式全表

| 模式 | CPOL | CPHA | SCLK 空闲 | 采样沿 | 数据改变沿 | 常见用途 |
|---|---|---|---|---|---|---|
| **Mode 0** | 0 | 0 | **低** | **上升沿**（前沿） | 前沿之前就摆好 | **W25Q64 用它**；最常用 |
| Mode 1 | 0 | 1 | 低 | 下降沿（后沿） | 前沿之时 | 较少 |
| Mode 2 | 1 | 0 | **高** | 下降沿（前沿） | 前沿之前就摆好 | 较少 |
| **Mode 3** | 1 | 1 | 高 | **上升沿**（后沿） | 前沿之时 | **W25Q64 也支持** |

**一句话记忆**：

> **CPOL 管"闲着的时候是高是低"，CPHA 管"在头一个边沿还是第二个边沿取数"。**
>
> 更实用的记法：**CPHA=0 → 前沿采样**（所以数据必须在**前沿之前**就摆好）；
> **CPHA=1 → 后沿采样**（所以数据在**前沿之时**才改变）。

### `spi_soft.c` 是怎么覆盖四种模式的

bit-bang 的好处正在这里：时钟和数据都是你用 GPIO 一个边沿一个边沿翻出来的，
所以"四种模式"在代码里只差两件事：**先翻谁、在哪个边沿读**。

```c
/* 把"前沿/后沿"抽象成两个函数，模式就只剩下参数差别 */
static void sck_edge_idle_to_active(uint8_t cpol);   // 前沿
static void sck_edge_active_to_idle(uint8_t cpol);   // 后沿

uint8_t spi_soft_transfer_ex(uint8_t tx, uint8_t tx_mode, uint8_t rx_mode)
{
    ...
    for (i = 7; i >= 0; i--) {
        uint8_t bit = (tx >> i) & 1U;

        if (tcpha == 0U) { mosi_set(bit); }    // CPHA=0：前沿之前摆好数据
        sck_edge_idle_to_active(tcpol);        // ---- 前沿 ----
        if (sample_at_edge1) { rx = (rx<<1) | miso_get(); }
        if (tcpha == 1U) { mosi_set(bit); }    // CPHA=1：前沿之时改变数据
        sck_edge_active_to_idle(tcpol);        // ---- 后沿 ----
        if (!sample_at_edge1) { rx = (rx<<1) | miso_get(); }
    }
}
```

> **用硬件 SPI 的话**，对应的就是 `SPI_CR1` 寄存器的 `CPOL`（bit1）和 `CPHA`（bit0）。
> 能说出这句，就说明你不是只会调库。

### 切换模式后必须立刻摆正 SCLK 空闲电平

```c
void spi_soft_set_mode(uint8_t mode)
{
    s_cpol = (mode >> 1) & 1U;
    s_cpha = mode & 1U;
    sck_set_idle(s_cpol);   // ★ 否则 SCLK 停在旧电平，
                            //   从机看到的第一个边沿方向就是错的
}
```

## 三、⚠️ 重要修正：计划书里的"回环自测能看到 CPHA 配错"，**这个说法不成立**

### 计划书原文（第 3.2 节，第 2 步）

> 回环自测：用一根杜邦线把 MOSI 与 MISO 短接，四种模式各发同一个字节。
> 模式配对正确 → 收到原值；**CPHA 配错 → 收到移位一拍的错值**（如 0xA5 → 0x4B / 0x52）

### 为什么它不成立

**单主机回环时，收发用的是同一个模式。**
"什么时候把数据摆上线"和"什么时候去读线"是**同一个人**控制的，两者永远自洽。

推一遍就知道：

| 模式 | 循环体做的事 | 采样瞬间线上是什么 |
|---|---|---|
| CPHA=0 | ① 摆 MOSI ② 前沿 ③ **采样** ④ 后沿 | 刚摆好的那一位 ✓ |
| CPHA=1 | ① 前沿 ② 摆 MOSI ③ 后沿 ④ **采样** | 刚摆好的那一位 ✓ |

**⇒ 四种模式都会读回 0xA5。根本看不到"移位半拍"。**

### 那"配错会移位"这句话是错的吗？

**不是错的，只是"回环"测不出来。** 移位发生在**两个设备用了不同模式**时：

```
发送方按 CPHA=1（前沿才换数据）
接收方按 CPHA=0（前沿就采样）
                    ↓
接收方的采样点正好压在数据跳变的那一刻
→ 建立时间不满足 → 读到的是【相邻位】 → 整体错位半拍
```

### 本工程的三层处理（已实现）

| # | 测试 | 能证明什么 | ❌ 不能证明什么 |
|---|---|---|---|
| **1** | **杜邦线回环**（MOSI↔MISO 短接），四种模式各发 `0xA5` | **位引擎正确**：移位方向、边沿计数、MISO 通路都对 | ❌ 模式配对正确性 |
| **2** | **`spi_soft_transfer_ex(tx, tx_mode, rx_mode)`** —— 发送侧与接收侧用**不同**模式 | ✅ 真的能看到移位（这是"主从模式不匹配"的软件等价演示） | — |
| **3** | **W25Q64 分模式读 JEDEC ID** | ✅ **模式配对正确性**（物理证据） | — |
| **4** | **逻辑分析仪看波形** | ✅ CPOL（空闲电平）、CPHA（数据稳定沿） | — |

**代码里的说明文本（不会让人误判）**：

```
#SPI4,注意: 四种模式回环【全部 MATCH】才是预期结果。
#SPI4,     因为回环时收发用同一个模式，两者永远自洽 ——
#SPI4,     它只能证明「位引擎正确」（移位方向、MISO 通路、边沿计数），
#SPI4,     证明不了「模式配对对不对」。
```

> **这件事本身就是一个很好的面试素材**：
> "我一开始按文档说的做回环自测，结果四种模式全都读回原值，我以为是测试写错了。
> 后来想明白了原因 —— 回环时收发是同一个模式，自洽是必然的。
> 所以我又补了两项：用不同模式收发来演示移位，以及用 W25Q64 分模式读 ID 作物理证据。"
>
> **能把"我发现的文档错误"讲清楚，比背下四种模式更有说服力。**

### "为什么 W25Q64 用 Mode 0"（必答）

> 数据手册标注 W25Q64 **支持 Mode 0 与 Mode 3**。
> 选 Mode 0 的理由是：**Mode 0 下 SCLK 空闲为低，与上电后的默认电平一致**，
> 不会在片选拉低的那一瞬间产生一个多余的时钟边沿去误触发从机。
>
> 而且 —— **模式由从机决定，主机必须跟随**。

## 四、W25Q64：两条铁律（**必问**）

### 铁律 ①：位只能 1→0，写之前必须先擦

NOR Flash 的编程是"**按位与**"：只能把 1 变成 0，**不能把 0 变回 1**。

```
   擦除后的状态：  1 1 1 1 1 1 1 1   （0xFF）
   想写入 0xA5：   1 0 1 0 0 1 0 1
                   ↓ 按位与
   结果：          1 0 1 0 0 1 0 1   ✓ 对了

   如果这 8 位之前是 0x0F： 0 0 0 0 1 1 1 1
   再想写入 0xA5：          1 0 1 0 0 1 0 1
                   ↓ 按位与
   结果：                    0 0 0 0 0 1 0 1 = 0x05   ✗ 完全不对！
```

**最阴的地方**：这个错误**不报错、不烧毁**，只是数据悄悄不对。
你读回来发现 CRC 全部失败，会先去怀疑 SPI 时序 —— 白查半天。

```c
/* 本工程的处理：进入新扇区时先擦 */
if ((s_wr_addr & (W25Q64_SECTOR_SIZE - 1UL)) == 0UL) {
    rc = w25q64_sector_erase(s_wr_addr);
    if (rc != 0U) { return 2U; }
}
```

### 铁律 ②：擦/写之后必须轮询 BUSY 位

擦除/编程是**芯片内部**在干活，主机要等它做完：

```
主机发 0x20（擦扇区）→ 芯片进入忙状态（典型 45 ms，最坏 400 ms）
                      ↓ 这期间芯片【只响应读状态寄存器】
主机循环发 0x05 读状态 → 看 bit0 (BUSY)
                      ↓ BUSY 变 0
才能发下一条指令
```

**不等会怎样？** 下一条指令被**静默忽略** —— 又是"不报错但不干活"。

```c
static uint8_t wait_busy(uint32_t timeout_us)
{
    /* ★ CS 全程保持低、只发一次 0x05，之后连续读状态字节 ——
     *   这是数据手册推荐的做法，比"每次重发 0x05"快得多。 */
    spi_cs_low();
    (void)spi_soft_transfer(CMD_READ_STATUS1);
    for (;;) {
        sr = spi_soft_transfer(0xFFU);
        if ((sr & SR1_BUSY) == 0U) { break; }
        /* ★ 必须带超时：嵌入式铁律"永不无限阻塞" */
        if ((delay_now_us() - t0) >= timeout_us) { break; }
    }
    spi_cs_high();
    return (sr & SR1_BUSY) ? 1U : 0U;   /* 1 = 超时未完成 */
}
```

> 超时用 DWT 的微秒计数（`delay_now_us()`），
> 页编程给 12 ms、扇区擦除给 1 s（都是最坏值的 2~2.5 倍）。

### 写使能要回读确认（一个容易被忽略的细节）

```c
uint8_t w25q64_write_enable(void)
{
    spi_cs_low();
    (void)spi_soft_transfer(CMD_WRITE_ENABLE);   // 0x06
    spi_cs_high();
    /* ★ 回读 WEL 位确认真的置上了 —— 这是"写使能生效"的唯一证据 */
    return ((w25q64_read_status() & SR1_WEL) != 0U) ? 0U : 1U;
}
```

**为什么必须回读？** 因为 WEL 位在操作开始后**自动清零**，
而且"没置上"的后果同样是**静默忽略**。回读一下的成本是一次单字节 SPI，非常值。

### 页编程的两个前置检查

```c
if ((len == 0U) || (len > 256U)) { return 1U; }                    // 长度 ≤ 256
if (((addr & 0xFFU) + len) > 256U) { return 2U; }                  // 不能跨页
```

**跨页的后果**：多出来的字节会**回卷到本页开头**，把前面刚写的数据覆盖掉 ——
而且是静默覆盖。

## 五、32 字节记录格式（简历第 4 条的落地）

### 5.1 字节布局（定稿）

```
偏移    长度  字段              类型 / 换算
-----  ----  ---------------  ----------------------------------
0–3     4    记录序号          uint32 小端
4–7     4    时间戳(秒)        uint32 小端
8–11    4    温度              int32  小端，℃ × 1000
12–15   4    湿度              uint32 小端，%RH × 1000
16–19   4    气压              uint32 小端，单位 Pa
20–23   4    ADC 通道 1        uint32（预留，11 月模块 3 填；现阶段固定 0）
24–27   4    ADC 通道 2        uint32（预留）
28–29   2    ★ 头 CRC          CRC-16/MODBUS，覆盖偏移 0–27（数据区）
30–31   2    ★ 尾 CRC          CRC-16/MODBUS，覆盖偏移 0–29（数据区 + 头 CRC）
-----  ----  ---------------  ----------------------------------
合计   32 B
```

### 5.2 为什么不用 `memcpy` 打包（一个很值钱的细节）

```c
/* ★ 不使用 memcpy(&buf, d, sizeof(*d)) ！ */
```

**原因**：结构体会因为**内存对齐**插入填充字节。

```
struct { uint8_t a; uint32_t b; };
  内存里实际是：[a][pad][pad][pad][b][b][b][b]   ← 3 个填充字节
  不同编译器 / 不同成员顺序，填充位置都可能不同
  ⇒ 存进 Flash 的字节格式就【不可控】了
```

**手工逐字节拆装虽然啰嗦，但字节布局由你说了算** ——
这也是 PC 端能独立解析的前提。

```c
static void put_u32_le(uint8_t *p, uint32_t v)
{
    p[0] = (uint8_t)(v & 0xFFU);
    p[1] = (uint8_t)((v >> 8) & 0xFFU);
    p[2] = (uint8_t)((v >> 16) & 0xFFU);
    p[3] = (uint8_t)((v >> 24) & 0xFFU);
}
```

> 顺带一提：**全部字段小端存放，与 STM32 原生字节序一致，不需要转换。**
> 面试问"字节序"的时候，这是个能直接讲的例子。

### 5.3 头尾双 CRC 的分工（**这是 32 B 相对 16 B 最有价值的地方**）

| | 覆盖范围 | 回答什么问题 |
|---|---|---|
| **头 CRC**（28–29） | 偏移 `0–27`（数据区） | 数据区**有没有被改坏** |
| **尾 CRC**（30–31） | 偏移 `0–29`（数据区 + 头 CRC） | 这条记录**有没有写完** |

**两者配合，就能把断电时刻精确定位到三种情况：**

```
【情况 ①】编程中断电
   数据区末尾仍是 0xFF  →  头 CRC 校验失败
   ⇒ 判定「半写记录」，丢弃                       状态 = HALF

【情况 ②】数据写完，但尾 CRC 还没写
   头 CRC 【通过】、尾 CRC 是 0xFFFF
   ⇒ 判定「数据完整但记录未收尾」
     ★ 关键：能精确识别，而【不是误判成数据有错】
     ★ 单 CRC 方案在这里只能报"整条坏了"，会把这份好数据一起丢掉
                                                   状态 = UNFINISHED

【情况 ③】全部写完
   两个 CRC 都通过   ⇒  有效记录                  状态 = OK
```

### 5.4 ⚠️ 为了让"情况 ②"真的可复现，必须**分两步写**

如果一次页编程写满 32 字节，掉电时**要么整条写好、要么整条没写**，
"数据完整但没尾 CRC"这个中间状态**几乎采集不到**，双 CRC 的设计就**白费了**。

所以 `recorder_append()` 分两次页编程：

```c
#if REC_TWO_STEP_WRITE
    /* 第一步：写偏移 0–29（28 B 数据区 + 2 B 头 CRC） */
    rc = w25q64_page_program(s_wr_addr, s_buf, REC_TAIL_CRC_OFF);
    if (rc != 0U) { return 3U; }

    /* 第二步：写偏移 30–31（2 B 尾 CRC） */
    rc = w25q64_page_program(s_wr_addr + REC_TAIL_CRC_OFF,
                             &s_buf[REC_TAIL_CRC_OFF], 2U);
    if (rc != 0U) { return 5U; }
#endif
```

**两次之间掉电 → 正好复现"记录未收尾" → 双 CRC 的设计才有意义。**

> **验证方法**：命令 `t` 会跑 `selftest_powerloss_cases()`，
> 人为构造这三种状态，然后逐一判定：
> ```
> #PWR,case1=完整记录,expect=OK(1),got=1,PASS
> #PWR,case2=数据完整但未收尾,expect=UNFINISHED(3),got=3,PASS
> #PWR,case3=编程中断电(半写),expect=HALF(2),got=2,PASS
> #PWR,case2_tail_crc=0xFFFF
> ```
> **这就是"双 CRC 不是摆设"的直接证据。**（Python 端也已用假日志验证过，见 `tools/parse_records.py`。）

### 5.5 尾 CRC 的一个数学小技巧

尾 CRC 覆盖 0–29，也就是"头 CRC 再往后算两个字节"。
既然 CRC 是**流式（有状态）算法**，就没必要重新算一遍全部 30 字节：

```c
/* 头 CRC：覆盖 0–27 */
head_crc = crc16_modbus(buf, REC_DATA_LEN);
put_u16_le(&buf[REC_HEAD_CRC_OFF], head_crc);

/* 尾 CRC：从头 CRC 的状态【续算】最后两个字节 */
put_u16_le(&buf[REC_TAIL_CRC_OFF],
           crc16_modbus_update(head_crc, &buf[REC_HEAD_CRC_OFF], 2U));
```

`crc16(buf, 30)` ≡ `crc16_update(crc16(buf, 28), buf+28, 2)` ——
数学上完全等价，而且这样写把"**尾 CRC 包含了头 CRC**"这件事直接写在代码里了。

> **面试点**："CRC 能不能分段计算？"
> 答：能。CRC 是有状态算法，`crc(A+B) = update(crc(A), B)`。
> 本项目的尾 CRC 就是这么省的。这比背一张 CRC 表更能说明你理解它。

### 5.6 断电后写指针怎么定（`recorder_scan()`）

```
逐槽位看状态，遇到第一个【不是有效记录】的槽位就停：

  · 该槽位是 EMPTY（全 0xFF）   → 写指针 = 这个槽位
                                   （它还是 0xFF，可以直接编程）

  · 该槽位是 HALF / UNFINISHED  → 写指针 = 【下一个】槽位
                                   为什么跳过：NOR Flash 位只能 1→0，
                                   这个槽位里已经有残数据，不擦扇区写不回去。
                                   跳过它只损失 32 字节，不损失其它记录 ——
                                   这是顺序追加型日志最划算的取舍。
```

**还有一个 bug 修复值得知道**（原 `recorder.c` 注释里记录的）：

```c
/* ★★ 必须从 page-1 页开始精扫，不能从 page 页开始 ★★
 *
 * 页级粗扫的判据是"页的第 1 条是否为空"。
 * 若某页只写了前几条就断电，这页的第 1 条仍然是有效记录，
 * 粗扫会认为它"写过"从而跳到下一页；
 * 但这一页后面还有空槽 —— 真正该继续写的位置【在这里】，不在下一页。
 *
 * 不回退的话就会在 Flash 里留下一个【永久空洞】：
 * 扫描把空洞后面的记录也算作有效，回读自检就会报这些空洞 CRC 错。
 * 回退一页再逐条扫，最多多读 8 条，但保证结果精确。 */
idx = (page > 0UL) ? ((page - 1UL) * REC_PER_PAGE) : 0UL;
```

> 这是一个**典型的"看起来对、边界上错"的 bug**，很值得在面试里讲：
> "粗扫只看每页第一条，遇到'页只写了一半就断电'的情况会跳页，
> 结果在 Flash 里留下永久空洞。修法是精扫时回退一页。"

## 六、完整闭环：I2C 采集 → SPI 存储 → UART 上传 → PC 逐字节校验

这是简历第 4 条的原话，也是整个项目的**验收主线**。

```
┌─────────────┐   ┌──────────────┐   ┌──────────────┐   ┌─────────────┐
│ 采集任务     │   │ 处理任务      │   │ W25Q64       │   │ PC 端        │
│              │   │              │   │              │   │             │
│ BME280       │→→→│ 打包 32 B    │→→→│ 两步页编程    │   │             │
│ (I2C)        │队列│ 头CRC + 尾CRC│ SPI│ 跨扇区先擦除  │   │             │
└─────────────┘   └──────────────┘   └──────┬───────┘   │             │
                                             │           │             │
                    通信任务（UART，命令 r） │           │             │
                    读回 → 转 HEX 打印 ──────┼──────────→│ 逐字节重算   │
                                             │           │ 头 CRC ✓     │
                                             │           │ 尾 CRC ✓     │
                                             └──────────→│ 字段比对     │
                                                         └─────────────┘
```

### ⚠️ 每一步各证明了什么、没证明什么（**这点必须分清**）

| 证据 | 证明了 | ❌ 没证明 |
|---|---|---|
| 串口打出的 HEX 行 | 打包正确 + UART 传输正确 | ❌ 写进 Flash 的字节对不对 |
| 板子自己的命令 `v` 报 OK | 板子**自己**前后一致 | ❌ 打包函数有没有把字段放错位置 |
| **PC 端 `parse_records.py`** | **整条链路上的字节一个都没被改过**（独立实现重算） | — |
| **`selftest_record_roundtrip()`** | 写进去 = 读出来 = **原值**（三重比对：双 CRC + 序号/时间戳 + 温湿压） | — |

**为什么"只比 CRC 不够"**：CRC 只证明"**字节没变**"。
万一打包函数把字段放错了位置（比如温度写在湿度的位置上），CRC 依然全对。
**必须再比一次字段值**，才算真正证明"写进去 = 读出来 = 原值"。
（`selftest_record_roundtrip()` 做的就是三重比对。）

## 七、边界测试（执行计划要求"跨页、跨扇区不出错"）

32 B 记录和 Flash 边界的关系很"巧"，这是刻意选的：

| 边界 | 大小 | 能放几条 32 B 记录 | 为什么会跨 |
|---|---|---|---|
| 页 | 256 B | **8 条**（256 ÷ 32 = 8） | 每写 8 条就跨一次页 |
| 扇区 | 4096 B | **128 条**（4096 ÷ 32 = 128） | 每写 128 条就跨一次扇区 |

**⇒ 32 B 整除 256，所以一条记录永远不会跨页** ——
页编程逻辑简单到不会出错（这也是选 32 B 而不是 30 B / 33 B 的原因之一）。

### 为什么两步写也不会跨页

```
一步：写偏移 0–29，长度 30
      页内偏移最大 = 224（最后一条记录在页内的起始偏移）
      224 + 30 = 254 ≤ 256  ✓

二步：写偏移 30–31，长度 2
      页内偏移 = 224 + 30 = 254
      254 + 2 = 256 ≤ 256   ✓（刚好顶到边界，不越界）
```

### 自检怎么测边界

`selftest_record_roundtrip()` 在**保留的 8 KB 暂存区**（芯片最后 2 个扇区）写 **256 条**记录：

```c
/* 256 条 = 32 个页边界 + 1 个扇区边界（第 128 条）*/
#define SELFTEST_SCRATCH_ADDR   (W25Q64_TOTAL_SIZE - (2UL * W25Q64_SECTOR_SIZE))
#define SELFTEST_SCRATCH_SLOTS  ((2UL * W25Q64_SECTOR_SIZE) / REC_SIZE)   /* 256 */
```

**为什么用暂存区而不是记录区？**
因为自检要**擦除**扇区，直接拿记录区测会**毁掉真实日志**。
把暂存区放在芯片最尾部（`0x7FE000`），让"自检"和"记录"在物理地址上彻底分开 ——
**自检怎么写都不可能破坏日志。**

## 八、验收怎么做

| 验收项 | 命令 | 判据 |
|---|---|---|
| 四模式波形 | `t` + 逻辑分析仪 | 四种模式各发 `0xA5`，能指着波形说出 SCLK 空闲电平与采样沿 |
| 回环 | `t` | 四种模式 `echo=MATCH`（**全 MATCH 才是对的**，见 §3） |
| 主从不匹配 | `t` | `MISMATCH,...shifted=YES` |
| **分模式读 ID** | `t` | Mode0 / Mode3 得 `EF 40 17`；Mode1 / Mode2 得错值 |
| 记录闭环 | `t` | `#REC,written=256,mismatch=0,result=PASS` |
| **断电三情况** | `t` | `#PWR` 三行全 PASS |
| PC 逐字节校验 | `r` + `parse_records.py` | `结论: PASS —— 全部 N 条记录的头、尾 CRC 均在 PC 端独立重算通过` |
| 跨页跨扇区 | `t` | 上面的 256 条已覆盖 32 个页边界 + 1 个扇区边界 |

### 完整验收动线

```bash
cd firmware/tools

# ① 先确认 PC 端和固件是同一套 CRC（开机横幅里的 #CRC 行对一下）
python crc16_modbus.py --selftest        # 应输出 PASS (0x4B37)

# ② 跑完整 W4 自检（一条命令搞定，含回环 / 分模式 ID / 记录闭环 / 断电三情况）
python serial_capture.py --port COM5 --out selftest.txt \
       --seq t --stop-marker "W4 自检结束"

# ③ 回读全部记录并由 PC 逐条校验双 CRC
python serial_capture.py --port COM5 --out records.txt \
       --seq r --stop-marker "#DUMP,end"

python parse_records.py records.txt --csv records.csv --show 10
```
