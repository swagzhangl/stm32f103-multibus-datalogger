## 0 · 开工前：接线与工具

### 0.1 接线核对（照 `Core/Inc/board.h` 抄）

| 功能 | 引脚 | 接到 | 检查点 |
|---|---|---|---|
| LED | PC13 | 板载 | 无需接线 |
| USART1 TX | **PA9** | CH340 的 **RXD** | ⚠️ TX 接 RX，**交叉接** |
| USART1 RX | **PA10** | CH340 的 **TXD** | 本版新增；不接也能跑，但命令用不了 |
| I2C SCL | **PB6** | BME280 的 SCL | ⚠️ **必须共地** |
| I2C SDA | **PB7** | BME280 的 SDA | ⚠️ 上拉电阻（模块一般自带 4.7k） |
| SPI CS | **PA4** | W25Q64 的 CS | |
| SPI SCK | **PA5** | W25Q64 的 CLK | |
| SPI MISO | **PA6** | W25Q64 的 **DO** | ⚠️ DO = Data Out（从机出）→ 接主机入 |
| SPI MOSI | **PA7** | W25Q64 的 **DI** | ⚠️ DI = Data In（从机入）→ 接主机出 |
| 蜂鸣器 | **PB0** | 有源蜂鸣器 I/O | 低电平触发（见 `buzzer.c` 说明） |
| 调试 | SWDIO/SWCLK | ST-Link | |

**三个最容易接错的地方**：
1. **TX 与 RX 必须交叉**（板 TX → 适配器 RX）。
2. **SPI 的 MISO/MOSI 搞反**（DO↔DI）。搞反的表现是：**读 ID 全是 `FF FF FF` 或 `00 00 00`**。
3. **没共地**。所有模块的 GND 必须和板子 GND 接在一起，否则通信一定不稳。

```bash

# 串口抓包需要 pyserial
pip install pyserial
```

串口助手设置：**115200 / 8 / N / 1**，编码 **UTF-8**。

## 1 · 第一步：编译 + 烧录 + 看开机横幅

```bash
cd firmware
make                # 或 make -j4
make size           # 顺便看资源占用
```

**编译必须零错误、零告警**（`-Wall -Wextra` 已开）。
产出 `build/fw.elf` / `fw.hex` / `fw.bin`。

烧录（三种任选）：
```bash
# ① 菜单里选（最省事，会自动挑最新的产物并检查有没有过期）
python tools\run.py      → 选 8

# ② make 目标
make flash

# ③ 手动（注意是 -d 不是 -w：.hex/.elf 自带地址信息）
STM32_Programmer_CLI.exe -c port=SWD freq=4000 -d build\fw.hex -v -rst

# 如果你是在 CubeIDE 里编译的，产物在 Debug\ 而不是 build\：
STM32_Programmer_CLI.exe -c port=SWD freq=4000 -d Debug\firmware.elf -v -rst
```

⚠️ **CubeIDE 默认只产出 `.elf`，不产出 `.hex`**。所以"在 CubeIDE 里编完，
却去烧 `build\fw.hex`"会烧到旧版本 —— 用 `python tools\run.py` 选 8 可以避开这个坑。

### ✅ 开机横幅应该是这样（**逐行核对**）

```
========================================================
 多总线数据采集终端  |  STM32F103C8T6 寄存器裸机 + FreeRTOS
 I2C(BME280) + SPI(W25Q64) + UART(printf/命令) 三总线
========================================================
#CLK,got:    SYSCLK=72000000 HCLK=72000000 PCLK1=36000000 PCLK2=72000000
#CLK,expect: SYSCLK=72000000 HCLK=72000000 PCLK1=36000000 PCLK2=72000000
#CLK,APB1上限=36000000 —— 上面 PCLK1 超过它就会外设时好时坏
#UART,BRR=625 (expect 625 = 0x271, baud=115200 err=0%), DWT=ok
#BUILD,APP_MUTEX_ENABLE=1,APP_STACK_MEASURED=0,APP_UART_VERBOSE=1,REC_SIZE=32,TWO_STEP_WRITE=1
#CRC,check='123456789',got=0x4B37,expect=0x4B37,PASS (存储时低字节先发)
#CMD,发送 h 查看命令表
[boot] 记录区已存 0 条 / 容量 131072 条
[boot] 启动 FreeRTOS 调度器 ...
```

| 行 | 判据 | 不符说明什么 |
|---|---|---|
| `#CLK,got` | 必须和 `expect` **完全一致** | 不一致 → 时钟树没配对（看 §7 故障表） |
| `#CLK` PCLK1 | 必须是 **36000000** | 是 72000000 → **APB1 忘了分频 /2**（坑 #2） |
| `#UART,BRR` | 必须是 **625**，`DWT=ok` | BRR 不是 625 → 时钟没到 72 MHz。`DWT=FAIL` → 延时退化了 |
| `#CRC` | 必须是 **PASS 0x4B37** | FAIL → 源码被改过，先恢复 `crc16.c` |
| `REC_SIZE=32` | 必须是 **32** | 是 16 → 你烧的是旧固件 |

### ⚠️ 如果完全没有输出（连乱码都没有）

按这个顺序查：

1. **TX/RX 是否交叉**？把 PA9 和适配器的 RXD 对调试一次。
2. **是否共地**？
3. **串口助手波特率是否 115200**？CH340 的驱动装了吗（设备管理器里能看到 COM 口吗）？
4. **烧录真的成功了吗**？ST-Link 的 SWD 接线（SWDIO/SWCLK/GND/3V3，留意有没有接 NRST）。
5. 用逻辑分析仪直接抓 PA9 —— 有波形说明板子在发，是适配器侧的问题；没波形说明没跑到 printf。

### 如果输出是乱码

| 现象 | 原因 |
|---|---|
| 全是无意义字符 | 波特率不匹配（时钟没到 72 MHz 但 BRR 按 72 算；或串口助手设错） |
| 英文/数字正常，**中文乱码** | 串口助手编码不是 UTF-8。改一下即可，不影响机器可读的 `#TAG` 行 |

## 2 · W1 验收

### 2.1 时钟树 72 MHz + 串口输出

已在 §1 核对完毕。

### 2.2 逻辑分析仪验证 UART 波形

1. 探头接 **PA9**，地线接 GND。
2. 触发方式设 **下降沿**（起始位是低电平）。
3. 采样率给足（**≥ 1 MHz**，建议 4~24 MHz）。

**判据**：

| 量什么 | 期望值 | 怎么算 |
|---|---|---|
| **1 个 bit 的宽度** | **≈ 8.68 µs** | `1 / 115200 s = 8.6806 µs` |
| 一帧（10 bit） | ≈ 86.8 µs | 起始(1) + 数据(8) + 停止(1) |
| 空闲电平 | 高 | 停止位后保持高 |

**如果量到 ≈ 78 µs**（= 1/8MHz × 10）→ 说明**时钟没提上去**，BRR 按 72 MHz 算但实际跑在 8 MHz（坑 #1 / #3）。

> **技巧**：发 `0x55`（0101 0101）或 `0xAA` 最容易量 —— 边沿多，一眼能数出 bit 边界。
> 开机横幅里大量的 `0`/`1` 字符（ASCII `0x30`/`0x31`）也很好数。

### 2.3 LED 能闪

**判据**：PC13 上的 LED **每 10 秒翻转一次**（不是 1 秒 —— 别以为坏了）。
严格的抖动测量：把逻辑分析仪接 PC13，量跳变间隔，应该是 `10.000 s`。

## 3 · W2 验收

### 3.1 chip id = 0x60

串口发命令 **`i`**：

```
#CHIPID,0x60,BME280(有湿度)
```

| 结果 | 含义 |
|---|---|
| `0x60` | ✅ BME280，有湿度 |
| `0x58` | ⚠️ 是 **BMP280**（没有湿度通道），换器件 |
| `ERR,lock timeout` | 有别的任务长时间占着 I2C 锁（罕见） |
| 没反应/乱码 | 见 §7 故障表 |

### 3.2 读 33 个校准系数

串口发 **`c`**：

```
#CALIB,T1=28253,T2=26382,T3=50,P1=37150,...,H6=30,count=33
```

**判据**：
- `count=33`（表示 18 个字段覆盖了全部 33 个系数，其中 H4/H5 是 12 位拼接值）
- **所有值都不是 0**。如果全是 0 → I2C 读的是空（接线或上拉问题）

> **把这一行复制保存下来** —— PC 端复算要用它。

### 3.3 逻辑分析仪看完整 I2C 事务

探头接 **PB6(SCL) + PB7(SDA)**（双通道），触发设 SCL 下降沿。

**应该看到这样一个完整事务**：

```
① START（SCL 高时 SDA 下降）
② 7 位地址 EE + 写位 0  → 0xEE
③ 第 9 个时钟：从机拉低 = ACK
④ 8 位寄存器地址（比如 0xD0）
⑤ ACK
⑥ 【Repeated START】（没有再出现 STOP）
⑦ 7 位地址 EE + 读位 1  → 0xEF
⑧ ACK
⑨ 8 位数据
⑩ 主机回 NACK
⑪ STOP（SCL 高时 SDA 上升）
```

> **面试时可以指着这张波形讲**："这是 START，这是 Repeated Start ——
> 中间没有 STOP，所以写寄存器号和读数据是同一个事务，别的总线主机抢不走。"

### 3.4 温湿压读数合理

看每秒一行的数据：

```
[12s] seq=12 T=2531c H=4823c P=101325Pa store=ok
        ↑ 0.01℃   ↑ 0.01%RH  ↑ Pa
       = 25.31℃   = 48.23%RH  = 1013.25 hPa
```

| 量 | 合理范围（室内） |
|---|---|
| 温度 | 15 ~ 35 ℃ |
| 湿度 | 30 ~ 80 %RH |
| 气压 | 99000 ~ 103000 Pa（随海拔和天气变化） |

### 3.5 ★ PC 端独立复算逐位一致（**简历第 3 条的证据**）

```bash
cd firmware/tools

# 抓日志：先发 c 拿校准系数，再发几次 m 触发测量
python serial_capture.py --port COM5 --out bme.txt --seq c,m,m,m,m,m --gap 2

# PC 端独立复算并比对
python verify_bme280.py bme.txt
```

**判据**：输出

```
复算比对：共 30 项，其中不一致 0 项
结论：PASS —— PC 端独立复算与固件输出【逐位一致】
```

> **关键**：PC 端**只使用**原始 ADC 值 + 出厂校准系数，
> **不复用固件的任何中间结果**（那叫抄答案）。
> 详细原理见 `docs/02_W2_I2C与BME280.md` 第六节。

## 4 · W3 验收

### 4.1 三任务跑起来（队列在传数据）

看串口：

```
[1s] seq=1 T=2531c H=4823c P=101325Pa store=ok
[2s] seq=2 T=2532c H=4824c P=101326Pa store=ok
...
```

| 字段 | 含义 |
|---|---|
| `seq` | 连续递增 → 采集任务在严格 1 s 节拍上跑 |
| `T/H/P` | `SENSOR_INVALID` 表示本次读失败（会被跳过，不写 Flash） |
| `store=ok` | **处理任务成功写进 Flash** → 队列在传数据 ✅ |
| `store=skip` | 本次采样无效，主动跳过（正常保护行为） |
| `store=ERR2/3/5` | 扇区擦除/数据段编程/尾 CRC 编程失败 → 见 §7 |

### 4.2 权威验证：周期到底漂不漂

把逻辑分析仪接 **PC13**（每 10 秒翻转一次）：

- 量 **100 个周期**（约 1000 秒 ≈ 17 分钟）
- **判据**：累积误差 < 10 ms

> **为什么这个测试重要**：它把"用 `vTaskDelayUntil`"这个选择变成了**可测量的结果**。
> 面试时可以说："我用逻辑分析仪量了 100 个翻转周期，累积误差 X ms。"

### 4.3 ★ 互斥锁对照实验（**面试最有说服力的一段**）

**第 1 步：关掉锁**

打开 `Core/Inc/app_config.h`，改：
```c
#define APP_MUTEX_ENABLE   0
```
重新编译烧录。

**第 2 步：观察 30 秒**

预期看到**两行文字互相插队**：

```
[0012s] seq=12 T=2531c H=4823c P=101[0012s] seq=12 store=ok
                     325Pa store=ok
```

```
!!! ALARM humidity >= 65.00 %RH a[0013s] seq=13 T=2532c H=...
```

**把屏幕**截图/拍照**保存下来 —— 这是面试素材。**

**第 3 步：加回锁**

```c
#define APP_MUTEX_ENABLE   1
```
重新编译烧录。输出应恢复成每行完整。

**第 4 步：解释为什么**

`uart_dbg_str("abc")` 是**逐字节**发出去的，一整行要好几毫秒。
这期间高优先级任务抢占 CPU 也去打印，字节就**插进了**前一条消息的中间。
**这不是显示问题，它揭示了"多步操作必须不可分割"这个普遍风险** ——
共享的 I2C / SPI 总线也是同一个道理。

## 5 · W3.5 验收（栈水位 + 稳定性 + 更新简历）

### 5.1 栈水位实测

**前提**：确保 `APP_STACK_MEASURED = 0`（宽裕档），这样测出来的"已用峰值"不受人为限制。

跑一段（越久越准，24 h 最佳），然后发命令 **`s`** 或等每 60 秒自动打印：

```
#STK,heap_free=3900,tasks=4,acq=NNN,proc=NNN,comm=NNN,uart_hold_us=NNN,lock_tmo=0
```

### 5.2 算压缩比

```bash
python stack_budget.py log.txt --alloc acq=256,proc=256,comm=384 --baseline 512
```

脚本会输出**可以直接粘进简历的句子**。

> ⚠️ **三条硬规矩**（脚本里也会提醒）：
> ① `--alloc` 必须和当时烧录的固件一致（横幅 `#BUILD,APP_STACK_MEASURED=` 可佐证）
> ② 压缩比**必须说明相对哪个基准**
> ③ **不许用示例值** —— 必须是你自己跑出来的

### 5.3 回填代码并复测

把脚本给的三个推荐值填进 `Core/Src/app_tasks.c` 的 `APP_STACK_MEASURED` 分支，
把 `app_config.h` 里的 `APP_STACK_MEASURED` 改成 **1**，重新编译烧录。

> 编译时会弹出一条 `#warning` 提醒你确认数字已替换 —— 这是故意的。

**复测判据**：新的 `#STK` 行里**所有任务的剩余水位仍 > 0**（有余量才算安全）。

### 5.4 24 小时稳定性测试

**先改这一行**（否则一天 86400 行日志，串口助手会卡死）：
```c
#define APP_UART_VERBOSE   0
```

然后挂着跑 24 小时。判据：

| 项 | 判据 |
|---|---|
| 不死机 | 24 h 后仍在正常打印 |
| 无栈溢出 | 不会出现 `!!! STACK OVERFLOW` |
| 堆不泄漏 | `heap_free` 保持稳定（持续下降 = 泄漏） |
| 记录数线性增长 | `records` 约 `24 × 3600 = 86400` 条 |

> ⚠️ **注意容量**：记录区 4 MiB ÷ 32 B = **131072 条 ≈ 36.4 小时**。
> 24 h 大概用 66% 的容量，**够用但别跑太久**（超过 36 小时会写满）。

### 5.5 更新简历

执行计划要求的改动：

## 6 · W4 验收

### 6.1 一键跑完所有自检

```bash
cd firmware/tools
python serial_capture.py --port COM5 --out selftest.txt \
       --seq t --stop-marker "W4 自检结束"
```

自检包含四块，逐块判据如下。

#### ① 四种模式回环自测

```
#SPI4,Mode0,CPOL=0,CPHA=0,SCLK_idle=LOW,tx=0xA5,rx=0xA5,echo=MATCH
#SPI4,Mode1,CPOL=0,CPHA=1,SCLK_idle=LOW,tx=0xA5,rx=0xA5,echo=MATCH
#SPI4,Mode2,CPOL=1,CPHA=0,SCLK_idle=HIGH,tx=0xA5,rx=0xA5,echo=MATCH
#SPI4,Mode3,CPOL=1,CPHA=1,SCLK_idle=HIGH,tx=0xA5,rx=0xA5,echo=MATCH
#SPI4,MISMATCH,tx_mode=1(CPHA=1),rx_mode=0(CPHA=0),tx=0xA5,rx=0x52,shifted=YES
```

**⚠️ 关键认知**：四种模式**全部 `MATCH` 才是预期结果**。
因为回环时收发用同一个模式，两者永远自洽 —— 它只证明**位引擎正确**，
**证明不了模式配对正确性**（详见 `docs/04` 第三节）。

**需要一根杜邦线把 PA7(MOSI) 与 PA6(MISO) 短接**。没短接的话会读到 `FF` 或 `00`。

`MISMATCH` 那行的 `rx` 值随 MOSI 残留电平变化，可能是 `0x52`、`0xD2` 之类 ——
只要 `shifted=YES`（不等于原值）就说明演示成功。

#### ② 四种模式读 W25Q64 的 JEDEC ID ★（最硬的证据）

```
#SPIID,Mode0,EF 40 17,OK
#SPIID,Mode1,FF FF FF,WRONG
#SPIID,Mode2,FF FF FF,WRONG
#SPIID,Mode3,EF 40 17,OK
#SPIID,读通模式数=2
```

**判据：读通模式数 = 2**（Mode0 与 Mode3）。
这符合 W25Q64 数据手册"只支持 Mode 0/3"的标注 ——
**这就是"模式配错会怎样"的物理证据**。

| 结果 | 含义 |
|---|---|
| 2 种读通 | ✅ 符合预期 |
| 4 种都读通 | 检查 `spi_soft_set_bit_delay_us()` 是不是设太大了（时序过宽松会掩盖问题） |
| 0 种都读通 | 查接线（PA4=CS / PA5=SCK / PA6=DO / PA7=DI）与 3.3V 供电 |

#### ③ 32 B 记录闭环（写 256 条 + 三重比对）

```
#REC,槽位数=256，跨 1 个扇区边界（第 128 槽）与 32 个页边界
#REC,written=256,mismatch=0,result=PASS
```

**判据：`mismatch=0`**。
自检在**保留的暂存区**（芯片最后 2 个扇区）做，**不会碰你的真实日志**。

三重比对 = ① 双 CRC 状态 ② 序号/时间戳 ③ 温湿压。
**只比 CRC 不够** —— CRC 只证明"字节没变"，证明不了打包时字段有没有放错位置。

#### ④ 断电三情况（双 CRC 的验证）

```
#PWR,case1=完整记录,expect=OK(1),got=1,PASS
#PWR,case2=数据完整但未收尾,expect=UNFINISHED(3),got=3,PASS
#PWR,case3=编程中断电(半写),expect=HALF(2),got=2,PASS
#PWR,case2_tail_crc=0xFFFF
#PWR,result=PASS
```

**这三行全 PASS，就证明了"头尾双 CRC 不是摆设"。**

### 6.2 逻辑分析仪看四种模式波形（**"能指着讲"就是验收标准**）

把探头接 **PA5(SCK)**（+ PA7/MOSI 可选），发命令 `t`，抓四种模式的波形。

> **诀窍**：如果波形太密看不清，调用 `spi_soft_set_bit_delay_us(5)` 把时钟降到几百 kHz。
> **这正是 bit-bang 的好处** —— 速度可控，波形可读。
> （硬件 SPI 想看波形就得改分频系数了。）

**要能指着波形说出这两件事**：

| 看什么 | 对应 |
|---|---|
| SCLK **空闲时**是高还是低 | **CPOL** |
| 数据在**哪个边沿**稳定（可采样） | **CPHA** |

### 6.3 ★ PC 端逐条双 CRC 校验（**简历第 4 条的证据**）

```bash
# 回读全部记录
python serial_capture.py --port COM5 --out records.txt \
       --seq r --stop-marker "#DUMP,end"

# PC 端逐字节重算两遍 CRC
python parse_records.py records.txt --csv records.csv --show 10
```

**判据**：

```
校验结果
  有效记录 (头尾 CRC 都通过) : N
  半写记录 (头 CRC 失败)      : 0
  未收尾   (头过、尾失败)     : 0
  序号连续性: 全部连续，无整条丢失
结论: PASS —— 全部 N 条记录的头、尾 CRC 均在 PC 端独立重算通过
```

> 如果出现「未收尾」而不是 0，也**不一定**是问题 ——
> 那正是断电测试留下的痕迹，说明双 CRC 在工作（见上面 ④ 的说明）。

## 7 · 故障排查表

| 现象 | 最可能的原因 | 怎么办 |
|---|---|---|
| **完全没有串口输出** | TX/RX 没交叉；没共地；波特率错；没真烧进去 | 对调 PA9 与适配器 RXD；查地线；确认 115200 |
| **输出乱码（英文数字也乱）** | 时钟没到 72 MHz，但 BRR 按 72 算 | 看横幅 `#CLK,got` 是否等于 `expect` |
| **只有中文乱码** | 串口助手编码不是 UTF-8 | 改成 UTF-8（`#TAG` 行是 ASCII，不受影响） |
| **`#CLK,got` PCLK1 = 72000000** | APB1 忘了分频 /2（坑 #2） | 查 `clock_init.c` 第 ④ 步是否执行到 |
| **`DWT=FAIL`** | `CoreDebug->DEMCR` 的 TRCENA 写不进去（少数兼容芯片） | 延时已退化为空循环；I2C 速度要重新降速标定 |
| **`#CHIPID` 读不到 / 不是 0x60** | I2C 上拉没接 / 引脚没配开漏 / 地址 0x76↔0x77 搞反 | 按 `docs/02` 第五节的排查顺序 ①②③④⑤ |
| **校准系数全是 0** | I2C 读的是空 | 同上；也可能是时序太快，先 `i2c_soft_set_delay_us(10)` |
| **温湿压明显离谱** | 气压用了 32 位补偿（会偏 +15%） | 确认 `compensate_pressure` 里用的是 `int64_t` |
| **`#SPIID` 三种以上 WRONG** | SPI 接线错（MISO/MOSI 反了）/ 供电 / CS 没拉高 | 用逻辑分析仪抓 4 根线；确认 PA6→DO、PA7→DI |
| **`#REC` 报 mismatch** | 扇区擦除失败 / 页编程跨页 / CS 时序 | 看返回码：`rc=2` 擦除失败，`rc=3` 数据段失败，`rc=5` 尾 CRC 失败 |
| **`store=ERR2`** | 扇区擦除失败 | 检查 3.3V 供电是否够（擦除电流较大）；换一片 W25Q64 试 |
| **`lock_tmo` 不为 0** | 某任务持锁时间过长 | 看 `uart_hold_us`；检查是不是在持锁期间做了大量串口输出 |
| **`!!! STACK OVERFLOW`** | 栈给小了 | 读该任务的 `uxTaskGetStackHighWaterMark`，按峰值 ×1.5 加大 |
| **`! pvPortMalloc FAILED`** | FreeRTOS 堆不够 | 调大 `configTOTAL_HEAP_SIZE`，或减小任务栈 |
| **周期越来越慢** | 用了 `vTaskDelay` 而不是 `vTaskDelayUntil` | 见 `docs/03` 第四节 |
| **两行文字互相插队** | `APP_MUTEX_ENABLE` 被设成了 0 | 改回 1（这就是对照实验要的现象） |
