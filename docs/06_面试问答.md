## 项目经历第 1 条：FreeRTOS 三任务架构

> 简历原文：*基于 FreeRTOS 构建 3 任务采集架构（采集/处理/通信）：采集任务用 `vTaskDelayUntil` 保证 1 s 周期不漂移；以消息队列解耦采集与存储速率差，用互斥锁保护 I2C / SPI 共享总线；用 `uxTaskGetStackHighWaterMark` 实测各任务栈水位并重新分配栈空间（压缩 XX%）。*

### Q1. 为什么用 RTOS，不用超级循环？

**一句话答案**：因为**采集周期和存储耗时差了两个数量级** —— 采集要求严格 1 秒，
而 Flash 擦一个扇区最坏 400 毫秒。放一个循环里，擦除会把采集周期顶掉，
而且顶掉多少不可预测。用消息队列解耦后，采集只管往队列里放，存储慢一点由队列缓冲吸收。

**追问：队列缓冲满了怎么办？**
> 丢弃本样本，**并且计数**（`s_drop_raw`）。有统计才叫工程实现 ——
> 丢数据不可怕，丢了不知道才可怕。这个计数会打到串口上。

**追问：那通信任务在干嘛？**
> 它大部分时间**阻塞在队列上**，不占 CPU。
> 这是超级循环做不到的 —— 超级循环只能空转轮询，白烧电。

### Q2. `vTaskDelayUntil` 和 `vTaskDelay` 有什么区别？

**一句话答案**：`vTaskDelay(t)` 是"从现在起再等 t"，**本轮耗时会被累加进周期**，
所以周期会越飘越大；`vTaskDelayUntil(&last, t)` 是"到下一个绝对时刻再叫我"，
**以固定节拍推进，不累积漂移**。

```
vTaskDelay：      每轮周期 = 1000 + 干活耗时  → 误差【累积】
vTaskDelayUntil： 每轮周期 = 1000 ms           → 误差【不累积】
```

**追问：那如果某一轮真的超时了（比如 Flash 卡了 400ms）怎么办？**
> `vTaskDelayUntil` 会**立刻返回**以追赶进度 —— 那一轮的间隔被压缩了。
> **这正是我们要的语义**：宁可某轮被压缩，也不让整体节拍往后漂。
> 因为"1 秒一次"是对整个运行期的承诺，不是对某一轮的。

**追问：`last` 变量为什么必须在循环外初始化？**
> 它是"上一次的目标唤醒时刻"。在循环内用 `xTaskGetTickCount()` 重新初始化的话，
> 就退化成 `vTaskDelay` 了，白用。

### Q3. 队列、信号量、互斥锁分别用在哪？

**一句话答案**：

| 机制 | 传什么 | 本工程用在哪 |
|---|---|---|
| **消息队列** | **数据**（有内容、有长度） | 采集→处理传样本；处理→通信传结果 |
| **二值信号量** | **事件**（只有"发生过了"） | 报警从"关"变"开"时通知通信任务 |
| **互斥锁** | **所有权** | 保护 I2C / SPI / UART 共享资源 |

**记忆法**：队列是**传送带**（能放东西），信号量是**门铃**（只告诉你有人来了），
互斥锁是**钥匙**（同一时刻只有一个人能拿）。

**追问：报警为什么用信号量而不是队列？**
> 因为它要通知的是"**湿度超限了**"这个**事件**，而具体内容（哪个时刻、多少湿度）
> 已经由状态变量承载了。队列适合传有长度的数据；只关心"发生过"就用信号量。
> **把队列和信号量用混，是新手最常见的 IPC 设计错误。**

### Q4. 互斥锁和信号量有什么区别？

**一句话答案**：二值信号量也能当"开关"用，但**互斥锁有"所有者"的概念，
并且带优先级继承**。

**追问：什么是优先级继承？为什么需要它？**
> 场景：低优先级任务 L 持有锁 → 中优先级任务 M 就绪（它不需要锁）→
> 高优先级任务 H 来取锁，被阻塞。
> **M 不会被 H 抢占**（M 优先级低于 H），但 L 也拿不到 CPU（低于 M），
> 于是锁一直不放，**H 被 M 无限期挡住**。这就是**优先级反转**。
>
> 优先级继承：当 H 来取锁时，系统**临时把 L 的优先级提到和 H 一样高**，
> 让 L 尽快跑完释放锁。这样 M 就抢不走 CPU 了。
>
> ⚠️ 著名的**火星探路者号**就栽在优先级反转上（1997 年，反复重启）。

### Q5. ⚠️ `uxTaskGetStackHighWaterMark` 返回的是"已用"还是"剩余"？

**一句话答案**：返回的是**历史最小剩余量**（单位：字），**不是已用峰值**。

```
峰值已用 = 分配栈大小 − 剩余水位
推荐分配 = 峰值已用 × 1.5
```

**追问：那你怎么定栈大小的？**
> **不能拍脑袋**。正确流程是：
> ① 先用**宽裕值**跑起来（我的工程里是 256/256/384 字）；
> ② 跑覆盖最坏情况的测试（我跑了 24 小时）；
> ③ 读高水位，算峰值 ×1.5；
> ④ 回填并**再跑一遍**，确认新的剩余水位仍然 > 0。
>
> ⚠️ **顺序不能颠倒**：先猜一个小数字然后祈祷它不溢出，是纯粹的赌博。

**加分点**：我另外开了 `configCHECK_FOR_STACK_OVERFLOW = 2`
（栈尾填 `0xA5A5A5A5` magic，任务切换时校验），
溢出时会调用钩子**先打一行字再停住**。

### Q6. ⚠️ 栈溢出钩子函数里你能做什么？

**一句话答案**：**只能往串口打一行字，然后关中断死循环停住。绝对不能调用任何 FreeRTOS API。**

**追问：为什么？**
> 因为它是在**调度器内部 / 异常上下文**被调起的，此刻内核状态已经不可信。
> 在里面再动内核（比如 `vTaskDelete`）等于把水搅得更浑。
> **死于"知道死在哪"，比"活着但行为诡异"好得多。**

### Q7. 你在项目里怎么验证互斥锁是必需的？

**一句话答案**：我做了一个**对照实验** —— 把 `APP_MUTEX_ENABLE` 改成 0 重新编译，
串口输出 30 秒内必然出现两行文字互相插队；改回 1 就恢复正常。

```
关锁：  [0012s] seq=12 T=2531c H=4823c P=101[0012s] seq=12 store=ok
                            325Pa store=ok
加锁：  [0012s] seq=12 T=2531c H=4823c P=101325Pa store=ok
        [0013s] seq=13 T=2532c H=4824c P=101326Pa store=ok
```

**追问：原理是什么？**
> `uart_dbg_str("abc")` 是**逐字节**发出去的，一整行要好几毫秒。
> 这期间高优先级任务抢占 CPU 也去打印，字节就插进了前一条消息中间。
>
> **关键**：这不是"显示问题"，它揭示了**"多步操作必须不可分割"**这个普遍风险 ——
> 共享的 I2C / SPI 总线也是同一个道理，一次事务被插入，从机侧就完全乱套了。

**面试金句**：
> "这个现象我是**亲眼看见**的，不是我背下来的。所以我知道临界区保护不是理论，是必须的。"

## 项目经历第 2 条：手写 bit-bang I2C / SPI 时序

> 简历原文：*不依赖 HAL 与现成驱动，手写 bit-bang I2C / SPI 主机时序（含 START / STOP / Repeated Start、四种 SPI 模式），并用逻辑分析仪对波形逐帧验证。*

### Q8. I2C 为什么必须开漏输出？推挽会怎样？

**一句话答案**：I2C 是**线与**总线 —— 任何一方拉低就是低，所有人都不拉才是高（靠上拉电阻）。
**推挽会主动输出高电平**，当别人正拉低时，两个管子直接对打形成短路。

**追问：开漏模式下你怎么切换收发方向？**
> 常规做法是"发的时候配输出、收的时候配输入"，每次都要改 CRL 寄存器。
> 我用的是：**全程保持开漏输出，用 ODR 位控制** ——
> ODR 写 0 = 拉低，ODR 写 1 = 松开（引脚变高阻，交给从机/上拉）。
> 读"线上真实电平"要去 **IDR** 读：即使 ODR 写了 1，只要从机拉低，IDR 读回仍是 0。
>
> **一句话**：`ODR` 是"我想干什么"，`IDR` 是"线上实际是什么"。

### Q9. START 和 STOP 是怎么定义的？为什么这么定义？

**一句话答案**：I2C 规定"**在 SCL 高电平期间翻转 SDA**"是**非法动作**，
然后把这两个非法动作定义成控制信号：

- **START**：SCL 高时，SDA 由**高变低**
- **STOP**：SCL 高时，SDA 由**低变高**

正常传数据只能在 SCL 为低时改 SDA。

### Q10. Repeated Start 解决什么问题？

**一句话答案**：读寄存器分两段（先写寄存器号、再读数据）。
如果中间插了 **STOP**，总线会短暂"空闲"，**别的主机可能抢走总线** ——
于是两段落在不同事务里，从机状态机被打断，读到的数据不可信。
**Repeated Start 就是"发 START 但不发 STOP"**，让整个复合事务不可分割。

**面试金句**：
> "能指着逻辑分析仪说'这是 START，这是 Repeated Start，中间没有 STOP' ——
> 这句话比背一百遍协议都有说服力。"

### Q11. ⚠️ 主机读 ACK 之前要注意什么？

**一句话答案**：**必须先松开 SDA**（写 1）。
否则主机把线拉着，从机想拉低也拉不动，就永远读不到 ACK。

```c
sda_high();     /* 主机松手，让从机拉低表示应答 */
scl_high();     /* 第 9 个时钟上升沿 */
nack = sda_read();
```

### Q12. CPOL 和 CPHA 各决定什么？

**一句话答案**：

| 参数 | 决定 |
|---|---|
| **CPOL** | SCLK **空闲时**是高还是低 |
| **CPHA** | 在**第几个边沿**采样 |

实用记法：**CPHA=0 → 前沿采样**（数据必须在前沿**之前**摆好）；
**CPHA=1 → 后沿采样**（数据在前沿**之时**才改变）。

### Q13. ⚠️⚠️ 你怎么验证"四种 SPI 模式"配对了？

**这道题是本项目最有区分度的一题，因为它藏着一个陷阱。**

**一句话答案**：**光靠"MOSI-MISO 短接回环"是验证不了的。**
因为回环时收发用**同一个模式**，"什么时候摆数据"和"什么时候读线"是同一个人控制的，
两者永远自洽 —— **四种模式都会读回原值**。

我做了三层验证：

| # | 方法 | 能证明什么 |
|---|---|---|
| 1 | 杜邦线回环，四种模式各发 `0xA5` | **位引擎正确**（移位方向、边沿计数、MISO 通路） |
| 2 | 发送侧与接收侧用**不同模式**收发 | 真的能看到移位（"主从模式不匹配"的等价演示） |
| 3 | **W25Q64 分模式读 JEDEC ID** | ✅ **模式配对正确性**（物理证据：Mode0/3 得 `EF 40 17`，Mode1/2 读错） |
| 4 | 逻辑分析仪看波形 | ✅ CPOL（空闲电平）、CPHA（数据稳定沿） |

**面试金句**（这段最能加分）：
> "我一开始按文档写的做回环自测，结果四种模式全都读回原值，我以为是测试写错了。
> 后来想明白了：回环时收发同一个模式，自洽是必然的。
> 所以我又补了两项 —— 用不同模式收发来演示移位，以及用 W25Q64 分模式读 ID 作物理证据。
> **能把'我发现的文档错误'讲清楚，比背下四种模式更有意义。**"

### Q14. 为什么 W25Q64 用 Mode 0？

**一句话答案**：数据手册标注它**支持 Mode 0 和 Mode 3**。
选 Mode 0 是因为 **Mode 0 下 SCLK 空闲为低，与上电后的默认电平一致**，
不会在片选拉低的那一瞬间产生一个多余的时钟边沿去误触发从机。

**追问：那到底该听谁的？**
> **从机决定模式，主机必须跟随。** 主机没有选择权，只能去读从机的手册。

### Q15. 为什么用 bit-bang 而不是硬件 SPI？

**一句话答案**：**为了看清楚、为了能改。** 三个具体理由：

1. **速度可控**：想看波形就 `spi_soft_set_bit_delay_us(5)` 把时钟降到几百 kHz。
   硬件 SPI 想看波形得去改分频系数，还没法逐帧控制。
2. **四模式只差参数**：时钟和数据都是我用 GPIO 翻出来的，
   写一个带 `mode` 参数的函数就覆盖四种。（硬件 SPI 对应 `SPI_CR1` 的 CPOL=bit1、CPHA=bit0。）
3. **求职线的时间预算**：W4 只有 2.5 人日，bit-bang 调起来比配硬件 SPI + DMA 快。

**追问：那实际产品会怎么选？**
> 实际产品当然用硬件 SPI —— 速度快、不占 CPU。
> **我知道这个取舍**：bit-bang 的代价是 CPU 全程参与（每字节约几十微秒），
> 而硬件 SPI 是 DMA 搬运、CPU 几乎不参与。

## 项目经历第 3 条：BME280 完整驱动

> 简历原文：*实现 BME280 完整驱动：读取 33 个出厂校准系数 + 移植 Bosch 官方整数补偿算法；气压补偿改用 64 位运算避免中间量溢出，温湿压结果经 PC 端复算逐位一致。*

### Q16. 为什么必须读 33 个校准系数？

**一句话答案**：BME280 输出的是**原始 ADC 值（20 位）**，
而这个值随**每颗芯片的工艺偏差**不同 —— 同一批芯片、同样气压，ADC 能差几个百分点。
芯片出厂时把补偿参数烧在 NVM 里，**不读出来就无法得到真实物理量**，换颗芯片数值就全变。

**追问：33 个怎么分布的？**
> 两段：`0x88–0xA1`（26 B）+ `0xE1–0xE7`（7 B）。
> 具体是 `T1..T3`（6 B）+ `P1..P9`（18 B）+ `0xA0` 保留（1 B）+ `H1`（1 B）+ `H2..H6`（7 B）。
> ⚠️ 注意 **`0xA0` 是保留字节要跳过**，`H1` 是**单字节**在 `0xA1`。

**追问：哪个最容易写错？**
> `dig_H4` / `dig_H5`。它们是 **12 位**，被拆成"高 8 位 + 低 4 位"跨字节存，
> 而且 **`0xE5` 这一个字节被 H4 和 H5 瓜分**：
> H4 = `0xE4` 全部 8 位 + `0xE5` 的**低** 4 位；
> H5 = `0xE6` 全部 8 位 + `0xE5` 的**高** 4 位。

### Q17. 为什么配置寄存器的顺序不能换？

**一句话答案**：**`ctrl_hum`（0xF2）必须在 `ctrl_meas`（0xF4）之前写。**
因为湿度配置只有在**写 `ctrl_meas` 时才被锁存进生效寄存器**。
顺序反了湿度配置根本不生效 —— 而且**不报错**，只是湿度一直是默认值。

**追问：除了这个还有哪些"静默失效"的坑？**
> 有好几个，都是"不报错但不干活"：
> - SPI Flash 的**写使能没置上** → 写/擦指令被静默忽略（所以我要**回读 WEL 位**确认）
> - Flash **擦/写后没轮询 BUSY** → 下一条指令被忽略
> - Flash **写前没擦扇区** → 新旧数据按位与，数据悄悄不对
>
> **这一类问题是最难查的**，因为返回值、流程都正常，只有结果是错的。

### Q18. 气压补偿为什么要用 64 位？

**一句话答案**：因为 Bosch 的 32 位版在这一行会**溢出**：

```c
p = (((p << 31) - var2) * 3125) / var1;   // ★ int32 下 p<<31 直接溢出成负数
```

64 位版中间量最长到 2^47 量级，必须用 `int64_t`。

**追问：你怎么发现的？**
> 我一开始用了 32 位版，实测气压**偏高 15%**（输出 1164 hPa，真值 1011 hPa）。
> 换成 64 位版就正确了。
> —— 这是一个**真实调过的 bug**，不是背公式。

### Q19. ⚠️ 温湿压为什么要"一起算"？

**一句话答案**：因为温度补偿会算出中间量 **`t_fine`**，
**气压和湿度的补偿公式都要用它**。所以顺序固定：先温度 → 再气压/湿度。

**追问：那读数据的时候要注意什么？**
> 必须**一次连读 8 字节**（`0xF7–0xFE`：气压 3 + 温度 3 + 湿度 2）。
> 分三次读可能跨两次转换，导致"气压是上一秒的、温度是这一秒的" ——
> 三个量不是同一批测量。数据手册明确要求整批读出。

### Q20. ⚠️ "PC 端复算逐位一致"你是怎么做到的？为什么不能复用固件的中间结果？

**一句话答案**：PC 端**只使用** `#CALIB`（33 个校准系数）+ `#RAW`（3 个 ADC 原始值），
用 Python **独立重写**一遍补偿算法，再和 `#CMP` / `#OUT` 比对。
如果拿固件的中间量再去算最终值，那叫**抄答案**，证明不了任何事。

**追问：PC 端重写遇到过什么坑？**
> **C 的整数除法是"向零截断"，Python 的 `//` 是"向下取整"**：
> ```
> C:      -7 / 2  = -3
> Python: -7 // 2 = -4
> ```
> 气压补偿里 `(p << 31) - var2` 完全可能是负数，所以必须显式实现向零截断的除法。
> 不处理的话 PC 算出来会**差 1** —— 而且看起来像随机误差，最难查。

### Q21. 那个"温度尖峰"是怎么回事？（**这道题能拉开档次**）

**一句话答案**：长跑 8.35 小时 / 30062 条里出现过 2 条孤立尖峰（温度 +15.6 ℃、气压 +25.2 hPa），
下一条立刻恢复。**两次偏移量几乎完全相同** —— 随机噪声不可能重复出同一幅度，
所以这是**确定性污染**，不是噪声。

**追问：你怎么定位的？**
> 用实测校准系数反推：单一 `t_fine` 偏移 Δtf≈79975 **恰好同时**产生
> +15.62 ℃ 与 +25.21 hPa，与观测量完全吻合
> ⇒ **温度 ADC 被污染，气压因依赖 `t_fine` 被同步带偏**。

**追问：为什么 CRC 抓不到它？**（**核心认知题**）

> **CRC 保护的是"打包 → 存储 → 传输"这条链路**，
> 它只能证明"存进去的字节 = 读回来的字节"，
> **不能证明"从传感器读到的字节是对的"** —— 这是两个完全不同的断言。
>
> ```
>   传感器 → 打包+CRC → Flash → UART → PC
>              ↑ CRC 的保护范围从这里开始
> ```
> 所以在驱动层必须再加一道**物理量闸门**。

**追问：那你怎么修的？**
> 两道防线：
> ① **事后拦截**：绝对范围（-40~85 ℃）+ 变化率（1 Hz 下相邻两次温差 ≤ 2.00 ℃）。
>    那条 +15.6 ℃ 会被变化率拦下，然后**立刻重读一次**；两次都不可信就返回错误码，
>    **绝不把已知错误的数据写进 Flash**。
> ② **事前避免**（根因修复）：读 8 字节**之前**先看状态寄存器的 `measuring` 位（`0xF3` bit3）。
>    它是 0 才读。因为转换只占 1000 ms 周期里的约 46 ms，
>    所以"看到 measuring=0"就说明接下来的 0.7 ms 突发读必然落在不会被改写的窗口里。
>
> 原物理量闸门保留作第二道防线 —— **纵深防御：能预判就预判，预判不到还有兜底**。

**面试金句**：
> "这个问题的价值不在于我怎么修的，而在于我意识到了 **CRC 和传感器数据正确性
> 是两个不同层面的保证**。很多人会以为'有 CRC 就安全了'。"

## 项目经历第 4 条：32 B 记录格式 + 双 CRC 闭环

> 简历原文：*设计 32 字节定长记录格式（含头尾双 CRC-16/MODBUS），打通 I2C 采集 → SPI 存储 → UART 上传 → PC 逐字节校验的完整闭环。*

### Q22. ★★ 为什么要两个 CRC？一个不够吗？

**这道题是本项目最有含金量的设计题。**

**一句话答案**：两个 CRC 回答**两个不同的问题**：

| | 覆盖范围 | 回答什么问题 |
|---|---|---|
| **头 CRC**（28–29） | 偏移 `0–27`（数据区） | 数据区**有没有被改坏** |
| **尾 CRC**（30–31） | 偏移 `0–29`（数据区 + 头 CRC） | 这条记录**有没有写完** |

**追问：具体能区分什么？**

> | 断电时刻 | 现象 | 判定 |
> |---|---|---|
> | 编程中断电 | 数据区末尾仍是 `0xFF` → 头 CRC 失败 | **半写记录**，丢弃 |
> | 数据写完、尾 CRC 没写 | 头 CRC 通过、尾 CRC 是 `0xFFFF` | **数据完整但记录未收尾** |
> | 全部写完 | 两个都通过 | 有效记录 |
>
> **关键在第二种**：单 CRC 方案在这里只能报"整条坏了"，
> 会把这份**完好的数据**一起丢掉。**双 CRC 能精确定位到断电的瞬间。**

**追问：那你怎么保证第二种情况真的能出现？（**这题答出来就赢了**）**

> **必须分两次页编程写。** 如果一次写满 32 字节，掉电时要么整条写好、要么整条没写，
> "数据完整但没尾 CRC"这个状态**几乎采集不到**，双 CRC 就白设计了。
>
> 所以我先把 **0–29 字节**（数据 + 头 CRC）写一次，再把 **30–31 字节**（尾 CRC）写一次。
> 两次之间掉电 → 正好复现。
>
> 我还写了自检 `selftest_powerloss_cases()` 人为构造这三种状态并逐一验证判定正确：
> ```
> #PWR,case2=数据完整但未收尾,expect=UNFINISHED(3),got=3,PASS
> #PWR,case2_tail_crc=0xFFFF
> ```

### Q23. ⚠️ 打包为什么不直接用 `memcpy`？

**一句话答案**：因为结构体会因为**内存对齐插入填充字节**。

```
struct { uint8_t a; uint32_t b; };
内存里：[a][pad][pad][pad][b][b][b][b]   ← 3 个填充字节
```

不同编译器 / 不同成员顺序，填充位置都可能不同 ⇒ **存进 Flash 的字节格式就不可控了**。

**追问：那你怎么做的？**
> 手工逐字节拆装（`put_u32_le` / `put_u16_le`），
> **字节布局由我说了算** —— 这也是 PC 端能独立解析的前提。

**加分点**：所有字段**小端存放，与 STM32 原生字节序一致，不需要转换**。
`CRC-16/MODBUS` 存储也是**低字节先发**（这跟 Modbus 在线路上的习惯一致，
跟 BLE 项目里 CRC16-ARC 的大端存储正好相反 —— 这是最容易想当然写错的地方）。

### Q24. NOR Flash 有哪两条铁律？

**一句话答案**：

**① 位只能 1→0，写之前必须先擦扇区。**

```
擦除后： 1 1 1 1 1 1 1 1   (0xFF)
想写：   1 0 1 0 0 1 0 1
         ↓ 按位与
结果：   1 0 1 0 0 1 0 1   ✓

但如果之前是 0x0F： 0 0 0 0 1 1 1 1
再想写 0xA5：      1 0 1 0 0 1 0 1
         ↓ 按位与
结果：   0 0 0 0 0 1 0 1 = 0x05   ✗ 完全不对！
```

**最阴的地方**：不报错、不烧毁，只是数据悄悄不对。
你读回来发现 CRC 全失败，会先去怀疑 SPI 时序。

**② 擦/写之后必须轮询 BUSY 位。**

擦除典型 45 ms、最坏 400 ms，这期间芯片**只响应读状态寄存器**。
不等就发下一条指令 → 被**静默忽略**。

```c
/* 本工程：CS 全程保持低、只发一次 0x05，之后连续读状态字节
 * （数据手册推荐做法，比"每次重发 0x05"快得多）
 * 并且必须带超时 —— 嵌入式铁律"永不无限阻塞" */
return (sr & SR1_BUSY) ? 1U : 0U;   /* 1 = 超时未完成 */
```

### Q25. 断电后你怎么找到上次写到哪了？

**一句话答案**：上电时逐槽位扫，遇到第一个**不是有效记录**的槽位就停：

- 是 **EMPTY（全 0xFF）** → 写指针 = 这个槽位（可以直接编程）
- 是 **HALF / UNFINISHED** → 写指针 = **下一个**槽位

**追问：为什么要跳过而不是重写？**
> 因为 **NOR Flash 位只能 1→0**，这个槽位里已经有残数据，不擦整个扇区就写不回去。
> 而为了一个 32 字节的残记录去擦 4 KB 扇区，会丢掉这一扇区里其它 127 条好记录。
> **跳过它只损失 32 字节** —— 这是顺序追加型日志最划算的取舍。

**追问：扫描会不会很慢？**
> 做了两级：**页级粗扫**（只看每页第一条，8 倍快）+ **条级精扫**（只在一页内找）。
> 满容量 131072 条最坏也就 16384 次单字节读量级。

**加分点（讲这个 bug 很值）**：
> 精扫时**必须从 page−1 页开始**。
> 因为粗扫的判据是"页的第 1 条是否为空" ——
> 如果某页**只写了前几条就断电**，这页的第 1 条仍是有效记录，
> 粗扫会认为它"写过"从而跳到下一页，但这一页后面还有空槽。
> **不回退就会在 Flash 里留下一个永久空洞**，回读自检会报这些空洞 CRC 错。
> 修法是精扫时回退一页，最多多读 8 条。

### Q26. CRC 能不能分段计算？

**一句话答案**：能。CRC 是**流式（有状态）算法**：`crc(A+B) = update(crc(A), B)`。
本项目的尾 CRC 就是这么省的：

```c
head_crc = crc16_modbus(buf, 28);                    // 头 CRC：覆盖 0–27
put_u16_le(&buf[28], head_crc);
put_u16_le(&buf[30],
           crc16_modbus_update(head_crc, &buf[28], 2));  // 尾 CRC：续算 2 字节
```

`crc16(buf, 30)` ≡ `update(crc16(buf, 28), buf+28, 2)` —— 数学上完全等价，
而且这样写把"**尾 CRC 包含了头 CRC**"直接写在代码里了。

### Q27. ⚠️ 你怎么证明"存进 Flash 的字节是对的"？

**一句话答案**：分三层，每层证明的范围不同：

| 证据 | 证明了 | ❌ 没证明 |
|---|---|---|
| 串口打出的 HEX 行 | 打包正确 + UART 传输正确 | ❌ 写进 Flash 的字节对不对 |
| 板子自己的命令 `v` 报 OK | 板子**自己**前后一致 | ❌ 打包函数有没有把字段放错位置 |
| **PC 端 `parse_records.py`** | **整条链路上字节一个都没被改过**（独立实现重算） | — |

**追问：为什么"只比 CRC"不够？**
> CRC 只证明"**字节没变**"。万一打包函数把字段放错了位置
> （比如温度写在湿度的位置上），CRC 依然全对。
> 所以我的自检做了**三重比对**：① 双 CRC 状态 ② 序号/时间戳 ③ 温湿压。

**追问：PC 端为什么能独立校验？**
> 因为记录格式是**手工逐字节定义**的，不依赖编译器。
> 我把同一套格式在 Python 里重写了一遍（`tools/multibus.py`），
> 并且用 CRC 界的**标准检查值**钉住算法一致性：
> ASCII `"123456789"` 在 CRC-16/MODBUS 下必须是 **`0x4B37`**。
> 固件开机横幅会打这一行，PC 端 `--selftest` 也打 —— 对得上才继续。

## 通用问题

### Q28. 为什么"全程寄存器手写"而不用 HAL？

**一句话答案**：三个理由：

1. **学得深**：HAL 把 `RCC->CFGR`、`FLASH->ACR` 这些细节封起来了，
   用 HAL 你不需要知道"72 MHz 要 2 个等待周期"。
   但面试问"你怎么配时钟树的"，答"CubeMX 点的"和答出推导过程是两个层次。
2. **代码小**：本项目 Flash 只用了 **27.4 KB / 64 KB**。
   如果用 HAL + CubeMX 生成的外设代码，光 HAL 驱动就吃掉十几 KB。
3. **可控**：HAL 的某些实现有隐藏行为（比如超时、回调链），
   出问题时你要穿三层才知道发生了什么。

**追问：那实际工作你会用手写吗？**
> **不会。** 实际项目里 HAL/LL 库是**工程效率的正确选择** ——
> 换型号时移植成本低、团队协作有统一约定。
>
> 我手写是为了**理解底层**，这个理解反过来让我用 HAL 时也知道它在干什么、
> 出了问题该往哪看。**这是一个学习手段，不是工程主张。**

> ⚠️ **这个"追问"很重要**：如果只答"手写更好"，会显得不懂工程。
> 要主动说出"实际产品会选 HAL"，这才是成熟。

### Q29. 你这个项目一共用了多少资源？

**一句话答案**（记住这三个数）：

| 项 | 数值 |
|---|---|
| Flash | **26.8 KB / 64 KB（42%）** |
| RAM | **11.4 KB / 20 KB（57%）** |
| 主频 | **72 MHz**（HSE 8 MHz × PLL9） |

**追问：RAM 怎么分的？**
> - FreeRTOS 堆 **9216 B**（任务栈 + TCB + 队列 + 互斥锁都从这里分）
> - 链接脚本保留 **1536 B**（C 库堆 512 B + 主栈 1 KB）
> - 其它 `.bss` 约 **936 B**（记录缓冲、自检批缓冲、校准系数…）
>
> **主栈那 1 KB 只服务两件事**：① 复位到调度器启动前的启动代码；
> ② **所有中断服务程序**。任务栈是另一回事 —— 从 FreeRTOS 堆里分。
> **两笔账分开算，这就是链接脚本里为什么要留 `_Min_Stack_Size`。**

### Q30. 如果让你继续做这个项目，下一步做什么？

**一句话答案**（按性价比排）：

1. **加 CAN 节点**（32% 的 JD 要求；文档里"三总线"升级成"四总线"）；
2. **Modbus-RTU 从站**（工业领域硬通货）；
3. **用 Linux 开发板补驱动**（56% 的 JD 要求，是我最大的缺口，
   代价是天花板约 12–20K，进不了 20K+ 那一档）；
4. SD 卡 + FatFs 做第二条存储线（拔下来直接看）。

**追问：为什么现在不补 Linux？**
> 因为秋招窗口期就在眼前，从零到"能写上简历"需要 1 个月，
> 会挤掉面试准备。**这是一个有意识的取舍，不是遗漏。**
