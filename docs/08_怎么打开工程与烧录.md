## 1. 为什么当初 CubeIDE "打不开"它（现在已经补上了）

你右键 `STM32F103C8TX_FLASH.ld` 找不到"用 CubeIDE 打开"，**两个原因叠加**：

**原因一：`.ld` 根本不是"工程文件"。**
它是**链接脚本**（Linker Script），告诉链接器"Flash 从 `0x08000000` 开始、共 64 KB、栈放哪儿"。
就是一份**给链接器读的纯文本配置文件**，用记事本都能打开。它本来就不该有"打开方式"。
类比：这相当于对着说明书里的"装订说明"那一页，问"为什么不能用 Word 打开这本书"。

**原因二：`firmware\` 当时没有 CubeIDE 认的工程描述文件。**

CubeIDE 认不认一个文件夹，只看它里面有没有这两个文件：

| 文件 | 作用 | `rtos_logger\` | `firmware\`（当时） | `firmware\`（现在） |
|---|---|---|---|---|
| `.project` | Eclipse 工程描述（"我是一个工程"） | ✅ 有 | ❌ 没有 | ✅ **已补** |
| `.cproject` | 编译配置（编哪些文件、什么选项） | ✅ 有 | ❌ 没有 | ✅ **已补** |
| `.settings\` | 编码、索引器设置 | ✅ 有 | ❌ 没有 | ✅ **已补** |
| `Makefile` | 命令行编译脚本 | ❌ 没有 | ✅ 有 | ✅ 保留 |
| `.mxproject` / `.ioc` | CubeMX 图形配置 | ✅ 有 | ❌ 没有 | ❌ **仍没有（故意的）** |

```
<另一个 CubeIDE 工程>\        <工程目录>\  (现在)
    .cproject                              .cproject        ← 新补
    .mxproject                             .project         ← 新补
    .project                               .settings\       ← 新补
    rtos_logger.ioc                        Makefile         ← 保留
    STM32F103C8TX_FLASH.ld                 STM32F103C8TX_FLASH.ld
                                           Core\ docs\ tools\ ...
```

**为什么仍然没有 `.ioc`？** 因为它是**故意不放**的 —— 详见 `docs\09_用CubeIDE开发与调试.md` 第 6 节。
简单说：这个工程是寄存器手写的，放个 `.ioc` 进去，一旦点了 "Generate Code"，
CubeMX 会按图形配置**重新生成 `main.c`**，把手写代码覆盖掉。

- `rtos_logger` = **CubeMX 生成的 IDE 工程** → CubeIDE 双击就进
- `firmware` = **纯 Makefile 工程**（故意做成这样的，见下）→ 对 CubeIDE 来说就是个普通文件夹

**当时为什么先做成 Makefile 工程？**
因为它能**用命令行编译**，我才能在你拿到手之前**真的编译一遍验证**（已通过：零错误零告警，Flash 26.8 KB / RAM 11.4 KB）。如果一开始就只有 CubeIDE 工程，我只能给你一堆文件让你自己点，编不过你也不知道是哪儿的问题。

**现在两种都支持** —— `Makefile` 保留着（命令行可编译、可验证），
再叠加上 CubeIDE 的 `.project` / `.cproject`（`Ctrl+B` 可编译、可单步调试）。
源码是同一份，见 `docs\09_用CubeIDE开发与调试.md` 第 3 节讲两者的差异。

> 类比：原来是**一摞打好顺序的散页 + 一份装订说明**（内容完整，但 CubeIDE 不认这个装订方式）；
> 现在是**同一摞散页，同时给了两种装订方式** —— 装订说明（Makefile）和书的封面目录（`.project`/`.cproject`）。

**顺带说清 `.ld` 是什么：**
`STM32F103C8TX_FLASH.ld` = **Linker Script，链接脚本**。它告诉链接器"Flash 从 0x08000000 开始、共 64 KB、栈放哪儿"。就是一份**给链接器读的配置文件**，用记事本都能打开看。**双击它打不开是正常的。**

## 2. 你的板子现在的实测状态（我刚连上去查的）

**不用你动手，我直接用 CubeProgrammer 连了一次（只读，没改任何东西）：**

```
ST-LINK SN  : 57FF68068389495630590867
ST-LINK FW  : V2J46S7
Voltage     : 3.18V               ← 板子供电正常
Device ID   : 0x410
Device name : STM32F103 Medium-density
Device CPU  : Cortex-M3
Flash size  : 128 KBytes
```

| 项 | 实测值 | 说明 |
|---|---|---|
| 克隆版 ST-Link | **能用** | CubeProgrammer v2.14 完全认它，不需要 Zadig 刷驱动 |
| 板子电压 | 3.18 V | 供电正常 |
| 芯片识别 | **通过** | Device ID `0x410` = STM32F103 中容量 |
| 串口 | **COM8**（CH340） | 这就是你的调试串口，115200-8-N-1 |
| 芯片里当前的程序 | **有一个** | 复位向量 = `0x08002388`（大概是你之前烧的阶段 0 固件） |

### ⚠️ 一个值得记下来的发现：Flash 实际是 128 KB

我读了你芯片内部的**容量寄存器 `0x1FFFF7E0`**，读回来的值是：

```
0x1FFFF7E0 : FFFF0080
              ↑↑↑↑ ↑↑↑↑
              低 16 位 = 0x0080 = 128  → 128 KB
```

**你的芯片标称 STM32F103C8T6（64 KB），但物理上是 128 KB。**

这是**正常现象**：C8 和 CB 是同一块晶圆（die），出厂时按测试结果分档。很多后期/国产的 C8T6 实际就是 CB 的芯片。CubeProgrammer 也会自报 `Flash size: 128 KBytes`。

**那为什么工程还是按 64 KB 编？**
因为**按 64 KB 预算做**才能保证换到一块"真·64 KB"的 C8T6 上也能跑。这是更有说服力的说法：

> 面试时你可以说：「我的链接脚本按 64 KB 约束，实测占用 26.8 KB（42%）。
> 我还发现手上这块 C8T6 的容量寄存器报 128 KB —— C8/CB 是同 die 分档，
> 但我不依赖这个余量，保证代码在任何标称 C8T6 的板子上都能跑。」

这句话能同时证明**你真上手摸过硬件**、**你懂芯片分档**、**你有工程冗余意识**。比背概念强得多。

## 3. 路线 A：命令行烧录（不进 CubeIDE）

### 前提
- 板子插着（**已经插着了**，我刚连上）
- ST-Link 的 SWD 四根线接好（SWDIO / SWCLK / GND / 3.3V）
- **已经编译过**（CubeIDE 里 `Ctrl+B`，或命令行 `make`）

### ★ 先搞清楚要烧哪个文件

这个工程有**两套构建方式**，产物在两个不同目录：

| 你在哪儿编译 | 产物 | 能烧吗 |
|---|---|---|
| CubeIDE（`Ctrl+B`） | `Debug\firmware.elf` | ✅ 能（`.elf` 自带地址信息） |
| 命令行 `make` | `build\fw.hex` | ✅ 能 |
| — | CubeIDE **不产出 `.hex`**，这是正常的 | — |

⚠️ **陷阱**：如果你在 CubeIDE 里编译完，却去烧 `build\fw.hex`，
烧进去的是**上一次 `make` 的旧版本** —— 现象是"代码改了却没生效"，非常难查。

**`tools\run.py` 第 8 项已经自动处理了这件事**（列出所有产物让你选 + 提示源码比固件新）。
所以**推荐直接用菜单**；手工敲命令的话请自己确认路径。

### 命令（一条，直接复制）

下面这条烧的是 **CubeIDE 的产物**（你去 CubeIDE 编译过就用这条）：

```cmd
"<CubeIDE 安装目录>\STM32CubeIDE\plugins\com.st.stm32cube.ide.mcu.externaltools.cubeprogrammer.*\tools\bin\STM32_Programmer_CLI.exe" -c port=SWD freq=4000 -d "<工程目录>\Debug\firmware.elf" -v -rst
```

如果只有 `make` 构建的产物，把上面 `Debug\firmware.elf` 换成 `build\fw.hex` 即可。

**参数逐个解释：**

| 参数 | 意思 | 为什么这么写 |
|---|---|---|
| `-c port=SWD freq=4000` | 用 SWD 口连，时钟 4 MHz | 4 MHz 对克隆 ST-Link 最稳；调快了容易连不上 |
| `-d <file>` | Download，把文件写进芯片 | **`.hex` 和 `.elf` 都自带地址信息**，所以不用像 `.bin` 那样写 `0x08000000` |
| `-v` | Verify，写完回读比对 | **一定要加**。不加就只是"写进去了"，不保证写对 |
| `-rst` | Reset system（软复位） | 让新程序立刻开始跑 |

**期望输出**（关键几行）：

```
Memory Programming ...
Download verified successfully
...
Software reset is performed
```

看到 `Download verified successfully` + `Software reset is performed` 就是**烧成功且已复位启动**。

### 更省事的办法：用菜单

```cmd
python tools\run.py
```

选 **8（烧录固件）**，它会自动找到 CubeProgrammer、把命令打出来让你确认、烧完还问你要不要立刻开串口看。**不用记上面那串长路径。**

## 4. 烧完怎么确认程序真的在跑

**这一步是必须的 —— 烧录成功 ≠ 程序在跑**（这个坑你之前踩过，见下面第 6 节）。

### 4.1 接串口看输出

- 串口：**COM8**（CH340）
- 参数：**115200，8 数据位，无校验，1 停止位**（115200-8-N-1）
- 接线：CH340 的 **RX 接板子 PA9（TX）**，**TX 接板子 PA10（RX）**，GND 对 GND
  （**TX/RX 要交叉** —— 两边都叫 TX 的话谁都收不到）

### 4.2 你应该看到这一串（开机横幅）

```
========================================================
 多总线数据采集终端  |  STM32F103C8T6 寄存器裸机 + FreeRTOS
 I2C(BME280) + SPI(W25Q64) + UART(printf/命令) 三总线
========================================================
#CLK,got:  SYSCLK=72000000 HCLK=72000000 PCLK1=36000000 PCLK2=72000000
#CLK,expect: SYSCLK=72000000 HCLK=72000000 PCLK1=36000000 PCLK2=72000000
#CLK,APB1上限=36000000 —— 上面 PCLK1 超过它就会外设时好时坏
#UART,BRR=625 (expect 625 = 0x271, baud=115200 err=0%), DWT=ok
#BUILD,APP_MUTEX_ENABLE=1,APP_STACK_MEASURED=0,...
#CRC,check='123456789',got=0x4B37,expect=0x4B37,PASS
#CMD,发送 h 查看命令表
[boot] 记录区已存 N 条 / 容量 ...
[boot] 启动 FreeRTOS 调度器 ...
```

**四个必须核对的点：**

| 行 | 看什么 | 对了说明什么 |
|---|---|---|
| `#CLK,got:` | 四个数字和下一行 `expect` **完全一致** | **72 MHz 时钟树真的配成了**（不是"我写了就当它是"） |
| `#UART,BRR=` | `625`，且 `DWT=ok` | BRR 按 72 MHz 算对了；微秒延时可用 |
| `#CRC,...,PASS` | **PASS** | 固件的 CRC 和 PC 端是同一套算法 —— 后面所有校验的前提 |
| 之后每秒一行 | 周期性的采集/上报 | 调度器起来了，三任务在跑 |

**只要 `#CRC` 那行是 PASS，你就可以去跑 `tools\run.py` 的第 7 项对答案**（PC 端也应算出 `0x4B37`）。

### 4.3 不想开串口助手？用菜单

`python tools\run.py` → 选 **8** 烧录 → 烧完它会问你要不要立刻开串口；或者直接选 **6**（W4 全量自检）等任意一项，都会抓串口并存到 `firmware\logs\`。

## 5. 路线 B：搬进 `rtos_logger` 工程（现在一般不需要了）

> 📌 **2026-09-17 更新**：`firmware\` 自己已经是 CubeIDE 工程了（见 `docs\09`），
> 所以**你多半不需要再往 `rtos_logger` 里搬**。这一节保留给两种情况：
> ① 你想把两个工程合并成一个；② 你想在 `rtos_logger` 那个你更熟悉的环境里开发。
> **搬之前先把整个 `rtos_logger` 复制一份备份。**

**目标**：把 `firmware\Core` 的源码搬进你已有的 `<另一个 CubeIDE 工程>\`。

**逐步操作见 `docs\07_同步回CubeIDE工程.md`**，这里只强调最容易翻车的一点：

> ### ⚠️ 必须把 CMSIS_RTOS_V2 从编译里排除
>
> 你原来的 `rtos_logger` 用的是 **CMSIS-RTOS2 包装层**（`cmsis_os2.c`），
> 而 `firmware\` 用的是 **FreeRTOS 原生 API**。
> 两者**都会定义 `SysTick_Handler` / `PendSV_Handler` / `SVC_Handler`**
> → 链接时**重复定义报错**，而且报错信息会指向启动文件，看起来像启动文件坏了。
>
> 在 CubeIDE 里：右键 `Middlewares\Third_Party\FreeRTOS\Source\CMSIS_RTOS_V2` → **Exclude from build**。

搬之前建议**先备份整个 `rtos_logger` 文件夹**（复制一份改名 `rtos_logger_backup`）。

## 6. 三个已知的坑（都踩过，先看再动手）

### 坑 1：烧录成功但程序不跑 —— 复位后内核可能停在暂停态

**症状**：CubeProgrammer 报 `Download verified successfully`，但串口一个字都没有、LED 不闪。

**根因**：调试器复位后，内核可能**停在暂停状态**，程序根本没被执行。这不是代码问题。

**解决（按可靠性排序）**：

1. **拔掉 USB 再插上**（真正断电重上电）→ 芯片独立自动运行。**这是最可靠的验证方式**，也是"程序能不能脱离调试器独立跑"的唯一标准。
2. 或者命令行显式启动：
   ```cmd
   :: ① 读向量表，第 2 个字就是复位向量
   "...\STM32_Programmer_CLI.exe" -c port=SWD freq=4000 -r32 0x08000000 8
   :: ② 用 -g 启动（注意：复位向量末位是 1，是 Thumb 标志，要清掉）
   "...\STM32_Programmer_CLI.exe" -c port=SWD freq=4000 -g <复位向量 & 0xFFFFFFFE>
   ```
   比如烧完之后读出来是 `0x080003C5`，那 `-g 0x080003C4`。

**判断依据**：用 **DWT 或串口输出**判断程序跑没跑，**不要**用"读外设寄存器"判断（SWD 连接本身会软复位、把外设寄存器清回复位值，看到复位值不等于程序没跑）。

### 坑 2：串口被别的程序占用

打开着串口助手 / CubeIDE 的 Terminal，`tools\run.py` 就抓不到串口，报 `PermissionError`。

**串口一次只能被一个程序打开。** 抓包前先关掉串口助手。

### 坑 3：CubeIDE 抢着连 ST-Link

CubeIDE 开着调试会话时，CubeProgrammer 会报 `No ST-LINK detected` 或连接失败。

**先关掉 CubeIDE 的调试会话（或整个 CubeIDE）**，再烧。

## 附：CubeProgrammer 命令行速查（都是只读的，不会改芯片）

```cmd
set CLI="<CubeIDE 安装目录>\STM32CubeIDE\plugins\com.st.stm32cube.ide.mcu.externaltools.cubeprogrammer.*\tools\bin\STM32_Programmer_CLI.exe"

%CLI% --list                  :: 列出所有 ST-Link / 串口
%CLI% -c port=SWD             :: 只连接，读芯片型号、电压、Flash 容量
%CLI% -c port=SWD -r32 0x1FFFF7E0 1   :: 读 Flash 容量寄存器
```

> `-r32 <地址> <字数>` 是**读**，不会改任何东西。
> 这四个命令在你怀疑"板子到底有没有连上""芯片到底是不是好的"时特别有用 ——
> 它们能把"猜"变成"读数"。
