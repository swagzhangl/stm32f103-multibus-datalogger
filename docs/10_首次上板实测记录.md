### 为什么"时钟自证"这一条特别硬

`#CLK,got:` 那四个数字**不是宏，是从 `RCC->CFGR` 的 SWS / PLLMUL / PPRE 位现算出来的**。
所以"我写了 72 MHz"和"它真的跑在 72 MHz"是两件事，这行输出证明的是后者。
`#CLK,expect:` 紧跟在下一行，是为了让核对变成"两行对不对得上"而不是"我记得应该是多少"。

### 为什么"三者同时合理"是个强证据

温度 27.32 ℃、湿度 61 %RH、气压 1010 hPa —— **三个量同时落在合理区间**，
说明 BME280 的 33 个出厂校准系数读对了、Bosch 整数补偿公式跑对了。
如果系数读错或公式算错（比如气压用了 32 位而不是 64 位中间量导致溢出），
数值会明显离谱或全 0，不会三个都正常。

但要说清楚边界：
> **这只能证明"数值合理"，不能替代"PC 端独立复算逐位一致"。**
> 后者是简历原话，必须真跑一遍 `tools/run.py` 第 3 项才算做实。

### 已知显示问题（**已排除固件原因**）

输出里有两行被截断在中文中间（`…上�`、`0 �`）。**不是固件的问题**，依据：

`uart_dbg_byte()` 的实现是纯轮询，没有环形缓冲、没有超时丢弃分支：

```c
void uart_dbg_byte(uint8_t b)
{
    while ((USART1->SR & USART_SR_TXE) == 0U) { }   /* 等发送寄存器空 */

```

`uart_dbg_str()` 也只是 `while (*s) uart_dbg_byte(*s++);`。
**每个字节必定写入 DR，固件侧不存在截断路径。**

→ 截断发生在**接收端**：串口助手的显示 / 复制。

`recorder_capacity()` 与 W25Q64 的容量识别（4 MiB ÷ 32 B = 131 072）。

### 原始输出（用户提供，逐字保留）

```
#CHIPID,0x60,BME280(有湿度)
#CALIB,T1=28399,T2=26637,T3=50,P1=37164,P2=-10691,P3=3024,P4=6764,P5=30,P6=-7,P7=11700,P8=-11800,P9=5000,H1=75,H2=368,H3=0,H4=305,H5=50,H6=30,count=33

```

### 判定一：器件识别正确 ✅

`#CHIPID,0x60` —— BME280 的 chip id 寄存器 `0xD0` 返回 `0x60`（若是 BMP280 会返回 `0x58`，
那就没有湿度通道）。这行同时证明了 I2C 地址（0x76 或 0x77）与上拉都对。

### 判定二：33 个系数全部落在典型区间 ✅

| 系数 | 实测 | BME280 典型范围 | 判定 |
|---|---|---|---|
| `T1` (uint16) | 28399 | 27500 ~ 28500 | ✅ |
| `T2` (int16) | 26637 | 26000 ~ 27000 | ✅ |
| `T3` (int16) | 50 | 0 ~ 100 | ✅ |
| `P1` (uint16) | 37164 | 36000 ~ 38000 | ✅ |
| **`P2` (int16)** | **−10691** | −10000 ~ −11000 | ✅ **负值** |
| `P3` (int16) | 3024 | ~3000 | ✅ |
| `P4` (int16) | 6764 | 6000 ~ 8000 | ✅ |
| `P5` (int16) | 30 | 20 ~ 40 | ✅ |
| **`P6` (int16)** | **−7** | −7 ~ 0 | ✅ **负值** |
| `P7` (int16) | 11700 | 11700 ~ 12000 | ✅ |
| **`P8` (int16)** | **−11800** | ~ −11800 | ✅ **负值** |
| `P9` (int16) | 5000 | 5000 ~ 6000 | ✅ |
| `H1` (uint8) | 75 | 75 | ✅ |
| `H2` (int16) | 368 | 340 ~ 370 | ✅ |
| `H3` (uint8) | 0 | 0（H3 是唯一按原始 ADC 存的，不参与线性拟合） | ✅ |
| `H4` (int16) | 305 | 300 ~ 400 | ✅ |
| `H5` (int16) | 50 | 50 | ✅ |
| `H6` (int8) | 30 | 30 | ✅ |

**为什么"三个负值"这一条最有价值：**

`P2` / `P6` / `P8` 是 int16（有符号），而 `T1` / `P1` / `H1` / `H3` 是 uint16（无符号）。
如果读取时**漏了符号扩展**，`P2 = −10691`（即 `0xD645`）会被当成 `54853`，
`P8 = −11800` 会变成 `53736` —— 都是足以让气压补偿算出荒谬结果的量级。

实测三个负值**符号正确**，说明：
1. 33 字节的分段读取（`0x88–0xA1` 共 26 B + `0xE1–0xE7` 共 7 B）没有错位；
2. 有符号/无符号的拆分（`(int16_t)` 强转）是对的；
3. `dig_H4/H5` 那种**跨字节拼装**（H4 是 12 位、H5 是 12 位，需要移位拼接）也拼对了。

**这是 W2 最容易被忽略、也最容易出错的一环，现在有实测证据了。**

### 判定三：`#CALIB` 打了两遍 —— 定性为**发送端重复**，不是固件问题

输出里 `#CALIB` 两次、`#CHIPID` 一次。查了三处代码把它定性清楚：

| 环节 | 代码位置 | 结论 |
|---|---|---|
| `c` 命令做什么 | `app_tasks.c:387` → `selftest_bme280_calib_dump()` | 该函数（`self_test.c:532-566`）**只打 `#CALIB`，不打 `#CHIPID`** |
| `#CHIPID` 谁打的 | `app_tasks.c:392-410`，只属于 `case 'i'` | 所以本次输出是**两个不同命令**的结果：`i` 发过一次、`c` 发过两次 |
| 命令解析会不会重复派发 | `app_tasks.c:501-521` | `if (n > 0U)` 守卫使得 `c\r\n` **只派发一次**（`\n` 到达时 `n` 已归零）。发 `c\r\n\r\n` 也只派发一次 |
| 接收中断会不会重复投递字节 | `uart_dbg.c:205-222` | 每次中断**只读一次 `DR`、最多 `rx_push()` 一次**，且只在 `RXNE` 置位时 push；`ORE` 只用于清标志不重复入队 |

→ **固件侧不存在"一次按键变两次命令"的路径。**
因此是**串口终端把一次发送重复送出了两次**（常见的双击发送 / 自动重发行为）。

**10 秒验证法**：只发一次 `c`，看回来几行 `#CALIB`。
- 一行 → 终端行为，正常，无视即可
- 两行 → 才需要进一步查（那时优先怀疑终端设置里的"自动重发/追加换行"）

### 判定四（顺带发现）：`e` 擦除命令存在数据丢失隐患 → **已修**

顺着"终端会重复发送"这条线查下去，发现原实现在**同一秒内的两次 `e`** 会直接执行擦除：

```c
/* 原来的判据 */
if ((s_erase_armed != 0U) && ((s_seconds - s_erase_arm_t) <= 15U))   /* dt=0 也满足 */
```

`并不精确`：`s_seconds` 由采集任务每秒自增，不是时钟。两次 `e` 落在同一秒时 `dt = 0`，
仍然满足 `<= 15` → **当场擦除**。
后果：终端重复发送一次，就等于**一次按键擦掉全部记录**（毕设实测数据）。

**已修**（`app_tasks.c` 的 `handle_erase()`）：

```c
#define ERASE_MIN_GAP_S   2U      /* 两次确认的最小间隔 */
#define ERASE_WINDOW_S   15U      /* 确认窗口 */
...
if (dt < ERASE_MIN_GAP_S)  → 回 #ERASE,TOO_SOON，保持待确认但不刷新计时起点
if (dt <= ERASE_WINDOW_S)  → 才真正执行
```

顺带补掉了另一处静默失败：原代码在**取不到 SPI 锁时什么都不打**，
会让人误以为"擦成功了"。现在回 `#ERASE,ERR,lock timeout（未执行）`。

编译验证：`make` 退出码 0、零错误零告警；Flash 27 400 → **27 604 字节**（+204 B），RAM 不变。

> ⚠️ **这次改动只在 `build/` 里**（`make` 的产物）。
> 你在 CubeIDE 里编的 `Debug/firmware.elf`（22:35）**不含**这个加固 —— 那是你当时烧进去的版本。
> 要生效需在 CubeIDE 里重新 `Ctrl+B` 再烧。**这正好是 `docs\09` 第 3 节讲的"两套产物不一致"陷阱的实例。**

## 记录 3 ｜ 2026-09-17 23:0x ｜ PC 端独立复算（简历第 3 条）—— 先 FAIL 后 PASS

### 第一次运行：FAIL，但**问题在 PC 脚本，不在固件**

抓取命令：`serial_capture.py --port COM8 --out ../logs/bme.txt --seq c,m,m,m,m,m --gap 2`
（日志已存 `firmware/logs/bme.txt`，2691 字节）

`verify_bme280.py` 第一次结果：

```
复算比对：共 30 项，其中不一致 10 项
结论：FAIL

样本 0:
  adc_T=538907 adc_P=341041 adc_H=29403
  湿度补偿原始返回 Q22.10     固件=56817    PC=3121    差 53696
  湿度 0.01%RH                固件=5548     PC=304     差 5244
```

**关键观察：温度、气压全部一致，只有湿度不一致。**

| | 固件 | PC 脚本 |
|---|---|---|
| 湿度 Q22.10 | 56817 → **55.49 %RH** | 3121 → **3.05 %RH** |

**55 %RH 是合理的**（广东九月的室内湿度），**3 %RH 物理上不可能**（那是沙漠）。
→ 判定**固件是对的，PC 端脚本错**。

### 根因：Python 运算符优先级（`multibus.py:240`）

```python
# ✗ 错的（原代码）
v = i32(v - i32(i32(i32((v >> 15) * (v >> 15)) >> 7) * c["H1"]) >> 4)
#        └────────────── 这个 >> 4 被 Python 解析到了整个减法之外 ──────────────┘

# C 的原文是：
#   v = v - ( ((((v>>15)*(v>>15)) >> 7) * dig_H1) >> 4 );
#                                     ↑ >> 4 只作用于【减数】
```

**Python 的 `-` 优先级高于 `>>`**（与 C 相同，但这里的括号把我自己骗了），
所以实际算的是 `(v - X) >> 4` 而不是 `v - (X >> 4)`。

手算复现（样本 0）：

| | 表达式 | 结果 |
|---|---|---|
| 正确 | `v - (X >> 4)` = 232,712,775，再 `>>12` | **56,814** |
| 实际 | `(v - X) >> 4` = 12,784,978，再 `>>12` | **3,121** ← 与报错值一字不差 |

**手算复现了报错的 3121，根因确认。**

修复后（移位写进被除数自己的括号）：

```python
corr = i32(i32(i32((v >> 15) * (v >> 15)) >> 7) * c["H1"])
v = i32(v - i32(corr >> 4))
```

```

**样本数 5 × 每个样本 6 个量（t_fine / temp_centi / press_q24_8 / press_pa / hum_q22_10 / humi_centi）= 30 项。**

### ⚠️ 必须记下的教训：之前那次"验证通过"是**假 PASS**

早先交付时写过"PC 端工具链已用假日志跑通：BME280 复算 18 项 0 不一致"。
**那句话不可信。** 原因：

> `make_sample_log.py` 造出来的假日志，是用 **`multibus.py`** 算的值；

### W4-1 四种 SPI 模式回环自测 —— ✅ PASS

```
#SPI4,Mode0,CPOL=0,CPHA=0,SCLK_idle=LOW, tx=0xA5,rx=0xA5,echo=MATCH

- **四模式全 MATCH** —— 这正是预期（单主机回环时收发同一模式，两者永远自洽），
  它证明的是**位引擎正确**（移位方向、MISO 通路、边沿计数），并**证明 PA7–PA6 短接有效**。

  这印证了 `docs\08` 第 5 节对执行计划的修正（回环自测本身看不到模式配对错误）。

### W4-2 四种模式读 W25Q64 JEDEC ID —— ⚠️ 与预测不符（读通 3 种而非 2 种）

```
#SPIID,Mode0,EF 40 17,OK
#SPIID,Mode1,FF FF FF,WRONG
#SPIID,Mode2,EF 40 17,OK
#SPIID,Mode3,EF 40 17,OK
#SPIID,读通模式数=3
```

**实测：Mode0 / Mode2 / Mode3 通，只有 Mode1 错。**

**这修正了我先前的预测**（`docs\08` 写过"Mode0/3 通、Mode1/2 错"）。

为什么 Mode2 也通 —— **目前只有推断，没有确证**，所以只列可能性、不下结论：

- Mode2 = CPOL=1（SCLK 空闲高）、CPHA=0（在第一个边沿采样 = **下降沿**）。
  而 W25Q64 在 SCLK **上升沿**采样输入、下降沿更新输出。
  理论上 Mode2 的采样沿与从机不匹配，应当错位。
- 但 bit-bang 实现里"产生边沿"与"采样"的**先后顺序**会改变实际行为：
  若代码是"先拉低 SCLK、再读 MISO"，那么读到的是**从机在下降沿刚更新完的新位**，
  行为恰好等价于 Mode0/3 的采样时刻 → 读对。
- 也就是说 **`CPHA` 的敏感性，在这个实现的 Mode2 路径上被"边沿顺序"掩盖了**。

**要讲清这一点，唯一的硬证据是逻辑分析仪**：抓 SCLK 空闲电平（对 CPOL）
与数据稳定沿（对 CPHA），四种模式逐一对照。**这正是简历第 2 条"逐帧验证"要求的东西。**

> 结论：`#SPIID` 作为"模式配对"的判据**有效但敏感度有限**（只抓出 Mode1）。
> 面试若被追问"你怎么证明四种模式都对"，**必须能拿出波形**，不能只拿 ID 读取数。

### W4-5 记录区全量回读校验 —— ❌ **FAIL（发现了真问题）**

固件自报：

```
#VERIFY,slots=1245,ok=1242,half=3,unfinished=0,bad=3,first_bad_idx=980,result=FAIL
```

PC 端用自己实现的 CRC **独立重算**（`parse_records.py` + `multibus.py`），结论一致：

```
#DUMP,begin,total=1246,size=32      ← 实际读到 1246 条 REC 行
PC 端逐条双 CRC：ok=1243, half=3, unfinished=0
头 CRC 失败的记录下标：980, 981, 982
```

**另有两条 seq 层面的异常：**

| 现象 | 数据 |
|---|---|
| seq 与槽位下标不一致的位置 | **266 处** |
| 重复的 seq | **seq=1024 出现 2 次**，位于下标 980 与 981 |
| 跳跃点 | idx 980→seq 1024、idx 981→seq 1024（重复）、idx 982→seq 1280、idx 983→seq 1320，之后恒差 **+337** |
| 末条 seq | **1585**，但记录只有 **1246** 条 → **缺约 337 条** |
| 时间戳 vs seq | 全部相等（0 处不一致） |

**已能解释的部分：`store=skip` 的含义**

`app_tasks.c` 里 `s.store_rc` 的**初值就是 `0xFF`**，而只有在**成功取到 SPI 锁之后**
才会被 `recorder_append()` 的返回值覆盖。所以 `store=skip` 同时覆盖两种情况：

1. 传感器读数无效（`s.used == 0`）
2. **SPI 取锁超时** —— 采集任务拿不到锁，干脆跳过这一条，而不是去破坏别人正在读写的总线

第 2 条解释了为什么**跑 `t` / `v` 这类长时间持锁的自检时会出现成片的 `store=skip`**
（实测 `v` 之后连续 3 秒都是 `store=skip`）。
→ **"记录条数 < seq 跨度"本身是设计内的取舍**：宁可留缺口，也不写坏数据。

**尚不能解释、必须继续查的部分：**

- **重复的 seq=1024**（两条记录带同一个序号）—— `s.seq` 每秒自增一次，
  正常路径上产生不出重复值。
- **下标 980–982 三条连续的头 CRC 失败**，且 981 那条的字节形态很特殊：
  湿度字段 = 0、头 CRC = `0x0000`、尾 CRC = `0xFFFF`。
- 已核实 **`recorder_scan()` 全程没有被调用过**
  （只被 `recorder_erase_all()` 调用，而本次从未发过 `e`），
  所以**写指针没有被重算过**；`s_wr_addr` 只会 +32 单调前进。
  这一点反而让上面的异常更难解释 —— 需要继续查。
