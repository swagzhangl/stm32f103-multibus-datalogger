# 11 · W4 实测暴露的三个缺陷与修复

> 时间：2026-09-17 晚　板子：STM32F103C8T6（72 MHz 寄存器裸机 + FreeRTOS）+ W25Q64 + BME280
> 触发动作：短接 PA7–PA6 跑 `t` 自检，再发 `r` 倒出记录区，PC 端逐条校验
> 结果：倒出 1246 条，PC 端判定 **ok=1243、half=3、unfinished=0**

这三个缺陷都不是"程序崩了"那种显性故障，而是**静默产生错误数据**。
如果没做 PC 端独立校验，它们会被当成"Flash 有点脏"糊过去。

---

## 0. 先给结论

| # | 缺陷 | 性质 | 实测证据 | 后果 |
|---|---|---|---|---|
| 1 | `delay_now_us()` 回绕周期算错 | **实现 bug** | `uart_hold_us=4235319666`（真实约 4700 µs） | 假超时 → 写指针不推进 → 同一槽位写两次 → 按位与 → **半写记录** |
| 2 | 尾 CRC 退化成常数 | **数学必然的设计缺陷** | 1246 条里 1245 条尾 CRC = `0x0000`；改初值后仍恒为 `0x4FFE` | 尾 CRC 不含任何信息，"双 CRC 双保险"是假的 |
| 3 | 写失败后不推进写指针 | **健壮性缺陷** | idx 980/981/982 的 seq 是相邻序号按位与的结果 | 一旦发生失败就必然产生脏数据 |

三者是串在一条因果链上的：**1 触发 3，3 产生脏数据，2 让脏数据的危害被低估**。

## 1. 缺陷 1：`delay_now_us()` 的回绕周期

### 现象

串口 `s` 命令打出：

```
#STK,...,uart_hold_us=4235319666
```

一把串口互斥锁被"持有 4235 秒"是不可能的。真实值约 4.7 ms。

### 根因

```c
uint32_t delay_now_us(void) { return DWT->CYCCNT / s_cycles_per_us; }   /* 72 MHz → /72 */
```

`DWT->CYCCNT` 是 **32 位周期计数器**，每 `2^32` 个**周期**回绕一次。
72 MHz 下换算成微秒是 **`2^32 / 72 = 59 652 323 µs ≈ 59.65 s`**，
**不是** `2^32 µs`。

而原代码到处写：

```c
if ((delay_now_us() - t0) >= timeout_us) { break; }   /* ✗ */
```

"无符号减法天然能跨回绕"这句话**只在计数器铺满整个 2^32 值域时才成立**。
本计数器只用到 `0 … 59 652 322`，跨过回绕点后：

```
now - t0 = 4670 - 59 652 300 = -59 647 630
         ≡ 4 235 319 666   (mod 2^32)          ← 与实测值一字不差
```

反推真实间隔：`4294967296 − 4235319666 = 59 647 630`，
`59 652 323 − 59 647 630 = 4693 µs` —— **真实只持锁 4.7 ms**。

### 后果链（这是最要命的一环）

```
跨回绕 → (now - t0) ≈ 4.2e9 ≥ timeout → wait_busy() 第一次轮询就 break
      → w25q64_page_program() 返回 4（判为失败）
      → recorder_append() 直接 return，【s_wr_addr 不推进】
      → 下一秒采集又往同一个地址写一遍
      → NOR Flash 只能 1→0，落下去的是【旧值 & 新值】
      → 头 CRC 失败 → 半写记录
```

`wait_busy()` 里那句注释"无符号减法跨回绕安全"当时是**想当然写上去的** ——
这是本项目里唯一一处"注释比代码更危险"的地方。

### 修法

新增 `delay_elapsed_us(t0)`，显式按真实周期处理：

```c
uint32_t delay_us_period(void) { return 0x100000000ULL / s_cycles_per_us; }   /* 59652323 */

uint32_t delay_elapsed_us(uint32_t t0)
{
    uint32_t now = delay_now_us();
    return (now >= t0) ? (now - t0) : (delay_us_period() - t0) + now;
}
```

调用点全部改掉：`w25q64.c` 的 `wait_busy()`、`log.c` 的持锁统计。
`delay_us()` 内部那句 `(DWT->CYCCNT - start) < ticks` **是对的**，不用改 ——
它比较的是原始 CYCCNT（真 32 位），不是换算后的微秒。

## 2. 缺陷 2：尾 CRC 退化成常数

### 现象

PC 端逐条重算，发现：

```
1246 条记录里，1245 条的尾 CRC 存值 = 0x0000
并且 crc16_modbus(记录[0:30]) 也恒等于 0x0000
```

### 第一层原因：CRC 的"追加性质"

原实现：

```c
尾 = crc16_modbus_update(头CRC, buf+28, 2);      /* 覆盖 0–29 */
```

CRC-16/MODBUS（init=0xFFFF、refin/refout=1、xorout=0）满足：
**把一段数据的 CRC 追加到数据后面再算一次，结果恒为 0x0000。**
这是 Modbus RTU 帧校验能被"整帧算一遍得 0"验证的原理，本来是优点，
用在这里就成了陷阱。

### 第二层原因：换初值也救不回来（关键）

第一反应是"换个初值重算"，于是改成 `init = 0x0000` 覆盖 0–29 重算。
**结果尾 CRC 仍然恒定，只是换成了 `0x4FFE`。**

推导一下就明白为什么。CRC 对初值是**仿射**的：

```
crc_J(m) = crc_0(m) ⊕ g_len(J)        g 是线性函数
```

于是：

```
尾 = crc_J(数据 ‖ 头CRC)
   = crc_0(数据 ‖ 头CRC) ⊕ g_30(J)
   = g_30(0xFFFF) ⊕ g_30(J)          ← 头 CRC 满足自身校验，"吃掉"了数据
   = g_30(0xFFFF ⊕ J)                ← 与数据【完全无关】
```

两次实测都符合这个公式：

| 尾 CRC 初值 J | 尾 CRC 实测值 |
|---|---|
| `0xFFFF`（原实现，从头 CRC 续算） | 恒 `0x0000` |
| `0x0000`（中途改过） | 恒 `0x4FFE` |

### 结论（这条比 bug 本身更有价值）

> **只要第二条 CRC 的覆盖范围 =「数据 + 第一条 CRC 的输出」，
> 并且用的是同一个多项式，那它必然退化成常数。**
> 这与初值、字节序、实现细节都无关，是 CRC 代数结构的必然结果。

也就是说，常见写法"头 CRC 校验数据、尾 CRC 校验数据+头 CRC"**在数学上是错的**。
它退化之后只剩"写完没写完"这一个作用 —— 等价于一个 2 字节固定标记，
不是校验值。功能上还勉强能用（0x0000 vs 擦除态 0xFFFF 能区分），
但"双 CRC 双保险"这个说法站不住。

### 修法

**换多项式**，而不是换初值：

| 字段 | 算法 | 覆盖范围 |
|---|---|---|
| 头 CRC | CRC-16/MODBUS（poly 0xA001，反射） | 0–27（数据区） |
| 尾 CRC | **CRC-16/CCITT-FALSE（poly 0x1021，不反射）** | 0–29（数据区 + 头 CRC） |

覆盖范围不变（尾仍然覆盖头 CRC，语义保住了），但换掉多项式就打破了上面的恒等式。

修复后实测（6 条不同内容）：

```
#0  头CRC=0x386B  尾CRC=0x1308
#1  头CRC=0x7024  尾CRC=0xFDAD
#2  头CRC=0xCB57  尾CRC=0xFEE0
#3  头CRC=0xD8CF  尾CRC=0x3207
#4  头CRC=0xC634  尾CRC=0x4985
#5  头CRC=0x33DF  尾CRC=0x89A4     ← 尾 CRC 各不相同，不再退化
```

CCITT 实现的正确性用公认检查值钉住：`crc16_ccitt("123456789") = 0x29B1`。
固件开机横幅新增一行 `#CRC2,tail_algo=CCITT-FALSE,...,expect=0x29B1,PASS`，
PC 端 `tools/crc16_modbus.py --selftest` 能打出同一个值。

### ⚠ 破坏性变更

旧记录的尾 CRC 是 `0x0000`，在新固件下会被判成"未收尾"。
**刷本版固件后必须先清空记录区（串口发两次 `e`），再重新开始长跑。**
上电扫描会跳过那个坏槽，不会崩，但计数会乱。

## 3. 缺陷 3：写失败后不推进写指针

### 现象

三条坏记录在 **idx 980 / 981 / 982**，解析出来的 seq 是：

```
idx=980   seq=1024
idx=981   seq=1024      ← 重复
idx=982   seq=1280
```

`1024 = 0x400`、`1280 = 0x500`。而相邻序号按位与正好能得到它们：

```
0x400 & 0x401 = 0x400     (1024 & 1025 = 1024)
0x401 & 0x402 = 0x400     (1025 & 1026 = 1024)
0x500 & 0x501 = 0x500     (1280 & 1281 = 1280)
```

**这是"同一个槽位被写了两次"的铁证**：低几位被后面的写入清零了。

### 修法（两层）

1. **写之前先确认槽位是擦除态**（全 `0xFF`），不是就跳过：
   ```c
   recorder_read(s_wr_addr / REC_SIZE, probe);
   if (recorder_slot_state(probe) != REC_SLOT_EMPTY) { slot_abandon(); return 6U; }
   ```
2. **任何一次页编程失败，都把该槽位永久作废并前移写指针**：
   ```c
   static void slot_abandon(void) { s_wr_addr += REC_SIZE; s_count++; }
   ```

这样即使将来再出现任何意外（不只是这个回绕 bug），
也**不可能**再往写过的槽位写第二遍 —— 从结构上消灭了按位与。

## 4. 顺带修掉的：`e` 命令的确认窗口

排查过程中发现 `e`（清空记录区）的两次确认判据是 `dt <= 15`，
而 `dt = s_seconds - s_erase_arm_t` 用的是采集任务的**软秒计数**，
同一秒内到达的两次 `e` 算出 `dt = 0`，**仍然满足 `<= 15`** → 当场擦除。

叠加"串口终端会重复发送"这个现象（实测 `#CALIB` 打过两遍），
等于**一次手滑就擦掉全部长跑数据**。已加固为：
- 两次确认最小间隔 2 秒（`ERASE_MIN_GAP_S`）
- 太快时不刷新计时起点（防止随手重发一直"续命"）
- 取不到 SPI 锁时明确回 `#ERASE,ERR,lock timeout（未执行）`，不再静默

# 6 · 第二次长跑（11.6 h）的发现：防护起效了，但暴露了擦除逻辑的洞

> 时间：2026-09-18 00:24 ~ 11:52　uptime 41938 s = **11.65 h**
> 结果：**41266 条倒出，`records` 在全部 21 个采样点都严格等于 `uptime − 674`**
> —— **采集层零丢失**。但 PC 端校验：OK=28537，**HALF=12726**，UNFINISHED=3

## 6.1 先说结论：12726 条"半写"不是写坏，是**旧格式残留被正确跳过**

异常区段 **idx 3840 ~ 16567**（共 12728 条），看它的原始字节：

```
idx=16565  A56AA40A9E8A01004417CA321900933A A56BA40A9D8A01004517B23619003904
idx=16566  A56CA40A9E8A010046179A3A19000BDC A56DA40A9D8A01004417823E1900BFD1
idx=16567  A56EA40A9E8A010045176A421900BFB4 FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF
```

**每 16 字节一个单元，单元里有个 16 位计数器每次 +1（A5 6A → A5 6B → A5 6C…）**
—— 这不是新版 32 B 记录，是**旧版 16 B 格式的残留数据**（更早那次长跑写的）。

区段起点 idx 3840 = 字节 122880 = **扇区 30 的开头**，不是巧合。
区段终点约在扇区 129 —— 正好是旧数据结束的地方。

## 6.2 根因：`e` 只擦"用到的部分"，而且检查挡住了擦除

**两个 bug 叠加：**

1. **`recorder_erase_all` 只擦 `ceil(count×32/4096)` 个扇区。**
   清空那一刻 s_count≈288 → 只擦了 **3 个扇区**。
   4 MiB 里其余 1021 个扇区的旧数据一动没动。
   而旧的"收敛循环"**骗过了自己**：擦完 3 个扇区后 `scan()` 发现槽 0 已空 →
   返回 0 → 提前退出。返回值、日志、流程全正常，**只有结果是错的**。

2. **`recorder_append` 的顺序是"先前置检查、后擦扇区"。**
   跨入有旧数据的新扇区时：检查读到旧数据 → 判"占用" → 作废跳过 → 返回 6。
   于是这个扇区的 128 个槽位被**一条条作废**，而**擦除永远不会执行**。
   ⇒ 在跨扇区场景下，"先检查后擦除"是一个**逻辑死锁**。

## 6.3 值得肯定的一面：防护机制全部按设计工作了

- **12728 个可疑槽位全部被前置检查拦下**，没有一条新数据被写进脏槽位
  （对照 9-17 那次：3 条按位与脏数据。这次是 0 条）
- `slot_abandon()` 让写指针持续前进，**采集层零丢失**
  （21 个采样点 `records == uptime − 674` 分毫不差）
- 3 条 UNFINISHED 里，idx 68 是**真实的两步写第二步失败**，
  被 `slot_abandon()` 正确处理（idx 68→69、seq 742→743，各跳一格，无脏数据）
- `lock_tmo=0`、`uart_hold_us=59894`（回绕修复后一直正常）

## 6.4 修复

| 修复 | 内容 |
|---|---|
| `recorder_erase_all` | 改为**擦整个记录区（1024 个扇区）**。"records=0" 从此等于真的干净。代价约 46 s（最坏 6.8 min），一次性手动操作可接受 |
| `recorder_append` | **扇区擦除挪到前置检查之前**；刚擦过的扇区跳过检查（必然是 0xFF，再读是浪费）。擦除失败时**不**作废槽位（下一秒重试） |

编译：零错误零告警，Flash 27 844 B / RAM 11 712 B。

## 6.5 遗留

- 需要重刷固件 + 重新 `e`（这次会真的擦 4 MiB，约 1 分钟）+ 重跑一晚
- 现有 11.6 h 数据的**采集层结论仍然成立**（零丢失），
  但"PC 端逐条校验全过"这个说法要等干净重跑后才能用
