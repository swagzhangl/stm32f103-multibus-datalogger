### ★ 实测案例 1：DWT 回绕周期算错（本项目最值钱的 bug 之一）

`delay_now_us()` 返回 `DWT->CYCCNT / 72`。CYCCNT 是 **32 位周期计数器**，
回绕周期换算成微秒是 `2³²/72 = 59 652 323 µs ≈ 59.65 s`，**不是 2³² µs**。

```
(now - t0) 跨回绕 → 得到 ~4.2e9 的假值 → 任何 timeout 判定立刻成立 → 假超时
```

- 实测铁证：串口打出 `uart_hold_us=4235319666`（真实只有 4.7 ms）
- 反推：`2³² − 4235319666 = 59 647 630`，`59 652 323 − 59 647 630 = 4693 µs` ✓
- **面试讲法**："'无符号减法天然跨回绕'这句话只在计数器铺满整个 2³² 值域时成立；
  除法换算后的计数器值域变小了，这个前提就不成立了。"
- 修复：`delay_elapsed_us(t0)` 显式按真实周期处理（`delay_us.c`）
- **注意**：`delay_us()` 里直接比较原始 CYCCNT 是对的（那是真 32 位），不用改

### 实测案例 3：PC 端复算的运算符优先级 bug

`multibus.py` 里 `v - X >> 4` —— **Python 的 `-` 优先级高于 `>>`**，
被解析成 `(v - X) >> 4`；C 里那个 `>> 4` 只作用于减数。
湿度算成 3.05 %RH（固件 55.49 %RH，物理上不可能）→ 一眼锁定错在 PC 端。

**面试讲法**：跨语言移植公式时，**移位必须加括号**写在被除数自己那一侧。

### 实测案例 4：静默写失败（本项目最后一个被揪出的缺陷）

**现象**：4061 条里 9 条连续"未收尾"（idx 1629~1637），头 CRC 全对、尾 CRC 全 `0xFFFF`，
**固件没报任何错**，records 与秒数全程 1:1。

**机理**：第二步编程命令恰好在器件仍忙时发出 → **被静默忽略**（不报错、不烧毁、就是不干活），
随后的状态轮询又恰好读到"空闲" → 整条链路都以为写好了。

**修复**：**写后回读校验** —— 写完把这条读回来重算头尾 CRC：
OK 就过；"头对尾没写上"→ 重发第二步一次再验；仍不行 → 作废该槽位。
代价每条约 0.4 ms。

**面试讲法**："返回值只能证明'命令发出去了'，证明不了'数据落进去了'。
对不可靠介质，写后回读是把假设变成证据的唯一手段。"

### ★★ 实测案例 5：尾 CRC 退化成常数（数学必然，毕设"理论分析"得分点）

**现象**：1246 条记录里 1245 条的尾 CRC 存值都是 `0x0000`。

**第一层**：CRC-16/MODBUS 满足**追加性质** —— 把 CRC 追加到数据后再算一次，恒为 0。

**第二层（换初值也救不回来）**：CRC 对初值是**仿射**的，`crc_J(m) = crc_0(m) ⊕ g_len(J)`，于是

```
尾 = crc_J(数据 ‖ 头CRC) = g_len(0xFFFF ⊕ J)      ← 与数据无关
```

两次实测都符合公式：

| 尾 CRC 初值 | 实测值 |
|---|---|
| `0xFFFF`（从头 CRC 续算） | 恒 `0x0000` |
| `0x0000`（换初值重算） | 恒 `0x4FFE` |

> **结论：只要第二条 CRC 的覆盖范围 =「数据 + 第一条 CRC 的输出」且用同一多项式，
> 它必然退化成常数。** 与初值、字节序无关。
> 退化后只剩"写完没写完"一个作用，等价于 2 字节固定标记，**不是校验值**。

**修法**：尾 CRC 改用 **CRC-16/CCITT-FALSE(0x1021)**（覆盖范围不变，换多项式打破恒等式）。
标准检查值 `crc16_ccitt("123456789") = 0x29B1`，固件开机 `#CRC2` 行自证。
修复后 6 条记录尾 CRC = `0x1308/0xFDAD/0xFEE0/0x3207/0x4985/0x89A4`，各不相同。

**面试讲法**："我原本尾 CRC 从头 CRC 续算，上板发现它恒为 0；
推导后确认这是 CRC 仿射性的必然结果 —— 这也是为什么双 CRC 必须换多项式。"

### 实测案例 6：检查与擦除的顺序死锁

旧顺序"**先**前置检查、**后**擦扇区"：跨入一个有旧数据的扇区时，
检查读到旧数据 → 判"占用" → 作废跳过 → **擦除永远不会执行**。
实测后果：扇区 30~129 共 **12728 个槽位**被一条条跳过。

**修法**：扇区擦除挪到前置检查**之前**；刚擦过的扇区跳过检查（必然是 0xFF）。

### 实测案例 7：`e` 命令"成功地什么都没做"

`recorder_erase_all` 只擦 `ceil(count×32/4096)` 个扇区 —— 清空时 s_count≈288 → **只擦 3 个**，
4 MiB 里其余 1021 个扇区的旧数据没动。旧的"收敛循环"还骗过了自己：
擦完 3 个后 `scan()` 发现槽 0 已空 → 返回 0 → 提前退出。
**返回值、日志、流程全正常，只有结果是错的** —— 最难查的一类 bug。
**修法**："清空记录区"只有一种诚实实现：把 4 MiB 全擦（实测 1024 扇区约 26 s）。

### 实测案例 8：同一槽位被写两次的铁证

9-17 那次：idx 980/981/982 头 CRC 失败，解析出的 seq 是 **相邻序号按位与**：
`0x400 & 0x401 = 0x400`、`0x500 & 0x501 = 0x500`。
看到重复 seq 且值在 2 的幂附近 → 直接怀疑同一槽位被写了两次。
**修法**：前置检查 + 任何失败都 `slot_abandon()`。

### ★ 实测案例 9：假 PASS（验证方法的根本缺陷）

早先报告"假日志复算 18 项 0 不一致" —— **不可信**。

## 十一、学习路径建议（如果重来一遍 / 查漏补缺）

**第一优先（面试必手写）**
1. 时钟树配置 + FLASH 等待周期 —— 不理解这个，后面全靠背
2. GPIO 寄存器 + USART BRR 计算
3. I2C 起始/停止/应答时序（bit-bang 最练基本功）
4. SPI 四模式 + 什么时候采样
5. FreeRTOS：队列 / 互斥锁 / `vTaskDelayUntil`
6. NOR Flash 的"擦后写"模型

**第二优先（理解原理，答追问）**
7. CRC 原理：追加性质、仿射性、为什么双 CRC 要换多项式
8. 定点数 Q 格式与补偿公式
9. 断电一致性：两步写 + 双 CRC + 槽位状态机
10. 栈水位实测与重分配
11. 链接脚本与启动流程

**第三优先（知道即可，被问到能说清）**
12. heap_4 分配策略、优先级反转、时钟拉伸
13. Makefile / Eclipse 工程结构
14. 逻辑分析仪的使用（Mode2 定性还欠这一步）

**贯穿始终的一条主线**
> **"自证而不是自称"** —— 时钟要回读、CRC 要对检查值、写入要回读校验、
> 校验要用外部基准。这条思路贯穿本项目所有修复，也是面试里最能拉开差距的一句话。
