## 二、为什么非要有 Python？（这是关键，明白了就不会觉得它是多余的）

### 一个类比：固件是**考生**，Python 是**考官**

你想想考试是怎么判卷的：

- **让考生自己批自己的卷子** → 他只能告诉你"我写的两遍一样"，
  **证明不了答案是对的**。
- **换一个老师独立批一遍** → 这叫"第三方判卷"，才叫真验证。

这个项目里的 Python 就是那个**第三方考官**。

### 落到你的简历上，它具体在证明哪两句话

| 简历原话 | 谁在证明它 |
|---|---|
| 「温湿压结果经 **PC 端复算逐位一致**」 | `verify_bme280.py` |
| 「打通 I2C 采集 → SPI 存储 → UART 上传 → **PC 逐字节校验**的完整闭环」 | `parse_records.py` |

**注意"PC 端"这三个字** —— 它说的就是这些 Python 脚本。
如果只有板子，这两句话是写不出来的：板子自己校验自己，不叫"PC 端校验"。

### 为什么不能让板子自己校验自己？

看这张图就明白了：

```
   ┌─────────── 板子内部（固件 C 代码）───────────┐
   │                                              │
   │  BME280 → 补偿算法 → 打包32B → 写Flash        │
   │     ↑                     ↓                  │
   │  读校准系数            读回来重算CRC          │
   │                                              │
   └──────────────────────────────────────────────┘
                    ↑
             这一整圈全在板子里
        如果补偿公式写错了，两边一起错 → CRC 依然"全对"
        （因为 CRC 只检查字节有没有变，不检查算得对不对）

   ┌─────────── 电脑上的 Python ───────────────────┐
   │  拿【原始 ADC 值 + 出厂校准系数】              │
   │  照着 Bosch 官方公式【重新算一遍】              │
   │  和板子给的结果比对 → 一模一样 才算通过         │
   └──────────────────────────────────────────────┘
                    ↑
        这是独立的一份实现，它不知道板子怎么算的
        → 两边都对得上，才能说"结果可信"
```

**再说白一点**：

- **CRC 只能回答**：「存进去的字节 = 读回来的字节吗？」
- **CRC 不能回答**：「从传感器读到的数、算出来的温湿压，对不对？」

这是两个完全不同的保证。所以必须有人从**外面**再验一遍 —— 那个"外面的人"就是 Python。

## 五、每个选项到底在干什么

### 1 · 检查环境
看看 Python、pyserial、脚本、编译产物齐不齐。**随时可以跑，不会改任何东西。**

### 2 · 假日志演练 + 基准向量（★ 建议第一件事就做这个）

**这个不需要板子。** 它会跑四步：

1. **★ 基准向量测试**（`golden_vectors.py`）—— 用**真板子实测的数据**校验 PC 端算法
2. 造一份**格式和真日志完全一样**的假日志（里面故意混了 2 条"断电残记录"）
3. 用它跑一遍复算验证
4. 再用它跑一遍双 CRC 校验

**为什么要先做这个？** 因为这样能先把"**工具本身有没有问题**"这件事排除掉。
否则当你接上真板子、工具报了个错，你会分不清是**工具**的问题还是**硬件**的问题，
白查半天。

#### ⚠️ 第 1 步和第 3 步的可信度**完全不同**（这里踩过一个坑，值得记）

这两步看起来都在"验证算法"，但性质相反：

| | 期望值从哪来 | 可信度 |
|---|---|---|
| **第 1 步 基准向量** | **固件的 C 实现**（两套独立代码） | ✅ **真验证** |
| 第 3 步 假日志复算 | 假日志是 `make_sample_log.py` 用 `multibus.py` 算的，复算又用 `multibus.py` | ❌ **只证明自洽** |

**踩过的坑**：当初只做了第 3 步，报"18 项 0 不一致"，就写了"工具链已验证"。
结果真板子一跑，湿度算成 **3.04 %RH**（固件给的是 55.48 %RH）。
根因是 `multibus.py` 里 `v - X >> 4` 的 **Python 运算符优先级**问题
（Python 的 `-` 比 `>>` 高，C 里不是），而假日志和复算用的是同一条代码，
所以自己对自己必然"一致"。真板子数据才是外部基准。

> **一句话教训：用被测代码自己造测试数据，等于没测。**
> 所以第 1 步是**独立基准**，必须先跑；改过 `multibus.py` 之后也要重跑。

**它能证明什么、不能证明什么**：

| ✅ 能证明 | ❌ 不能证明 |
|---|---|
| PC 端算法与固件**逐位一致**（第 1 步） | **不能**证明固件"从传感器读到的数是对的"（那要上板看数值是否合理） |
| 记录格式、CRC 覆盖范围自洽 | 不能替代上板验证 |

固件和 PC 到底是不是同一套算法，还可以靠**开机横幅的 `#CRC` 行**对答案：

```
固件开机时打：  #CRC,check='123456789',got=0x4B37,expect=0x4B37,PASS
你电脑上跑第 7 项： got = 0x4B37
两边相同 → 算法一致，可以放心往后做
```

### 8 · 烧录固件（★ 板子到手的第一件事）

**为什么它排在这里、而不是让你先装 CubeIDE？**
因为**烧录根本不需要 CubeIDE**。ST-Link 配合命令行烧录器就能干完这件事，
而 CubeIDE 自带的那个烧录器（CubeProgrammer）就在你硬盘上，不用另外装。
（当然，**你想用 CubeIDE 也可以** —— `firmware\` 本身就是 CubeIDE 工程，见 `docs\09`。）

它会：
1. **自动找出所有编译产物**（`Debug\firmware.elf` 和 `build\fw.hex` 都会列出来），按新旧排序
2. **检查源码有没有比固件新** —— 有就提醒你先重新编译（防止烧到旧版本）
3. **自动找到** CubeProgrammer（第一次找到后会记住路径）
4. 把要执行的命令**原样打给你看**，让你确认
5. 你按 `y` 才开始烧

**为什么要"挑产物"这件事？**
这个工程有**两套编译方式**，产物放在两个地方：

| 你在哪儿编译 | 产物 |
|---|---|
| CubeIDE（`Ctrl+B`） | `Debug\firmware.elf` |
| 命令行 `make` | `build\fw.hex` |

而且 **CubeIDE 默认不产出 `.hex`**（只出 `.elf`）。
如果写死只烧 `build\fw.hex`，你在 CubeIDE 里编译完再烧，烧进去的会是**旧版本** ——
现象是"代码明明改了却没生效"，非常难查。所以第 8 项帮你把这件事管起来。

**它会打印这样一行**（这就是你以后可以自己手敲的命令）：

```
"…\STM32_Programmer_CLI.exe" -c port=SWD freq=4000 -d "…\Debug\firmware.elf" -v -rst
```

| 参数 | 意思 |
|---|---|
| `-c port=SWD freq=4000` | 用 SWD 口连，4 MHz。克隆版 ST-Link 用这个速度最稳 |
| `-d <file>` | 把固件写进芯片。**`.hex` 和 `.elf` 都自带地址**，不用像 `.bin` 那样另写 `0x08000000` |
| `-v` | 写完**回读比对**。不加就只是"写进去了"，不保证写对 |
| `-rst` | 软复位，让新程序立刻开始跑。用软复位是为了不依赖 NRST 那根线 |

> 注意是 **`-d`**（download，照文件里的地址写）而不是 `-w`（write，要你自己给起始地址）。
> 有些教程写 `-w` 也能过，是因为它假定了一个默认地址；用 `-d` 才是对 `.hex`/`.elf` 的正确用法。

**烧完必须确认出现这两行**：`Download verified successfully`、`Software reset is performed`。

> ⚠️ **万一烧完串口一个字都没有**：先**拔插一次 USB**。
> 调试器复位后内核可能停在暂停态，程序根本没被执行 —— 这不是代码问题。
> 详细原因和另外两种解法见 `docs\08_怎么打开工程与烧录.md` 第 6 节。

### 8.5 · 重刷固件之后：一键跑完「清空 → 采集 → 倒出」

**什么时候用**：每次重刷固件、想重新攒一批干净记录的时候。

```cmd
python tools\after_reflash.py 180
```

（数字 = 采集多少秒，默认 180 秒 ≈ 180 条记录。）

它会一口气做六件事，全程不用你敲命令：

| 步 | 做什么 | 你要盯哪一行 |
|---|---|---|
| 0 | 监听 3 秒确认板子在跑 | `[0] OK，板子在跑` |
| 1 | 发**两次** `e` 清空记录区（中间隔 3 秒） | 第二次应回 `#ERASE,OK,records=0` |
| 2 | 发 `p` 看状态 | `#STA,...records=0` |
| 3 | 采集 180 秒 | 每秒一行 `[Ns] seq=N … store=ok` |
| 4 | 发 `r` 倒出全部记录 | `#DUMP,begin,total=…` 与 `#DUMP,end` |
| 5 | 发 `s` 取栈水位 | `#STK,...`（后面算压缩比要用） |

跑完日志自动存到 `firmware\logs\records_v2.txt`。

**⚠️ 为什么必须先清空？**
尾 CRC 算法中途改过（MODBUS → CCITT-FALSE），这是**破坏性格式变更** ——
旧记录在新固件下会被判成"未收尾"，不清空就拿不到干净的校验结果。
详见 `docs\11_W4缺陷分析与修复.md`。

⚠️ **跑之前先关掉串口助手**（COM8 一次只能被一个程序占用）。

### 8.6 · 24 小时长跑（拿「连续 N 条」和「栈压缩比」这两个数）

三个脚本，全程不用记命令：

| 阶段 | 命令 | 干什么 |
|---|---|---|
| **开始** | `python tools\longrun_start.py` | 清空记录区 → 确认 `records=0` → **打印开始时间** |
| **过夜** | `python tools\longrun_watch.py 8` | **自动每隔 30 分钟采一次栈水位，跑满 8 小时后自己退出** |
| **中途** | `python tools\longrun_sample.py` | 手动补采一次（只发 `s`/`p`，**不占 SPI 锁**） |
| **收尾** | `python tools\longrun_finish.py` | 取栈水位 → 倒出全部记录 → 存 `logs\longrun_records.txt` |

> **为什么必须有 `longrun_watch.py`？**
> 睡一觉起来如果只有 1 条栈水位样本，那个压缩比还是不能填简历 ——
> `uxTaskGetStackHighWaterMark` 只反映**已经跑过的路径**，样本太少等于没测。
> 挂它过夜，8 小时能攒 16 条以上。
>
> 它**只发 `s` / `p`**，不碰 SPI 锁。已实测：挂着的 106 秒里
> `records` 严格等于 `uptime − 674`（270→376，一秒一条）—— **零丢失**，不影响采集。

**想过夜跑，正确姿势是这两步**（用完整路径，从任何目录都能直接复制粘贴）：

```cmd
:: ① 开一个 cmd 窗口，挂上（8 小时后自己退出，这个窗口不要关）
python D:\work\2026-09-17-15-24-45\firmware\tools\longrun_watch.py 8

:: ② 把电脑设成【从不睡眠/休眠】（否则 USB 掉电，板子停，白跑一晚）

:: ③ 明早起来，等上面那个窗口自己退出，再跑
python D:\work\2026-09-17-15-24-45\firmware\tools\longrun_finish.py
```

> 已经 `cd /d` 到 `firmware` 目录的话，上面那两个可以简写成
> `python tools\longrun_watch.py 8` 和 `python tools\longrun_finish.py`。

跑完把 `logs\longrun_records.txt` 和 `logs\longrun_stack.txt` 留着，那是简历数字的原始凭据。

**四条不能违反的规矩：**

1. **板子不能断电。** PC 别关机、别拔 USB；有条件就接独立电源（你有 18650 + LM2596）。
   断一次电，前面的记录虽然还在（这正是断电续写在做的事），但"连续运行 X 小时"这个数就废了。
2. **中途绝对不要发 `t` 或 `r`。**
   它们长时间占用 SPI 锁，采集任务拿不到锁就会成片 `store=skip`，
   于是 seq 出现跳号 —— 简历上"连续 N 条无丢失"这个数字直接被污染。
   只发 `s`（看栈）和 `p`（看状态）是安全的，它们不碰 SPI。
3. **栈水位要累计 10 次以上**，而且必须覆盖全程。
   `uxTaskGetStackHighWaterMark` 只反映**已经跑过的代码路径**，
   采一次就照着缩栈，将来一跑没跑过的分支就可能 HardFault。
4. **收尾倒出可能要几分钟**（几千条记录，串口 115200 一条条打）。脚本最多等 20 分钟，别中途 Ctrl+C。

### 9 · 看串口输出（只监视，不改板子）

就是"打开串口看一眼"，不校验、不碰芯片。
输出**同时**打在屏幕上并存到 `logs\monitor.txt`。

**开机横幅要核对这四行**：

| 行 | 看什么 | 对了说明什么 |
|---|---|---|
| `#CLK,got:` | 四个数字要和下一行 `expect` **完全一致** | 72 MHz 时钟树真的配成了 |
| `#UART,BRR=` | `625`，且 `DWT=ok` | 波特率算对了，微秒延时可用 |
| `#CRC,...,PASS` | 出现 **PASS** | 固件和 PC 是同一套 CRC 算法（后续校验的前提） |
| 之后每秒一行 | 周期性的采集/上报 | FreeRTOS 三任务都在跑 |

**看不到任何输出时，按这个顺序查**：
1. **拔插一次 USB**（最常见）
2. TX/RX 接反了 —— 要**交叉**：板子 PA9(TX) → CH340 的 RX
3. 波特率不是 115200

### 3 · 温湿压 PC 端复算逐位一致
对应**简历第 3 条**。前提：板子插好、已经烧了固件、**串口助手要关掉**
（串口一次只能被一个程序占用，不关会报"打开失败"）。

它会自动：发 `c` 取 33 个校准系数 → 发 5 次 `m` 触发 5 次测量 → PC 端独立复算 → 比对。

**判据**：最后出现「结论：PASS」，并且上面写着「不一致 0 项」。

### 4 · 32 B 记录 PC 逐字节双 CRC 校验
对应**简历第 4 条**。它把 Flash 里存的记录全倒出来，PC 端逐条重算头、尾两个 CRC。

**判据**：最后出现「结论: PASS」。
结果还会导出一份 `logs\records.csv`，**Excel 双击直接能打开**，可以拿去画图放进论文。

⏱ **耗时提醒**：115200 波特率下大约每秒 1.5 KB。
1000 条记录约 50 秒，10000 条约 8 分钟，**跑满容量（13 万条）要 1.5 小时以上**。
验收时跑几百到几千条就够，不用全倒。

### 5 · 算栈水位压缩比
对应**简历第 1 条那个红色占位符 `［实测后填］`**。

⚠️ **这个数字必须是实测的，不许用示例值。** 所以流程是：
1. 先让板子连续跑一段（越久越准，建议 1~24 小时）
2. 跑第 5 项，抓 300 秒日志（或更久）
3. 脚本会算好并给出**可以直接粘进简历的句子**

### 6 · W4 全量自检
一次跑完四块，每块都有可留存的输出：

| 检查 | 看什么 |
|---|---|
| 四种 SPI 模式回环 | 四种模式应**全部 MATCH**（全 MATCH 才是对的，原因见 `docs/04`） |
| 四种模式读 W25Q64 ID | **读通模式数 = 2**（Mode0 与 Mode3 得 `EF 40 17`） |
| 32 B 记录闭环 | `#REC,written=256,mismatch=0,result=PASS` |
| 断电三情况 | `#PWR` 三行全 PASS |

### 7 · 对 CRC 标准检查值
**最快的一步**，不需要板子。就是验证"PC 端和固件是同一套 CRC 算法"。

### p · 改串口号
不知道是哪个 COM 口？在菜单里填 `?` 就会列出来。
填过一次它会**自动记住**，下次不用再填。

> 其实平时用不到这一项：任何需要串口的步骤都会问你串口号，
> **你直接填一个新的，它就会记住新的**。

## 七、常见问题

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 提示 `'python' 不是内部或外部命令` | 命令行不在正确的环境 | 用第 4 节的"地址栏输入 cmd"方法打开 |
| `打开 COM5 失败` | **串口助手还开着**（最常见）；或串口号写错 | 关掉串口助手；菜单里填 `?` 列出可用串口 |
| 中文显示成乱码 | 控制台编码问题 | 菜单本身不受影响；如果在意，先在 cmd 里敲 `chcp 65001` |
| `ModuleNotFoundError: No module named 'serial'` | 用错了 Python | 用菜单（菜单会用正确的那个 Python）。手动跑时用 `C:\Python311\python.exe` |
| 第 3 步返回"返回码 1" | 假日志里有故意造的异常记录 | **正常**，脚本"发现了异常"正是它该做的。真板子数据正常时返回 0 |
| 第 8 项报 `No ST-LINK detected` | **CubeIDE 的调试会话还开着**，占着 ST-Link | 关掉 CubeIDE 的调试会话（或整个 CubeIDE）再烧 |
| 第 8 项报连不上 / target 无响应 | SWD 线松了、板子没供电 | 检查 SWDIO / SWCLK / GND / 3.3V 四根线；看板子电源灯亮不亮 |
| **烧录成功，但串口一个字都没有** | 调试器复位后内核停在暂停态，**程序根本没跑** | **拔插一次 USB**（最可靠）。详见 `docs\08` 第 6 节 |
| `py` 或 `python tools\run.py` 提示找不到文件 | 不在 firmware 目录下运行 | 在 `firmware` 文件夹地址栏输入 `cmd` 回车，再敲命令 |
| 日志文件在哪 | — | 都在 `firmware\logs\` 目录里，**别删**，那是验收证据 |
| CSV 在 Excel 里中文乱码 | 编码 | 我导出的 CSV 带 UTF-8 BOM，Excel 能直接正确打开；若仍乱码用"数据→从文本导入"选 UTF-8 |

## 九、一句话总结

> **Python 在这个项目里的角色是「第三方考官」，不是你项目的组成部分。**
> 固件（C）负责在板子上干活，Python 负责在电脑上**独立地**验证固件干得对不对。
> 你不需要写 Python，只需要敲 `python tools\run.py`，然后选数字。
